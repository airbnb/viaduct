# Tenant API Design Principles

The purpose of this document is to record the principles that have shaped the design of our Tenant APIs. We're maintaining this document in a very lazy manner: as we find ourself using unwritten design principles to explain to other team members why things are the way the are, or why we should do new things one way versus another way, we'll add such principles to this document.

## Prefer composibility

Viaduct Classic had many features that "bundled" a lot of functionality. For example, `@serviceBackedNode` bundled downstream-service clients, data loaders, and object-mapping into a single feature. When tenant developers needed these things composed in exactly the way `@serviceBackedNode` composed them, this was fine, but when they needed them composed in a different way, they were stuck implementing all of the bundled functionality using very low-level mechanisms.

In Viaduct Modern our principle has been to expose functionality to tenants using unbundled, more surgically-defined features designed to compose well with each other. In the case of `@serviceBackedNode`, for example, we have decomposed that into batch resolvers for more fluent data loading and a GRT-specific object mapping library for object mapping. We've left service-clients out of the core framework as an integration issue Service Engineers should design versus an issue Viaduct should dictate. (This is another design principle: use an SPI to separate core Viaduct concerns from larger IT-stack integration issues that should be the concern of Service Engineers.)

## Avoid expressing implementation details in the GraphQL schema

Viaduct Classic (and many other schema-first GraphQL systems) use GraphQL directives and/or "smart doc-strings" (ie, directives inside of GraphQL doc strings) as a convenient place to put implementation-related information, such as which Kotlin class implements the resolver for a field. Our experience is that these directives tend to proliferate and also become large and awkward, making the schema hard to read. Also, while in theory they can be filtered out so as to not litter the "consumer's" view of the schema with implementation noise, such tooling is rarely written. Finally, it tends to spread implementation out across both schema files and Kotlin files, making it difficult to navigate the full implementation of a schema.

In Viaduct Modern we have avoided putting implementation information into directives. So far we have just one exception, `@resolver` and its arguments, which are a fundamental seam in the Viaduct engine API that gets exposed uniformly by _all_ Tenant APIs. Given the fundamentality of `@resolver`, and after some exploration, we concluded this is an exception worth making. But even in the context of this exception, we have kept Tenant-API-specific implementaiton details out of the schema. For example, in the Viaduct Modern Tenant API, the mapping of Kotlin resolver classes to the fields they resolve is done via our code-generation patterns (i.e., resolver base classes) and our use of annotations (`@Resolver`).

Where possible, we encourage Tenant APIs to put implementation details in the code itself (as we've done, for example, by having the `objectFragment` parameter to the `@Resolver` annotation). This tends to bring together related implementation information into one place that can easily be inspected. Where it's not possible, e.g., configuration details for a GraphQL-relational-mapping library, we recommend putting such configuration information into a YAML file in a module's `src/main/viaduct` directory (which is where the schema is also found).
