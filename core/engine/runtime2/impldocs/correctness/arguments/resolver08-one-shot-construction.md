# Argument for `resolver08-one-shot-construction`

This claim concerns [Resolver08](../../../src/testFixtures/kotlin/viaduct/engine/runtime2/resolvers/resolver08/Resolver.kt) in its `FromArgument` object-fragment domain: finite post-validation selection forests and returned values, canonical field resolvers, a registry accepted by the conservative acyclic coordinate-level resolver-demand graph, and no runtime `FromObjectField` binding, nonempty resolver Query fragments, directives, `@parent`, checkers, or deferred execution. The graph may reject a world whose exact active occurrences would be acyclic, including a syntactic cycle broken by an error-valued argument; such rejection is an intentional scope restriction. Argument-error keys complete as errors without invoking resolver bodies, and source-supplied passive fields do not activate their registered resolvers. The one-application claim concerns activated ordinary resolver occurrences. Recursive objects, list elements, execution epochs, and otherwise equal objects are distinct occurrences and may each require their own field-resolver application.

For one concrete object occurrence, `closeOrchestrationConstructionDemand` repeatedly binds newly discovered resolver keys' argument-defined variables, instantiates their fixed object fragments at exact OER paths, and adds their grounded requirements. The resulting object-rooted value selections are grouped by `ObjectEngineResult.GroundKey`, so duplicate selections and aliases denoting the same alias-free cell contribute subselections to one group. Orchestration excludes already supplied passive cells and queues the remaining keys in the topological order returned by `SiblingDependencyLogic.order`. Publication preparation claims each destination cell before enqueueing its field task.

Before a selective producer is applied, `successorDemand` walks its complete output demand, substitutes argument-defined variables from nested resolver occurrences' concrete arguments, and recursively adds their input requirements at guarded object paths. The producer therefore receives the transitive passive and resolver-boundary demand required by nested consumers before its result is projected. That demand is aggregated before execution; the queue does not rerun an already applied producer to deepen its result.

Passive resolution stops at null, error, and simple values, copies demanded passive fields, and allocates one mutable OER per object occurrence. Internal typename demand uses the registered `V_A_typename` resolver and follows the same active-field boundary as other registered resolvers. Orchestration closes an object's demand before passive descent. Parent cells and list positions retain the exact target OER identities while queued tasks populate them; no ancestor is reconstructed. Explicit field and list-index path components distinguish occurrences even when their values are otherwise equal.

The reactor holds child orchestration discovered during passive descent until its parent has orchestrated. Among runnable tasks, greater Query-OER depth precedes greater task-path depth (the containing object's path for a field task), then field tasks precede orchestration at equal depth, and insertion order breaks remaining ties. Within this claim's empty-Query-fragment domain, sibling dependency order is preserved by insertion order, while deeper descendant and list-reference work completes before a later sibling consumer materializes its input. [The Resolver07 closure argument](resolver07-demand-closed-result.md#lemma-2-queue-order-makes-resolver-inputs-available) gives the corresponding readiness reasoning. The reactor drains all queued work and rejects unfinished held or dispatched tasks before returning.

Each orchestration is dispatched once, each unresolved ground key yields one claimed field task, and each queued task finishes once. Together with successor-demand aggregation, these properties establish one ordinary field-resolver application per activated ordinary resolver occurrence. Root-field references retain their separate invocation roots and may invoke target resolvers along a reference tail; those invocations are distinct from rebuilding the consumer occurrence. Passive descendants remain intact, and repeated applications at distinct recursive objects or list elements remain valid.

[ResolverWitnessTest](../../../src/test/kotlin/viaduct/engine/runtime2/resolvers/resolver08/ResolverWitnessTest.kt) compares independently reconstructed application identities and counts with observed invocations in generated worlds, including permutation-equivalent queries. [ResolverSelectiveDemandWitnessTest](../../../src/test/kotlin/viaduct/engine/runtime2/resolvers/resolver08/ResolverSelectiveDemandWitnessTest.kt) checks a producer's exact supplied successor demand. These witness assertions supply evidence for the one-shot claim beyond the ordinary generated result-correctness and permutation checks, which do not enable exact application counting.

Deterministic feature contracts and generated properties exercise nested and recursive values, interfaces, unions, lists, arguments, ordinary field resolvers, root-field references, and `Query.node` dispatch. This evidence constrains the Kotlin implementation within the stated domain. The claim does not establish JVM scheduling, runtime side-effect behavior, or minimal construction outside that domain.
