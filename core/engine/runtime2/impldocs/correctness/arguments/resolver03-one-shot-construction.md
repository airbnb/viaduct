# Argument for `resolver03-one-shot-construction`

This claim concerns `viaduct.engine.runtime2.resolvers.resolver03` in its `FromArgument` object-fragment domain: finite post-validation selection forests, canonical field resolvers, a registry accepted by the conservative acyclic coordinate-level resolver-demand graph, and no runtime `FromObjectField` binding, nonempty resolver Query fragments, directives, `@parent`, checkers, or deferred execution. The graph may reject a world whose exact active occurrences would be acyclic, including a syntactic cycle broken by an error-valued argument; such rejection is an intentional scope restriction rather than a counterexample to this claim. The claim is scoped per resolver-bearing OER occurrence; distinct recursive objects, list elements, execution epochs, and otherwise equal objects are distinct occurrences and may each require their own field-resolver application.

For one concrete object occurrence, Resolver03 uses `closeConstructionDemand` to repeatedly bind every newly activated resolver key's argument-defined variables, instantiate its fixed open object fragment at the key's exact OER path, and add the grounded direct requirements to the applicable selections. The resulting selections are grouped by `ObjectEngineResult.GroundKey`, so duplicate selections and aliases that denote the same alias-free cell contribute their subselections to one group. `SiblingDependencyLogic.order` is a permutation of the unresolved key set, and the constructor writes each grouped key exactly once after every sibling key required by its grounded object fragment is present in the current OER.

Before a field resolver is applied, `successorDemand` walks its complete output demand, substitutes argument-defined variables from each nested resolver occurrence's concrete arguments, and recursively adds that resolver's input requirements at its guarded object path. A selective producer therefore receives the transitive passive and resolver-boundary demand required by every nested consumer before its result is projected, rather than discovering additional demand after the producer cell has been constructed.

`resolvePassiveValues` first constructs the selected passive result beneath a produced value. Internal typename demand is represented by the registered `V_A_typename` resolver, so construction omits it at the same active-field boundary as every other registered resolver. Construction stops at null, error, and simple values, copies demanded passive fields, and omits registered resolver fields while allocating one mutable OER for every object occurrence. For each occurrence requiring registered resolution it retains the exact path, source object value, collapsed selections, and target OER. The parent cell and immutable list positions retain those target OERs before the targets are populated deepest first through the ordinary object constructor, so no ancestor is reconstructed. Object fields and list indices are explicit path components, so each list element is a distinct object occurrence receiving the same collapsed demand. Within one object continuation, keys already present in the target OER are excluded from the unresolved set. This preserves the boundary between one application for one occurrence and valid repeated applications for distinct occurrences without discarding passive descendants.

Deterministic counterexamples and generated properties exercise nested and recursive values, interfaces, unions, lists, arguments, ordinary field resolvers, root-field references, and `Query.node` dispatch. This evidence constrains the Kotlin implementation within Resolver03's stated domain; it does not establish JVM scheduling or runtime side-effect behavior.
