# Argument for `field-only-node-lowering`

This claim concerns the pre-reasoning translation performed by `TestWorld`, not production GraphQL schema rewriting and not a claim that Viaduct's public node-resolver API has disappeared. The supported source domain contains ordinary GraphQL SDL and fragments, field resolver functions, and raw node lookup functions. A Node-valued field must be declared as `Node` or a subtype, every possible concrete output type must have a raw node lookup, and outputs that mix node-resolved and inline object values are excluded.

The GraphQL-Java source schema remains unchanged and is retained for source validation. The separately decoded model schema retains every Node-valued field at its source coordinate with its complete return type, argument definitions, list wrappers, and nullability. When the source declares `Node` but omits the standard root field, fixture lowering adds the canonical model-only field `Query.node(id: ID!): Node`. No per-field producer coordinates or per-type payload records are generated, so ordinary GraphQL covariance is preserved directly by the retained schema.

When a source field resolver or passive source object supplies a node reference, fixture composition maps that value pointwise to a `RootFieldReferenceData` targeting `Query.node`. Null, error, object, and list structure are preserved recursively. The root-field-reference argument uses an internal encoding that contains the concrete canonical Node object type and the original resolver ID; the original ID remains authoritative even if the eventual node-resolver payload repeats a different ID.

Because the producing field retains its coordinate, `foo(a)` and `foo(b)` remain distinct ordinary ground keys. The synthesized `Query.node` reference carries only its grounded encoded `id`; no source producer arguments are transferred into node dispatch.

Registry composition gives `Query.node` built-in dispatch logic in addition to its ordinary client-facing behavior. An internally encoded ID is decoded and validated against the possible concrete types of the declared `Query.node` output. The concrete object type selects the raw node resolver, which receives the untouched original ID and Resolution's node-owned demand. A normal client `Query.node` call whose ID lacks the internal prefix continues through the ordinary field resolver. `Query.nodes` is an ordinary root resolver whose list elements may each be `Query.node` references, so mixed concrete types dispatch independently at each list position without introducing batching or deduplication.

Ordinary root-field-reference conformance conservatively requires every possible target type to fit the consumer. Applying that rule to the statically abstract `Query.node: Node` would reject a reference published into a narrower `User` field before invocation. For the canonical node-reference encoding, conformance instead validates the encoded concrete type against the consumer's possible object types. This preserves the same pre-invocation restriction with better information; the resolved runtime object is still validated against both the decoded concrete type and the consumer field type before publication.

The implementation tests exercise the claim by checking that the GraphQL-Java schema stays source-only, Node-valued field coordinates and return covariance are retained, source-shaped references normalize recursively, malformed or incompatible encoded identities are rejected, concrete and abstract consumer conformance is checked, `Query.node` dispatches by concrete type, `Query.nodes` resolves list elements independently, selective ID-only demand skips tenant node code, and the authoritative reference ID survives node-resolver output and root-reference tails. Mixed node/inline abstract outputs, missing node lookups, batching, caching, and deduplication remain outside this evidence and the claim.
