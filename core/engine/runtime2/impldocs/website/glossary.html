Viaduct and its contracts

NameIn codeWhat it is
sourceThe spec’s objectValue; QPlanExecutionSource (Runtime2)The parent object’s value that each of its fields is read from, in a shape the spec leaves unconstrained. In Runtime2 it wraps an object result, the engine’s store of one object’s field values.
multi-tenancy—Many teams contributing schema and resolvers to one connected schema, each tenant owning its own part.
resolverFieldValueResolver, SDL @resolverTenant code registered for one object field that produces that field’s value. In Runtime2, it runs only where the parent resolver’s output lacks the value, and at most once for each cell that needs it. A cell is one field, with one set of arguments, in one object result. Its output can also contain nested values for the fields below it. Also called a field resolver or value resolver.
node resolverNodeResolverFunctionThe resolver a tenant writes for a type that implements Node: given an object’s ID, it loads that object. Runtime2’s registry, its per-schema map of resolvers, holds only field resolvers. So the engine reaches a node resolver through a field resolver, such as the built-in one for Query.node, and runs it like any other resolver.
registryResolverRegistryThe per-schema map from object fields to their value resolvers, and from fields and types to their access checkers. It is built once and by default shared by every request, and building it fails if the inputs of its resolvers and checkers depend on each other in a cycle.
required selection set (RSS)ResolverFragments: objectFragment, queryFragment; tenant API @Resolver(objectValueFragment = …, queryValueFragment = …)A resolver’s or checker’s declared inputs: the fields it needs to read, written as a selection set. The object RSS (objectValueFragment) is read from the object that contains the field, and the Query RSS (queryValueFragment) is read from Query. An RSS names direct inputs only; the engine adds the inputs of any resolvers they depend on. Also called a resolver fragment, with object fragment and Query fragment for its two parts.
selective resolver@resolver(isSelective: true), FieldValueResolver.ofSelective, FieldSelectivityProviderA resolver that is given the fields it is asked to return. In Runtime2, it must return only fields within them. Those fields are its successor demand: the fields requested below it plus the inputs that resolvers and checkers below it read. Runtime2 uses its output without trimming but checks it against that demand: a returned field outside it is an error. A non-selective resolver may return more, and its output is trimmed to the demand.
selective policyAssumptions.selectiveResolvers, snipToDemandA per-schema setting that limits every resolver’s output to the fields it was asked for. With it on, a selective resolver’s output must stay inside those fields, and a non-selective resolver’s output is trimmed to them. Runtime2’s main engine requires it on and refuses to start resolution with it off. The off setting exists only for tests of the reference resolvers, the test-only alternative engines. Whether a given resolver is selective is set for its field, in the schema or by the service, not by this setting.

Selections and keys

NameIn codeWhat it is
selectionSelection, ObjectSelectionOne requested field, with its arguments, its @skip/@include condition and its subselections. In Runtime2, a selection has no alias, and it records the parent types it applies to; the response view (MaterializeSelection) keeps the response key. It describes requested work, not a returned value or a resolver call.
selection forestSelectionForestA collection of selections and their subselections. It is unordered, except for mutations, and can contain repeated contributions of one key. The parsed operation is one, and so is every kind of demand: what an object must contain, what a resolver or checker reads, and what a resolver is asked to return.
field contribution—One appearance of a field in an operation’s or an RSS’s syntax. Repeating a field, or reaching it through two fragment spreads, gives several selections with the same key. It counts syntax, not objects in the result or resolver calls. It is not an occurrence, which is a position in the result tree.
flatteningflatten, flattenForMaterializationTurning GraphQL selections into plain field selections without fragment nodes. Spreads contribute their fields, and inline fragments contribute type and inclusion restrictions. Flattening keeps repeated keys as separate selections.
possible typesSelection.possibleTypesThe concrete parent object types a selection applies to, which is the intersection of the type conditions around it. Each child field starts afresh from its parent field’s result type, and the set can be empty even in a valid operation. Also called possible parent types.
inclusion conditionInclusionCondition (Always, Never, Requires; internal Conjunction, Disjunction)The parsed form of @skip/@include on a selection: Always, Never, or Requires. In Runtime2, Requires(v₁=true, v₂=false…) holds only when those resolver or checker variables have those values. A client’s directives become Always or Never once the operation’s variables are substituted, so Requires appears only in an RSS. Also called a guard.
concrete-object mergeSelectionForest.merge(type)Combining the selections that apply at one concrete parent type into one selection per key. Selections with the same key become one selection that is included if any of them is, and their subselections are put together, each still carrying the condition of the selection it came from. Only that one level is combined, and selections that @skip or @include rule out are kept. Also called merge or normalization.
object selection forestObjectSelectionForestA selection forest merged at one concrete type, with exactly one selection per key. Its child selections are not merged yet, and selections that @skip or @include rule out can remain.
mutation selection forestMutationSelectionForestThe ordered forest used at mutation roots and namespaces. False conditions are removed, equal response keys collect at their first appearance, and distinct aliases stay separate. It rejects ordinary merge, which would lose that order and identity. Also called a mutation forest.
materialize selectionMaterializeSelection, MaterializeSelectionForestA selection that keeps its response key, used to build tenant-visible inputs. constructionSelections() drops the response keys to give ordinary demand. It is not the final JSON response.
keyObjectEngineResult.Key, ObjectKeyA field plus its argument values, with no alias and no subselections. Merging groups selections by key, and an object key names one cell, so two aliases of one field with the same ground arguments share a cell in a query. Different arguments give different keys for the same field. Also called a construction key or object key.
ground keyGroundKeyA key whose arguments are ground, meaning resolved or wholly erroneous, with no variables left.
symbolic keynon-ground ObjectKeyAn object key whose arguments still contain resolver variables, for example one whose value is read from another field (FromField). It already names its cell, and binding the variables later doesn’t rekey it. This lets the engine plan an object’s work before the argument values exist. Also called symbolic arguments.
mutation keyMutationKeyA ground key that also carries the response key, so that two aliases of the same mutation field stay separate invocations.
@parent fieldParentKeyA field marked @parent on a type, which returns the object one level up: the object whose (single, argumentless) field produced this one. Creating the child’s orchestrator fills its cell with that existing parent object result instead of running a resolver, so following it creates no new object or task. An RSS can select through it to read the parent’s fields, which adds demand to that ancestor. Also called a parent key or parent backedge.
argumentsArguments (Ground: Resolved, Error; Template), Arguments.VariableA field’s argument values. Some may still come from a resolver variable whose value isn’t known yet. Once none do, the arguments are ground (fully known): either every value is resolved, or the whole set is an error because some variable’s value couldn’t be computed.

Demand and supply

NameIn codeWhat it is
demandDemand<SelectionForest>Every field the engine must build at one object result: its value, its access decision or both. Client selections, resolver inputs and checker inputs all introduce demand. It has two parts: checked demand, whose values are read through access checks, and unchecked demand, whose values are read raw.
checked demandDemand.checkedDemand whose values are read through access checks: the client’s selections and the inputs of value resolvers. Checkers’ own inputs are unchecked demand instead.
unchecked demandDemand.uncheckedDemand whose values are read raw, without access checks: the inputs of checkers. If a checker’s input has its own resolver, that resolver’s inputs are still read with checks. Also called raw demand.
expansion—One application of a dependency rule: adding the direct requirements, such as an RSS, of work already demanded. New requirements may need expanding in turn.
closurecloseSelectedConstructionDemand (closePrecomputedConstructionDemand, closeOrchestrationConstructionDemand)Works out the full list of fields an object result must build, before any of them run. It starts from the fields requested on that object and, for each one whose resolver or access checker will run, adds the fields it needs to read as input; some of those inputs belong to the Query result or an ancestor object rather than this one. Those additions can need inputs of their own, so it repeats until nothing new is added; it only finds work and computes no values. Also called demand closure.
construction demandClosedConstructionDemandContext (objectRooted, queryRooted), OrchestrationConstructionDemandEverything an object result must contain: the fields requested on it, plus the inputs that the resolvers and checkers that will run there need to read. Closure, the engine’s planning pass, works it out. It is kept in two parts, one read from the object and one read from Query, and each part is split into checked and unchecked demand.
input demandresolverInputDemand, checkerInputDemandWhat a resolver or checker reads to run: its RSS, instantiated at this occurrence.
successor demandsuccessorDemandFromConstructionDemandWhat a resolver is asked to return: the fields requested below its field, plus the inputs that resolvers and checkers beneath it will read, plus fields that work below reads through @parent fields (a public Viaduct directive), which lead back up to this resolver’s object or its ancestors. In Runtime2, the resolver doesn’t return those paths or any field with arguments: the engine fills @parent fields itself, and a field with arguments always runs its own resolver. Other fields it leaves out also fall to their own resolvers. Also called producer-facing demand.
guarded demandSelectionForest.guardedByDemand whose selections carry an added inclusion condition, so whether it applies is decided at run time.
parent demandliftParentConstructionDemand, installParentBackedgeFieldsDemand created when a descendant selects through a @parent field (one that returns the object one level up). It is lifted into that ancestor’s construction demand, the list of everything the ancestor must build, with its conditions and access requirements. Also called lifted ancestor demand.
liftliftParentConstructionDemandMoving parent demand up the tree: closure lifts it into an existing ancestor’s construction demand, and successor demand lifts it onto the resolver that produces that ancestor. The lifted demand keeps its conditions and access requirements.
passive fieldrequiresStandardResolution = false, PassiveValueOccurrenceA field whose value comes from the output of the resolver that returned its object, not from its own resolver. In Runtime2, this is a demanded argumentless field present in that output, directly or nested, even if the field has a registered resolver. Its own resolver doesn’t run there; the parent’s resolver task copies the value in. “Passive” says how a value is produced, not whether the client selected it or whether it is checked. Also called a passive value or passive output.
active fieldrequiresStandardResolution = trueA demanded field with a registered resolver whose value the parent resolver’s output lacks, so its own resolver must run at that occurrence; a field that takes arguments can never be passive. It gets a claimed cell and its own resolver task, whereas an unregistered field missing from the output is an error. “Active” says where the value comes from; activation is the separate include-or-skip decision for one occurrence. Its value is also called an active value.
passive descentresolvePassiveValues, resolvePassiveObjectValues, materializePassiveFieldsThe part of a resolver task that turns the value its resolver returned into object results, without calling any resolver. For each returned object it creates the object result and its orchestrator, copies the passive fields’ values into their cells, and then dispatches the orchestrator. It handles nested objects and lists inside the returned value the same way, all synchronously.

Results and cells

NameIn codeWhat it is
object engine result (OER)ObjectEngineResult (OER), ListEngineResult, EngineResultCellOne object in the response as the engine builds it: a map from field keys to cells, slots that each hold one field’s value once it is produced. It is not a resolver’s returned value or the final response map. Also called an object result.
result treeObjectEngineResult, ListEngineResultThe tree of object results and list results for one request, rooted at the operation’s root object engine result, or OER (the Query OER for a query): the response under construction. Completion reads it while values are still arriving. It is not the final response map. Also called the OER tree.
associated Query object resultqueryOER (SharedOERContext)A fresh Query object result that each orchestrator creates beside its own object, where the Query RSS inputs of that object’s resolvers and checkers are built. It is not the operation’s root Query result, and each object occurrence gets its own. No resolver output contains it, so every field demanded on it is active and runs its own resolver. Also called the associated Query scope.
occurrenceOEROccurrence, ResolverOccurrenceIdOne position in the result tree: an object result together with its root, the result its path starts from, and that path. A resolver occurrence ID names one resolver application the same way, so each position gets its own cells, tasks and resolver call. It is not the schema type. Also called an object occurrence.
ownerResolverOccurrenceId, VariableInstanceIdThe resolver or checker occurrence that declares an RSS or a variable. Each variable is instantiated for its owner’s occurrence, so equal names or values from different owners stay distinct.
cellEngineResultCellOne field or list-element slot with three write-once parts: an activation (include-or-skip) decision, a value promise and a promise for the field checker’s result. Also called a field cell.
list resultListEngineResultA list of cells, one per element, in which each object-typed element gets its own object result.
engine resultEngineResult, ErrorEngineResultThe union of what a cell’s value can hold: simple values, object results, list results and error values. ErrorEngineResult is the error value that a failed resolver or a denied check becomes.
activationEngineResultCell.setActivated, fetchActivatedWhether one field of one object is included or skipped, decided once from its @skip/@include condition. For a field whose own resolver runs, the field’s resolver task decides it and skips the resolver call if the field isn’t included; a value copied from the parent’s output is marked included when it is written, and completion still leaves a client-skipped field out of the response. A copied list of root-field references, such as node references, under a condition is different: a task holds it until activation is decided, so its references are resolved only if it is included, and a Never list isn’t copied at all. The field’s value and check result can’t be read or written until it is decided. It is unrelated to an active field, which is one whose value must come from its own resolver.
promisePromise, ReservablePromiseA write-once value that readers can await before it is completed. A cell’s value is a reservable promise, whose single writer can claim it after readers have started waiting.
reserveObjectEngineResult.reserveCellGet a field’s cell, its slot in an object result, first creating an empty one if it is absent, so readers can wait before anything writes it. When the engine plans an object, it reserves a cell for each field that will be read through access checks, and later gives each resolver’s cell to the task that runs that resolver. Once the object is frozen, reserving only finds existing cells, and a missing one is an error.
claimReservablePromise.claimAssign a reserved value promise to exactly one writer. An orchestrator claims each resolver task’s cell for that task.
register as writerCycleCheckState.registerWriterRecord with the cycle checker which task writes a slot, so that later reads of that slot can be checked for cycles. The slot is a cell’s value or field-check slot, or an object result’s type-check slot.
completePromise.complete, ReservablePromise.set; FieldResolutionLogic.publishResultWrite a promise’s value, once, which resumes any readers waiting on it. A resolver task completes its cell with the field’s final value, and a passive field’s cell is claimed and completed in one step (set). An object in a completed cell is readable while some of its own fields are still pending. Completing a cell is not GraphQL completion, the separate step that reads the cells to build the response.
freezeObjectEngineResult.freeze, ReservablePromise.freezeClose an object result to new fields, so no more cells can be added to it. Cells reserved but never given a writer then fail (“Missing engine-result cell”), while cells that have a writer may still complete. An orchestrator freezes its object right after dispatching its tasks.
EngineObjectDataEngineObjectDataThe engine API’s object-data carrier. A resolver returns its object output as an OED, and its RSS inputs are handed to it as synchronous OED views. Unlike an object result, an OED has no pending cells. Also called OED.

Tasks and execution

NameIn codeWhat it is
resolutionstartResolution (Runtime2); FieldResolver (today)Obtaining field values into the result tree. Runtime2 runs its own algorithm for it; completion builds the GraphQL response from the result tree.
completionQPlanWiringFactory (Runtime2); FieldCompleter (today)The step that builds the GraphQL response, reading each field’s value as it arrives. It calls no tenant resolvers. It is a separate step from resolution, which obtains the field values, though for a query the two interleave: completion reads each value as resolution publishes it. Fields that are built only because a resolver or checker reads them never appear in the response. Also called GraphQL response completion.
execution strategyQPlanExecutionStrategyRuntime2’s entry point for each request. It decodes the validated operation into selections, starts resolution and hands completion the live root object result to read from.
orchestratorOrchestrationTaskThe one-shot task that plans one object in the response. It works out every field the object needs, starts a task to call the resolver of each field whose own resolver must run, then freezes the object’s field list. Its creator, usually the parent field’s resolver task, then copies the values already in the parent resolver’s output into the object and dispatches it. It never waits for a value. Also called object orchestration.
resolver taskFieldResolverTask, FieldResolutionLogic.publishResultThe task that produces one field’s (or list element’s) value and completes its cell. It decides whether the field is included, waits for the resolver’s arguments and inputs, calls the field’s resolver, if it has one, once, and turns the returned value into object results for the fields below. Also called a field task.
checker taskFieldCheckerTask, TypeCheckerTaskThe task that runs one checker beside the resolver tasks. A field checker task completes the field-check slot of a cell; a type checker task completes the type-check slot of an object result.
mutation orchestratorMutationOrchestrationTaskThe orchestrator for a mutation root, run as one coroutine. It claims every mutation field up front, then runs them in source order, waiting for each field’s resolver task and its whole payload before starting the next.
dispatchCoroutineTaskDispatcher (dispatchOrchestration, dispatchFieldResolver, dispatchFieldChecker, dispatchTypeChecker)Handing a prepared task to the engine’s dispatcher. Runtime2’s main engine launches a resolver or checker task as a coroutine in the request scope, while other dispatchers may run it inline or queue it. An ordinary orchestrator never suspends, so it has claimed its cells and launched its tasks before dispatch returns. Also called launch.
operation contextOperationContextOne execution scope of a request: dispatcher, variable bindings, binding-declaration state, cycle checker and observers. There is one per request, plus a child for each nested ctx.query or ctx.mutation call, which gets its own dispatcher and shares the rest.
worldAssumptionsThe fixed per-schema configuration that resolution runs under: the schema, the resolver registry, which field produces the parent that each @parent field returns, the selective policy and which closure variant to use. Requests read it but never change it. In code this is the Assumptions class.

Access checks

NameIn codeWhat it is
field checkerFieldCheckerResolverA registered access check on one object field. It receives the field’s arguments and its own raw inputs, and returns a checker result. It applies to passive fields too.
type checkerTypeCheckerResolverA registered access check on one concrete object type, with no field arguments. It runs for an object result of that type when the object is read through access checks, as client selections and resolver inputs are; an object that only checkers read is not type-checked.
checker resultCheckerResult, combineWhat a checker returns: success or an error. A checked read combines the type result with the field result. If the result is an error, completion gets an error value (ErrorEngineResult) instead of the field’s value.
field-check slotEngineResultCell.fieldCheckerResultA cell’s write-once promise for its field checker’s result; null means no checker applies. The field checker task completes it, or, with no checker, the resolver task when it activates the cell, or, for a passive field with no checker, the orchestrator when it runs.
type-check slotObjectEngineResult.typeCheckerResultAn object result’s write-once promise for its type checker’s result; null means no type check is needed for this object, because the object’s type has no checker or nothing reads the object through access checks. It starts pending when a type check may be needed, and then either the type checker task completes it or the orchestrator sets it to null once it finds none is needed. Otherwise it starts as null.
checked readmaterializeCheckedValue, awaitCheckedValueA read that awaits the field-check slot, then the value, then (for an object) its type-check slot, and returns an error value if the combined result denies. A field denial can return before the value is ready. Client data and resolver inputs are read this way. Also called a checked incoming read.
raw readmaterializeResolverInput(checked = false)A read that takes values without applying checks. Checkers read their inputs raw.
materializationmaterializeResolverInput, materializeResultBuilding a consumer’s input object from cells by response key. It reserves cells for resolver inputs, awaits each one with a checked or raw read and records every read with the cycle checker.

Variables and bindings

NameIn codeWhat it is
variableArguments.Variable, VariableDefinition (FromArgument, FromField, FromProvider); engine API FromObjectFieldVariable, FromQueryFieldVariable; tenant API @Variable(fromArgument | fromObjectField | fromQueryField)A variable that a resolver or checker defines and uses in its RSS. Its value comes from one source: an argument of the field (FromArgument), a path in the resolver’s object or Query RSS (FromField; tenant code writes fromObjectField or fromQueryField), or a variables provider (FromProvider). Unlike an operation variable, which the client declares and sends, it is declared by tenant code, bound during execution, and gets its own instance for each resolver occurrence. Also called a resolver variable.
variables providerVariablesProviderA tenant callback that computes variables for a resolver or a field checker. The resolver task calls a resolver’s provider once per resolver occurrence, after the field is included and before the resolver runs, and its values are shared by the object and Query RSS inputs. The checker task likewise calls a field checker’s own provider.
bindingVariableBindingsStateThe value of one variable instance, that is, one resolver occurrence’s copy of a variable. A request keeps all its bindings in one store; each is written once and never removed, and readers can await a pending one.
declaring bindingsOrchestrationTask.declareBindings, BindingDeclarationsState.markBindingsDeclaredThe step of creating an orchestrator that registers every variable instance its resolvers and checkers need. A variable read from a field’s arguments is bound at once when those arguments are already known; the rest stay pending. Then the object’s bindings are marked declared, which readers wait for.
resolver targetResolverTargetThe slot that owns one resolver and its variables, which is a field’s value resolver, a field checker or a type checker.

Special mechanisms

NameIn codeWhat it is
root-field referenceRootFieldReferenceData, createRootFieldReferenceA value a resolver can return in place of a field’s value: an instruction to resolve one field reachable from Query, given by a path from Query, whose fields before the last are single and argumentless, and fully resolved arguments for the last one. Its fields can’t be read until the engine runs that field’s resolver. It works for object fields and list elements.
node referencenodeRootFieldReferenceOf, createNodeReferenceA value a resolver can return in place of an object, carrying only that object’s type and ID. The engine later loads the object by resolving Query.node with that ID; until then, tenant code holding the reference can read only its id.
tail loop (hops)while (fieldValue is RootFieldReferenceData) in publishResultThe loop inside a resolver task that follows a returned node reference, or another kind of root-field reference. Each pass, called a hop, invokes the reference’s target resolver, and the loop repeats while that resolver returns another reference. The final value completes the original cell.
invocation rootObjectEngineResult.of(Query) in prepareRootFieldReferenceInvocationA fresh, empty Query object result created for each hop of the tail loop, which gives that resolver call its identity and is never shared.
cycle checkerCycleCheckState, ResolverReadCycleExceptionPer-request state that records which task writes each slot (a cell’s value or field-check result, or an object result’s type-check result) and every read of a slot by a task. A read that would close a cycle of tasks waiting on each other fails with ResolverReadCycleException.
payloadawaitMutationPayloadCompletionA mutation field’s value together with every check and cell beneath it, not counting @parent fields, which point back up to an ancestor. The mutation orchestrator waits for all of it to complete before running the next mutation field.
Runtime2’s main engineResolution (src/main)The engine Runtime2 runs requests with, as opposed to its reference resolvers.
reference resolver familiesresolvers/resolver06 … resolver23 (src/testFixtures)Alternative whole resolution engines that model the semantics of Runtime2’s resolution. They are kept in the repository’s unpublished testFixtures source set, which the published library must not contain, and are used to build and test features. They never serve requests and are not tenant resolvers. There are six, in two families: explicit depth-first tasks and structured coroutines.
