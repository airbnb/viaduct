Deep dive · Motivation

Three consequences

Demand is not the client’s selection

Resolvers and checkers add inputs the client never wrote, and those inputs add more. The engine must reach a fixed point, called closure, before it knows what an object must contain. Hidden inputs still never appear in the response.

A value and its check are separate

A value can be ready while its access decision is still pending, and the reverse. Checked and raw readers of the same value need different things.

No fixed traversal order

Dependencies cross fields, objects, separate Query results and ancestors. So Runtime2 plans each object before it runs anything there, and every task waits on the exact values it reads.

Viaduct turns “fetch what the client selected” into “find and schedule everything that selection depends on, then show the client only what it asked for”.

Runtime2 implements the same Engine interface as today’s engine: its Engine2 and today’s EngineImpl both implement viaduct.engine.api.Engine. Runtime2 is designed so that its behavior can be reasoned about precisely. Its central habit is to plan before it runs.
