Deep dive

Motivation

Runtime2 is a new implementation of Viaduct’s engine, in core/engine/runtime2. It is still in alpha, and today’s engine remains the default. This deep dive explains why Viaduct needs an engine of its own on top of GraphQL Java, and what Runtime2 changes in that engine.

What Viaduct adds to a GraphQL Java engine

GraphQL Java can already run a GraphQL service on its own. It parses and validates the request, walks the client’s selections from the top, and calls each selected field’s data fetcher. Each data fetcher gets its arguments and a source: its parent’s value, the spec’s objectValue. GraphQL Java then completes the result: it coerces scalars and applies GraphQL’s null and error rules.

The hidden contract: a data fetcher’s source

Take displayName, which joins a user’s firstName and lastName. In a traditional GraphQL engine such as GraphQL Java, its data fetcher assumes that its source is something specific, for example the User data service’s response. It plucks firstName and lastName out of that object. The firstName and lastName fields themselves are probably served by the default property data fetcher, reading the same response object.

// GraphQL Java: displayName's data fetcher (sketch)
val displayName = DataFetcher { env ->
  // assumes a User service response
  val user = env.getSource<UserResponse>()
  "${user.firstName} ${user.lastName}"
}
// Viaduct: displayName's resolver (sketch)
@Resolver(objectValueFragment = "firstName lastName")
class DisplayName : UserResolvers.DisplayName() {
  override suspend fun resolve(ctx: Context): String? {
    val user = ctx.getObjectValue()
    return "${user.getFirstName()} ${user.getLastName()}"
  }
}

So traditional engines rely on the source far more than they advertise. A well-structured application needs a carefully structured source, and however careful the structure, it leads to a web of data dependencies: displayName depends on a specific version of the User service’s response. That web limits how many teams can contribute to one graph.

This isn’t a flaw in GraphQL Java. The GraphQL spec is intentionally unopinionated about how execution interacts with the sources of its inputs, and most GraphQL servers, GraphQL Java included, carry that over as a source parameter with very few constraints. That makes sense in the spec, and in a server that wants to give application developers maximum flexibility. It lacks modularity, though, so it can’t scale to multi-tenancy: many teams contributing to one well-connected schema.
