What each feature asks

Viaduct’s features, and what each one asks of the engine

The table lists Viaduct’s execution features roughly in order of how much complexity each adds to the engine. Every row describes a feature of public Viaduct, with two exceptions. In the first row, only Runtime2 lets any ancestor’s passive value replace a field’s resolver; today’s engine does so only below a parent-managed value. And @skip/@include conditions that use variables derived from fields are not accepted by either engine yet; their row is marked. Three that may look new are already public: ordered mutations, including fields on @namespaceType types reached from the mutation root (types whose fields group related operations); root-field references made with ctx.ref(); and @parent fields, which return the object one level up.

The Earliest support column names the first of Runtime2’s six reference resolvers that handles the feature. Despite the name, they are complete alternative engines, unrelated to the root-field and node references in the table, kept beside Runtime2 resolution for comparison. They come in two families. They live in the repository’s core/engine/runtime2/src/testFixtures source set, which is not published. 06–08 run explicit depth-first tasks, ordered so that each consumer runs after the producers it reads. That is simple but limits the features they can support. The numbers aren’t contiguous: each names a source file, not a version in a sequence. 21–23 are structured coroutines that wait on promise completion, but they don’t support variables derived from fields. Runtime2 resolution is Runtime2’s main resolution algorithm, the full-featured, non-test one that Engine2, Runtime2’s implementation of Viaduct’s Engine interface, runs to serve requests. This page uses that one name for it.

Why checkers break depth-first order: checkers without input fragments would fit depth-first order. Checkers with their own RSS don’t, because their required selections add dependencies that can cross objects and the associated Query, through raw reads, checked resolver inputs and access decisions that become ready on their own schedule. Those dependencies need not fit a depth-first engine’s fixed order. The depth-first resolvers 06–08 are value-only and accept no checkers, so checks of any kind start with the coroutine family. That is why resolver 21 introduces the checker machinery and resolver 22 exercises the harder dependency problem.
