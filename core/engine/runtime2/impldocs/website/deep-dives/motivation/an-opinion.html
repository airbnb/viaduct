Deep dive · Motivation

Taking an opinion

How Viaduct took an opinion

  1. Viaduct’s fragment APIFragments. Instead of depending directly on the backend responses of other teams, resolvers express their data needs more abstractly, as fragments on the schema. The approach came straight from Viaduct’s emphasis on multi-tenant development, which would break down if every contributing team depended on other teams’ responses.
  2. Today’s engineObject results and their tree. Giving the spec’s objectValue a concrete form produced object engine results (OERs, ObjectEngineResults) and the OER tree. Today’s engine builds the OER tree separately from the GraphQL response: it separates field resolution from field completion.
  3. Runtime2Doubling down. At this altitude Runtime2 adds nothing architecturally; it doubles down on the resolution/completion split. For resolution, it moves away from GraphQL Java altogether, to a bespoke execution algorithm. For completion, it moves towards GraphQL Java’s own execution algorithm. The concrete change is in resolution: today’s engine starts a field’s required selections only when that field starts fetching, while Runtime2 works out an object’s whole demand before anything there runs.
In today’s engine Today’s engine completes the response with its own FieldCompleter, which reads the OER tree and applies the spec’s value-completion rules: it coerces scalars and enums, enforces non-null types and keeps partial results when errors occur. Runtime2 hands completion to GraphQL Java’s components instead: resolution builds an abstract, schema-shaped objectValue meant to slot directly into the spec’s execution algorithm, and GraphQL Java implements that algorithm very directly.

Isn’t that just the source problem one level down? No. Where the spec stays unopinionated, Viaduct’s field resolution is opinionated on purpose. The OER is a shared representation that is both the input and the output of resolvers, and resolvers can ask for data only in prescribed ways, as fragments: their required selection sets (RSS). That is the modularity the spec leaves out.

In short
  • The GraphQL spec is intentionally unopinionated about how execution gets its inputs, and GraphQL Java carries that over as a source parameter with very few constraints.
  • That suits a single application team, but it lacks modularity, so it can’t scale to many teams contributing to one well-connected schema.
  • Through fragments first and OER trees later, Viaduct takes a strong opinion about the data going into and coming out of resolvers. That is the basis for composing resolvers modularly.
  • OER trees are not GraphQL responses, so the approach also needs resolution separated from completion.
  • Runtime2 is an implementation improvement in that direction: it uses GraphQL Java where it adds the most value, turning OER trees into GraphQL responses. That leaves its own resolution free to handle the hardest rows of the features table on the next page, such as variables read from resolved fields and nested ctx.query() calls, while GraphQL Java’s components complete the response. For now, Engine2, Runtime2’s implementation of Viaduct’s Engine interface, returns one complete result even for a query with @defer.

What changes for the engine

Because resolvers don’t call each other or read other teams’ sources, the engine works out everything they need from their declared inputs: which other resolvers and access checks those inputs reach, which values a parent’s output already contains, and in what order the work can safely run. Running a Viaduct request is therefore less like walking a query and more like discovering and scheduling a dependency graph.

The right column describes Viaduct running on Runtime2. Today’s engine differs in three rows: What runs, Where a value comes from, and Order. It starts a field’s required selections when that field starts fetching, not before anything runs, so its order still follows the client’s selections from the top. And a selected field’s resolver always runs, even when its parent’s output already holds the value. The one exception is a parent-managed value, an engine API wrapper (ParentManagedValue) that a resolver returns to supply its whole subtree. It skips the registered resolvers below it, until a StandardResolutionValue, the inverse wrapper, further down turns them back on.

An object’s associated Query result is a fresh, empty Query result that its orchestrator creates beside the object, where the Query-fragment inputs of that object’s resolvers and checkers are built. It is not the operation’s primary Query result, and no resolver code starts it, unlike a ctx.query() root. The object’s resolvers and checkers share it, so an equal Query field runs once per object, not once per request. Each task waits on exactly the values it reads.
