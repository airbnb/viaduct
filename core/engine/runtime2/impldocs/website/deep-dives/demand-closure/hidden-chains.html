Hidden dependency chains

Reading the step diagramsIn each step diagram, every object engine result (OER) except an associated Query gets an orchestrator. Creating the orchestrator closes the object’s demand, working out every field the object needs, and the orchestrator then launches a task for each field that needs its own resolver and for each checker. In between, the resolver task that returned the object copies in the passive values its resolver already returned. A resolver task reads its inputs and calls one resolver. Reading the step diagrams explains the labels.

1. One field hides a dependency chain

This schema is also used in Example 2.

Annotated schemaSDL + contracts
type Query {
  user: User
    @resolver(result: {first: 2, last: 3})
  project: Project
    @resolver(result: {owner: {first: 2, last: 3}})
}

type Project {
  owner: User
}

type User {
  first: Int
  last: Int
  display: Int
    @resolver(
      objectValueFragment: "first last"
      result: "sum(first, last)"
    )
  greeting: Int
    @resolver(
      objectValueFragment: "display"
      result: "sumplus1(display)"
    )
}
Client operationGraphQL
{
  user {
    greeting
  }
}

Step by step

Read the RSS directly on User.display and User.greeting; Query.user and Query.project have empty RSS. The client asks for user { greeting }. The producer of user returns passive values first = 2 and last = 3. For User.display, these are passive inputs: their values come from Query.user without separate first or last resolver calls. For User.greeting, display is an active input produced by User.display’s resolver.

Why one expansion fails: discovering display does not provide the data needed to compute it. Transitive requirements matter even for a scalar response with no fragments, conditions, or access checks.

Reading the outcomes. The trees in each example name the layer they show: local checked or unchecked construction demand, parent demand, active successor-demand paths, or completed occurrence fields. Path sets omit argument and owner identity, so the example tests asserted those separately. Excluded selection metadata may remain in a selection forest even when its active path set is empty.

Worked source example: Demand closure. Direct closure assertions: ConstructionDemandClosureTest.

2. The same dependency chain through a passive nested object

Annotated schemaSDL + contracts
type Query {
  user: User
    @resolver(result: {first: 2, last: 3})
  project: Project
    @resolver(result: {owner: {first: 2, last: 3}})
}

type Project {
  owner: User
}

type User {
  first: Int
  last: Int
  display: Int
    @resolver(
      objectValueFragment: "first last"
      result: "sum(first, last)"
    )
  greeting: Int
    @resolver(
      objectValueFragment: "display"
      result: "sumplus1(display)"
    )
}
Client operationGraphQL
{
  project {
    owner {
      greeting
    }
  }
}

Step by step

Query.project has an empty RSS. It returns a Project containing an owner: User with first = 2 and last = 3. The two User resolver contracts are unchanged.

This extends Example 1 with a passive nesting step: Project.owner has no separate value resolver. The dependency chain remains greeting → display → first + last. Query.project returns the two numeric inputs inside owner; the two User resolvers compute display and greeting.

Although the operation requests only owner.greeting, demand closure discovers that computing it requires owner.first and owner.last. The successor demand passed to Query.project therefore includes those fields. Query.project returns them inside owner, and output projection, which decides what a selective producer’s output must keep, must not discard them before User.display reads them. User.display and User.greeting compute their own fields. The client response selects only owner.greeting. Example 1 already needs these hidden inputs; Example 2 adds the traversal through the passive nested object.

Output projection example; SuccessorDemandRegressionTest checks shared resolver and checker input expansion.

3. Hidden requirements inherit conditions

Annotated schemaSDL + contracts
type Query {
  subject: Subject
    @resolver(result: {__typename: "Person", first: 7})
    # Organization run: result: {__typename: "Organization", legal: 7}
}

interface Subject {
  summary: Int
}

type Person implements Subject {
  first: Int
  summary: Int
    @resolver(
      objectValueFragment: "first"
      result: "sum(first)"
    )
}

type Organization implements Subject {
  legal: Int
  summary: Int
    @resolver(
      objectValueFragment: "legal"
      result: "sum(legal)"
    )
}
Client operationGraphQL
query Summary($a: Boolean!, $b: Boolean!) {
  subject {
    summary @include(if: $a)
    ... @include(if: $b) {
      summary
    }
  }
}

The annotated producer shows the Person case; the comment gives the Organization result used in the other runs. The recorded runs covered all four combinations of Boolean operation variables a and b, for each of the two concrete return types. The producer returns first = 7 for Person or legal = 7 for Organization.

Let subject return an interface Subject. Both Person and Organization implement its summary field. A Person’s summary requires first; an Organization’s summary requires legal. Neither concrete type has the other’s input field.

At the same subject object occurrence, either applicable field contribution can demand summary. Each contribution carries a guard, its inclusion condition: a for the first and b for the second. A guard on a client selection is already Always or Never once the operation is decoded. The hidden requirements are:

RequirementWhen needed
summarya OR b
firstPerson AND (a OR b)
legalOrganization AND (a OR b)

The concrete type may become known only when the producer returns. The dependency description must associate each requirement with its type conditions until its applicability is known. If both variables are false, neither contribution requests summary. If one is true, the other, excluded contribution does not cancel it.

Why flattening fails: an unconditional union loses both which concrete type owns each requirement and when it is applicable. Along one occurrence path, conditions combine with AND; alternative contributions to shared work combine with OR. Fragments can introduce those contributions several layers away from the selected field, as explained in the Field selection forests deep dive.

Concrete-type successor requirements; ParentConstructionDemandTest checks that guards still apply after subselections are merged for each concrete type. SingularQueryGuardIsolationTest covers two owners whose guarded alternatives share one input: if one owner fails or is still waiting, the shared input is still produced once, and the other owner completes without waiting.
