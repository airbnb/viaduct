Deep dive · Demand closure

Where inputs come from

Reading the step diagramsIn each step diagram, every object engine result (OER) except an associated Query gets an orchestrator. Creating the orchestrator closes the object’s demand, working out every field the object needs, and the orchestrator then launches a task for each field that needs its own resolver and for each checker. In between, the resolver task that returned the object copies in the passive values its resolver already returned. A resolver task reads its inputs and calls one resolver. Reading the step diagrams explains the labels.

4. Inputs can have two different roots

4a. A record checker reads from both roots

Annotated schemaSDL + contracts
type Query {
  viewerId: ID!
    @resolver(result: "viewer")
  records: [Record!]!
    @resolver(
      result: [{ownerId: "viewer", secret: "first"}, {ownerId: "other", secret: "second"}]
    )
}

type Record {
  ownerId: ID!
  secret: String
    @fieldChecker(
      inputs: [
        {
          name: "accessInputs"
          objectValueFragment: "ownerId"
          queryValueFragment: "viewerId"
        }
      ]
      decision: "allow when accessInputs.object.ownerId == accessInputs.query.viewerId"
    )
}
Client operationGraphQL
{
  records {
    secret
  }
}

Step by step

Query.viewerId returns "viewer". The records producer returns two records: { ownerId: "viewer", secret: "first" } and { ownerId: "other", secret: "second" }.

The client asks for records { secret }. A checker for each Record.secret requires that record’s ownerId and a Query-rooted viewerId. The computed demand above keeps these two projections separate. The checker grants access only when the two match, so the client receives "first" for the first record but not "second" for the second. The step diagram shows each raw value; the access decision is tracked separately.

The requirement cannot be represented as Record { ownerId viewerId }. Query-rooted fields have their own resolver contracts, which can introduce more Query demand.

In today’s engine Every queryValueFragment, for a resolver or a checker, is read from one shared Query result. In a query operation that is the operation’s own root result (root Query result · resolver Query inputs · checker Query inputs). Each field and argument key in that result is fetched at most once (memoized fetch), so both records would share one viewerId call. Runtime2 gives each object result its own associated Query OER instead, so it makes one viewerId call per Record, as steps 5 and 6 show.
Why the two calls are not sharedRuntime2’s design notes make the result occurrence the identity of work: a resolver occurrence is its root result plus its exact path. Equal schema coordinates, arguments or values in different roots do not merge two occurrences. Caching, batching and request deduplication belong to separate physical execution layers, which must not change that identity (result occurrence is identity). The notes accept the cost here. Sharing one associated Query among all the resolvers and checkers of one object avoids repeating work within that object, but it does not share work across distinct objects, such as these two Records (known cost). Sharing is left to that physical layer. The notes allow safe batching across scopes (batching allowed). They list physical batching and data-loader reuse as gaps in the present Engine API integration, not as settled semantics (integration gaps). For now, Runtime2 makes more calls here than today’s memoized fetch.

4b. The associated Query has transitive dependencies

This is a separate world with a new schema. One rule explains it. Each orchestrator creates exactly one associated Query OER for its object, and that associated Query gets no orchestrator of its own. A resolver that runs inside the associated Query reads both its object inputs and its Query inputs from that same associated Query, so closure adds them there instead of creating a nested one (one per orchestrator; same root, dynamic loop; same root, precomputed loop;design).

Annotated schemaSDL + contracts
type Query {
  field0: Int
    @resolver(
      queryValueFragment: "field1 field2"
      result: 0
    )
  field1: Int
    @resolver(
      queryValueFragment: "field2 field3"
      result: 1
    )
  field2: Int
    @resolver(
      queryValueFragment: "field3"
      result: 2
    )
  field3: Int
    @resolver(result: 3)
}
Client operationGraphQL
{
  field0
}

Step by step

The value resolver for each fieldN returns the integer N. Its Query-rooted RSS is attached to that field’s resolver in the schema above.

These are declared input fragments, distinct from a resolver starting another query with ctx.query(). In Runtime2’s model, the resolver and checker owners on one containing object share one associated Query OER, while each receives only its own declared input projection. The primary operation’s Query OER has its own identity, and so does the associated Query OER of each object occurrence. Equal field names and arguments alone do not make those scopes interchangeable.

The new obligation: close dependencies across both input roots, sharing eligible work within a scope while keeping owner-specific bindings distinct. A shared field3 value does not entitle every consumer to see every field in that shared result.

5. A dependency’s arguments come from resolved data

5a. Arguments distinguish sibling invocations

Annotated schemaSDL + contracts
type Query {
  boxes: [Box]
    @resolver(result: [{}, {}])
}

type Box {
  consumer(seed: Int!): Int
    @resolver(
      objectValueFragment: "sibling(value: $seed)"
      result: "sum(sibling)"
    )
  sibling(value: Int!): Int
    @resolver(result: "sum($value)")
}
Client operationGraphQL
{
  boxes {
    a: consumer(seed: 7)
    b: consumer(seed: 9)
  }
}

First consider a simple contract: consumer(seed: 7) requires sibling(value: $seed). The argument fixes the dependency’s value: sibling(value: 7). A call with seed 9 requires a different key. During closure the key is still symbolic. The diagrams write it sibling($seed→7): a key that uses this consumer’s own $seed, which the orchestrator binds to 7 right after closure, because the consumer’s own argument is already known.

Step by step

Query.boxes returns two empty Box objects. Each consumer returns the value of its required sibling; sibling(value: N) returns N. This creates two argument bindings at each of two list positions.

5b. From-field variables cross the object and Query roots

Annotated schemaSDL + contracts
type Query {
  payload: Payload!
    @resolver(result: {seed: 11})
  seed: Int!
    @resolver(result: 7)
  consume(local: Int!, query: Int!): Int!
    @resolver(result: "sum($local, $query)")
}

type Payload {
  first: Int!
    @resolver(
      objectValueFragment: "seed localConsume(value: $query)"
      queryValueFragment: "seed consume(local: $local, query: $query)"
      variables: [
        {name: "local", fromObjectField: "seed"}
        {name: "query", fromQueryField: "seed"}
      ]
      result: "value(query.consume)"
    )
  second: Int!
    @resolver(
      objectValueFragment: "seed localConsume(value: $query)"
      queryValueFragment: "seed consume(local: $local, query: $query)"
      variables: [
        {name: "local", fromObjectField: "seed"}
        {name: "query", fromQueryField: "seed"}
      ]
      result: "value(query.consume)"
    )
  seed: Int!
    # Passive: Query.payload returns seed = 11.
  localConsume(value: Int!): Int!
    @resolver(result: "sum($value)")
}
Client operationGraphQL
{
  payload {
    first
    second
  }
}

Step by step

Now consider a test fixture whose variables are from-field variables (VariableDefinition.FromField in Runtime2): each one reads its value from a source path in its resolver’s own object or Query RSS, not from a variables provider (definition). Here they cross roots. The client selects payload { first second }. Each field owns variables $local and $query:

FactMeaning for each consumer
$localRead Payload.seed = 11 from the containing object.
$queryRead Query.seed = 7 from the associated Query OER.
Object requirementsseed localConsume(value: $query)
Query requirementsseed consume(local: $local, query: $query)

The engine must demand the source paths before their values are available, bind each variable at its owning occurrence, and use the correct root for each read. The local call receives 7; the Query call receives 11 and 7 and returns 18. Both first and second therefore return 18.

Runtime2 keeps the owners’ symbolic variable instances distinct even when their eventual values agree. This fixture asserts one Query seed invocation but two consume invocations and two localConsume invocations. Calls are shared only when their keys are equal. A key with no variables, like Query.seed, is the same for both consumers in the Payload’s one associated Query OER, so one call serves both. A key whose arguments use variables names each variable instance, and each instance belongs to the resolver occurrence that declared it (variable instance identity). So first and second get different consume and localConsume keys. Two aliases with equal ground arguments share a cell only when their arguments are already values; these arguments are variable instances, so the keys stay distinct even after both bind to the same numbers. Across lists, position and logical root distinguish otherwise equal-looking occurrences too.

Why equal values do not mergeThe design notes name three ways to handle an argument whose value is not yet known (ungrounded keys). The engine can wait until every key that might merge has its value, but that needs cycle rules strong enough to rule out deadlock. It can widen a resolver’s successor demand in case later keys join it, but then demand depends on timing, which the notes call “not an acceptable developer contract.” Or it can merge keys by their symbolic arguments and variable instances before any value is known. Runtime2 takes the third path and accepts its cost: distinct symbolic keys may later bind to equal arguments and call the same resolver more than once, as consume and localConsume do here. The notes treat symbolic identity as the meaning of a key, not as an approximation of its final values, and record no plan to merge keys after binding. Caching and deduplication would belong to a separate physical layer (physical layer).

5c. A source path can be excluded even when its value exists

Annotated schemaSDL + contracts
type Query {
  item: Item!
    @resolver(result: {token: 8, protected: 1})
  echo(value: Int): Int
    @resolver(result: "value($value)")
}

type Item {
  token: Int!
  protected: Int!
    @fieldChecker(
      inputs: [
        {
          name: "local"
          objectValueFragment: "excluded: token @include(if: $enabled) included: token"
          queryValueFragment: "excluded: echo(value: $excluded) included: echo(value: $included)"
          variables: [
            {name: "excluded", fromObjectField: "excluded"}
            {name: "included", fromObjectField: "included"}
          ]
          providerVars: {enabled: false}
        }
        {name: "physical", objectValueFragment: "token"}
      ]
      decision: "assert the consumer-specific projections; allow"
    )
    # Repeat with providerVars: {enabled: true} in the second context.
}
Client operationGraphQL
{
  item {
    protected
  }
}

Query.item returns { token: 8, protected: 1 }; Query.echo returns its argument, including null. The checker for Item.protected owns the following raw input pair:

fragment LocalInput on Item {
  excluded: token @include(if: $enabled)
  included: token
}

fragment QueryInput on Query {
  excluded: echo(value: $excluded)
  included: echo(value: $included)
}

$enabled comes from the checker’s variables provider; $excluded and $included read the correspondingly named response paths in LocalInput. These are checker-owned bindings, separate from operation variables. A second named checker input reads raw token unconditionally, and the checker returns success. The schema shows providerVars with enabled false; a second test run sets it to true. The test runs the same client operation both ways. The source path excluded: token @include(if: $enabled) is allowed because $enabled comes from a variables provider, not from a field: registry checks reject a from-field variable whose path or inclusion condition depends on itself, directly or through other from-field variables, and a provider variable adds no such dependency (cycle check). With enabled=true, Query.echo(value: 8) runs twice because $excluded and $included are different variable instances, and symbolic keys merge only when their variable instances are equal (symbolic keys).

The alias adds one more distinction. Here one named input selects both excluded: token @include(if: $enabled) and included: token, while another selects token. When disabled, the excluded response path is absent even though the raw token cell exists for the other inputs. A variable read from that absent path binds null, so echo still runs, with null. The excluded source path stays absent even when another alias provides the same underlying value.

Why a static graph of grounded field names fails: dependency identity includes runtime value flow and the owner of each binding. Sharing work does not erase consumer-specific aliases, exclusions, or error outcomes.
