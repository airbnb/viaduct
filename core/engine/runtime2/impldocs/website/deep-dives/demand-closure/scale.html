Deep dive · Demand closure

Scale and difficulty

Reading the step diagramsIn each step diagram, every object engine result (OER) except an associated Query gets an orchestrator. Creating the orchestrator closes the object’s demand, working out every field the object needs, and the orchestrator then launches a task for each field that needs its own resolver and for each checker. In between, the resolver task that returned the object copies in the passive values its resolver already returned. A resolver task reads its inputs and calls one resolver. Reading the step diagrams explains the labels.

9. Many dependency paths can describe little distinct work

Start with the concrete depth-5 world. The tests also generate depths 10, 20, and 40 by adding fields through that depth. Every depth uses the same operation. The views below split demand into two access components: the checked part, read with access checks enforced, and the unchecked part, read raw by checkers.

Query.root returns { seed: { value: 7, other: 8 }, child: {} }. Child.parent is a backedge to that existing Parent. Every active Child field returns 1 after its inputs are ready. The depth-5 schema above shows every resolver and checker contract.

The graph has many paths to the same fields. At larger depths, each non-leaf field requires the next two fields that exist, and the last field reads the parent seed. Recursively copying each dependency path can grow much faster than the actual required work.

This fixture comes from SuperlinearGrowthTest, in Runtime2’s tests under core/engine/runtime2/src/test. It uses the Runtime2 test world’s default closure loop, which is the dynamic one unless a system property selects the precomputed one (two closure loops). For both checked and unchecked reads, the lifted parent demand holds one seed key, with just its two children, value and other. When the examples were run at depths 5, 10, 20, and 40, they recorded 7, 12, 22, and 42 value-resolver calls respectively: depth + 2, including the root producer, with every demanded field value correct. The test checks the same count at depth 20. The paths grow much faster. Following resolver inputs alone, field0 reaches the parent seed along F(n + 1) distinct paths at depth n, where F is the Fibonacci sequence (F(1) = F(2) = 1): 8, 89, 10,946, and 165,580,141 paths at those four depths.

Each non-leaf resolver owns separate bindings for $a and $b, both bound to true by its annotated providerVars. Query.audit has no resolver of its own in the test. The Runtime2 test world gives every Query field that lacks one a fallback resolver with an empty required selection set (RSS), which returns null for a nullable field such as audit (fallback resolvers). Its call is included in the resolver counts. The client operation has no variables. At larger depths the chain continues to fieldDepth, and the checker is attached to that final field.

Guards create a second source of growth. Each non-leaf resolver’s Query RSS selects the next field twice, with separate a and b guards, as shown in the schemas above.

At depth n, the audit input’s condition is a product of n two-way choices, one a-or-b choice per guarded level. Distributing it into every possible conjunction creates up to 2^n terms, even though the factored expression is linear in depth. This second fixture runs at depths 3, 6, 9, and 12 with both alternative guards true. The test checks that the checker’s audit-input condition has at most 8 × (depth + 1) nodes. When the examples were run, the associated Query held exactly field1 through fieldDepth plus audit, and total resolver calls were 5, 8, 11, and 14. These are structural bounds for this fixture, not timings. Another regression test adds a @parent field that the request never uses, and checks that it does not make closure of a similar diamond grow exponentially.

The new obligation: combine overlapping dependencies without changing what they require or copying every dependency path. Sharing cannot collapse genuinely distinct object/list positions or owner-specific variable instances. Conversely, distinct paths are not automatically distinct work. A finite closed demand can still be very large when unfolding fragments or runtime fanout creates genuinely different occurrences; these tests do not prove a universal linear bound.

The current suite disables two additional complexity assertions. Their recorded reasons are that occurrence-owned arguments can still permit exponential symbolic-key multiplicity (as in Example 5b, each resolver occurrence owns its variables, so equal-valued arguments still make distinct keys, and in a diamond those keys can multiply with depth; disabled test), and cycle detection still performs a fresh reachability search for every dependency edge. Those skipped assertions leave real limits on the claims we can make about general growth; the passing compact-demand fixtures do not establish those stronger bounds.

What makes closure difficult in general?

The first example is ordinary reachability. The later ones change what a node or edge means. A useful description of a demand obligation needs the following context:

DimensionWhat it prevents us from confusing
Object occurrence and rootEqual-looking values at different list positions, independent Query scopes, and a parent backedge to an existing object.
Field and argumentsDifferent invocations of one schema coordinate.
Variable owner and source pathRuntime bindings with equal values but distinct symbolic identity, aliases, or exclusions.
Types and conditionsPossible demand and applicable demand (Example 3), and a failed or pending alternative (SingularQueryGuardIsolationTest).
Consumer and access provenanceA raw value read, a checked field read, and a checked incoming read of an object.
Input versus output needsConstructing a current resolver’s inputs versus returning passive values for descendants.

Completeness means following every applicable contract until no new obligation appears, including contracts introduced by access checks and parent demand. Correct sharing means combining equivalent work without losing each consumer’s projection. Correct exclusion means an excluded path stays absent and a failed read stays failed even if another consumer can use the same physical value.

These obligations explain why “collect all required field names” is insufficient. They do not prescribe tasks, coroutines, promises, caches, or a particular fixed-point algorithm. Runtime2 provides concrete evidence of the interactions; the problem remains whichever execution design is used to solve it.
