Checks and ancestors

Reading the step diagramsIn each step diagram, every object engine result (OER) except an associated Query gets an orchestrator. Creating the orchestrator closes the object’s demand, working out every field the object needs, and the orchestrator then launches a task for each field that needs its own resolver and for each checker. In between, the resolver task that returned the object copies in the passive values its resolver already returned. A resolver task reads its inputs and calls one resolver. Reading the step diagrams explains the labels.
Scope of this evidenceThe examples on this page come from Runtime2 resolution model tests. Runtime2’s execution layer, which connects Runtime2 resolution to Viaduct’s public Engine API, does not yet enforce field checkers on @parent backedges, or on the path to the value a root-field reference (made with ctx.ref()) points at. Examples 7 and 8 use @parent, so they do not show field checks across those backedges end to end. That exclusion names field checkers only. It doesn’t list type checks across @parent, such as Example 8’s, as unsupported, but neither the docs nor this page show that they are enforced end to end. No example here uses root-field references. See what the execution layer supports and rejects.

6. Needing a value is different from needing its checks

Annotated schemaSDL + contracts
type Query {
  record: Record
    @resolver(result: {protected: 7, dependency: 40})
}

type Record {
  protected: Int
    @fieldChecker(
      inputs: [{name: "input", objectValueFragment: "derived"}]
      decision: "allow when input.object.derived == 41; deny on a failed read"
    )
  derived: Int
    @resolver(
      objectValueFragment: "dependency"
      result: "sumplus1(dependency)"
    )
    @fieldChecker(decision: "fail the test if invoked")
  dependency: Int
    @fieldChecker(decision: "deny")
}
Client operationGraphQL
{
  record {
    protected
  }
}

Step by step

A client or an ordinary value resolver makes checked reads: it reads selected values with applicable access checks enforced. A checker makes raw reads of its required inputs, without enforcing their field or type check results. Resolving a check and enforcing its result are separate operations. Raw inputs prevent a policy decision from depending on its own enforcement.

The checker’s demand for derived activates its value resolver. With no independent checked demand for derived, its own checker need not run. But that resolver’s input dependency is an ordinary checked read. Its checker runs and the resolver cannot read the raw 40 through that input. The protected checker therefore cannot obtain a successful derived value of 41. It grants access only when derived is 41 (checker contract), so the client does not receive protected’s value of 7. The step diagram shows each raw value; the access decision is tracked separately.

Why a global “unchecked mode” fails: raw access belongs to a particular consumer edge. It does not propagate through arbitrary resolver calls. If another client or resolver also demands derived checked, its checker becomes required without removing the checker’s raw access to the same value.

In today’s engine Today’s engine also builds a checker’s inputs without access checks. Runtime2 keeps that rule and limits it to the checker’s own input edge: a resolver that a raw read activates still reads its own inputs checked.

Likewise, merely selecting checked fields inside an object does not establish a checked incoming read of that object. Its type-check obligation depends on how consumers reached that occurrence. Demand needs both field-level and object-level access provenance. Example 8 shows an object first reached raw that a later checked read makes checked.

Raw-read example and consumer rules; FieldCheckerClosureTest asserts checked resolver inputs after raw boundaries on both roots; SymbolicTypeCheckerTest checks incoming type-check provenance.

7. A descendant demands work on an existing ancestor

An ordinary nested result creates a new object occurrence. A Viaduct @parent field returns the object one level up, the one from which the current object was reached (@parent). It is a backedge to that existing occurrence, not a new one. Reading it can introduce demand on an object encountered earlier, even when the client never selected a parent field.

7a. New requirements propagate through two ancestors

Annotated schemaSDL + contracts
type Query {
  grand: Grand
    @resolver(result: {grandValue: 7})
}

type Grand {
  grandValue: Int
  parentNode: Parent
    @resolver(result: {})
}

type Parent {
  parent: Grand
    @parent
  bridge: Int
    @resolver(
      objectValueFragment: "parent { grandValue }"
      result: "value(parent.grandValue)"
    )
  child: Child
    @resolver(result: {})
}

type Child {
  parent: Parent
    @parent
  result: Int
    @resolver(
      objectValueFragment: "parent { bridge }"
      result: "value(parent.bridge)"
    )
}
Client operationGraphQL
{
  grand {
    parentNode {
      child {
        result
      }
    }
  }
}

How Grand learns about bridge before Parent exists. Closure looks ahead. When an orchestrator closes its object’s demand, it walks the selections planned below that object, not objects that already exist. For each planned field it also reads the object required selection set (RSS) of that field’s resolver and the inputs of its checkers. A parent selection found on the way down becomes a request for the object one level up. As the walk comes back up, the request lands on the object that owns the field producing that child, and becomes demand there. The lifted demand is walked again in the same way. So in Grand’s closure, Child.result’s read of parent { bridge } lands on the planned Parent, and Parent.bridge’s own read of parent { grandValue } then lands on Grand. Closure does this for each round of new demand, and lifted demand keeps the guards of the path it came from (lookahead · landing on the producer · each round). That describes the dynamic loop. The precomputed loop, which Engine2 (Runtime2’s entry point for real requests) uses by default, does the same lifting from prepared summaries. The registry finds the parent selections in each resolver’s and checker’s fixed inputs once, when it is built. At run time, closure lifts parent demand out of the demand it starts with, and adds the prepared parent demand of each input it activates (prepared summaries · starting demand · activated inputs).

Step by step

The example test registered Parent.parent and Child.parent as @parent fields: they reuse the existing Grand and Parent occurrences. The other object fields produce new occurrences. Query.grand returns grandValue = 7; bridge and result each return their declared input value.

One upward pass is insufficient: adding bridge discovers a new resolver whose contract goes upward again. Any conditions on the original path must survive that movement, and passive ancestor data must remain available for it.

7b. An ancestor re-enters the same child

Annotated schemaSDL + contracts
type Query {
  root: Root
    @resolver(result: {})
}

type Root {
  child: Child
    @resolver(result: {})
  ancestorValue: Int
    @resolver(
      objectValueFragment: "child { parent { child { marker } } }"
      result: "value(child.parent.child.marker)"
    )
}

type Child {
  parent: Root
    @parent
  grandchild: Grandchild
    @resolver(result: {})
  marker: Int
    @resolver(result: 42)
}

type Grandchild {
  parent: Child
    @parent
  greatGrandchild: GreatGrandchild
    @resolver(result: {})
}

type GreatGrandchild {
  parent: Grandchild
    @parent
  result: Int
    @resolver(
      objectValueFragment: "parent { parent { parent { ancestorValue } } }"
      result: "value(parent.parent.parent.ancestorValue)"
    )
}
Client operationGraphQL
{
  root {
    child {
      grandchild {
        greatGrandchild {
          result
        }
      }
    }
  }
}

Step by step

The registered backedges are Child.parent → Root, Grandchild.parent → Child, and GreatGrandchild.parent → Grandchild. Each reuses the original ancestor occurrence. Child.marker returns 42; ancestorValue and result return the values read through their required paths in the schema above.

The harder re-entry example requests a result three levels down. Its resolver reads an ancestor’s ancestorValue; that ancestor resolver then goes down to the same already-open child to read marker.

Why tree order fails: response nesting is not dependency order. The object graph contains a backedge, but that alone is not a circular computation. Here marker can resolve first and both consumers can finish. In contrast, if marker required ancestorValue too, there would be a real value-dependency cycle. Those cases must be distinguished at the relevant occurrences. Runtime2 does this at run time: its cycle checker records each read against the task that writes the cell, and rejects a read that would close a cycle.

Transitive parent lifting tests; complete re-entry world. @parent is a public Viaduct schema directive, not a GraphQL language feature.

8. A raw ancestor becomes checked and adds new demand

This small existing Runtime2 fixture combines passive output, raw checker inputs, an active descendant, a parent backedge, and a type checker. The test is named “checked parent demand checks a raw ancestor and expands its type inputs”. It captures a difficult interaction in a small world; larger worlds can repeat it across many fields and occurrences.

Annotated schemaSDL + contracts
type Query {
  raw: Int!
    @resolver(result: 1)
    @fieldChecker(
      inputs: [{name: "input", objectValueFragment: "wrapper { child { computed } }"}]
    )
  wrapper: Wrapper!
    @resolver(result: {token: 7, secret: 11, child: {}})
}

type Wrapper
  @typeChecker(inputs: [{name: "input", objectValueFragment: "secret"}])
{
  token: Int!
  secret: Int!
  child: Child!
}

type Child {
  parent: Wrapper!
    @parent
  computed: Int!
    @resolver(
      objectValueFragment: "parent { token }"
      result: 3
    )
}
Client operationGraphQL
{
  raw
}

Step by step

Child.parent is a @parent backedge to its existing Wrapper. Query.raw returns 1; Query.wrapper returns { token: 7, secret: 11, child: {} }.

OwnerContract
Field checker for Query.rawRaw input wrapper { child { computed } }; returns success.
Value resolver for Child.computedChecked input parent { token }; returns 3.
Type checker for WrapperRaw input secret; asserts it receives 11, then returns success.

The entire client operation is { raw }. Follow the logical additions; these steps explain causality, not an engine scheduling trace.

  1. Start with the checked raw field.

    Despite its name, Query.raw is a normal checked client selection. Its value and registered field-check result are required.

  2. The field checker adds an unchecked subtree.

    It needs wrapper.child.computed. Reaching Wrapper and Child through this checker input alone does not demand their type checks.

  3. The active computed field adds a checked input.

    Its value is required even though its consumer is a checker. Its own resolver contract introduces a normal checked read of parent { token }.

  4. The parent edge reaches the same Wrapper.

    The required token belongs to the ancestor already produced by Query.wrapper. This incoming checked read now also demands that Wrapper occurrence’s type check.

  5. The type checker adds another passive input.

    It needs raw secret from that Wrapper. Both token and secret must survive the wrapper producer’s output selection. No further contracts add demand.

A closure that stops after expanding the first checker misses the computed resolver’s input. One that propagates raw mode transitively misses Wrapper’s type check. One that treats parent as a fresh object loses ancestor identity. One that adds the type check without expanding its input misses secret. A producer that returns only the client-selected fields would omit these hidden inputs.

The executed successor demand also includes child.parent.secret: the checked parent read introduces the Wrapper type checker’s raw input along that path. This is another path to the same Wrapper’s secret. The recorded run showed that the parent points to the original Wrapper and that its local field set stayed exactly { child, token, secret }.

The test checks that the Wrapper type checker receives 11 and records exactly one type-checker application.

The fixture. These are Resolution model tests; see the scope note at the top of this page.
