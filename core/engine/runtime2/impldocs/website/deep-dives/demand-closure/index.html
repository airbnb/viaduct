What does “demand closure” mean?

Start with the applicable fields requested by the client. Add everything needed to produce those fields and make the required access decisions. Then apply the same rules to the additions. A demand is closed when applying those rules adds no further requirements: a fixed point.

Keep the applicable client demand.

02 / ExpandAdd required work

Follow each resolver and checker contract.

03 / RepeatReach a fixed point

Stop when no requirement is missing.

This is a logical definition, independent of how an engine represents or schedules the work. Required selections are Viaduct resolver and checker contracts; GraphQL alone does not specify these hidden dependencies.

In today’s engine Today’s engine also knows transitive inputs ahead of time: each resolver’s RSS is a child plan in the query plan, and launching a plan launches its child plans. But it launches a field’s plans only when that field starts fetching. Runtime2 closes an object’s whole demand when its orchestrator is created, before any work on that object runs.

Runtime2 has two separate loops that compute this fixed point, and a setting picks one (loop selector). The dynamic loop reads each resolver’s and checker’s input fragments as it discovers them. The precomputed loop reads input templates that the resolver registry prepares once for each resolver field (templates). Both still add work in rounds, one frontier of newly activated resolvers and checkers at a time, and both return the same kind of closed demand (design notes). Engine2, Runtime2’s implementation of Viaduct’s Engine interface and the entry point for real requests, uses the precomputed loop by default (Engine2 default). The Runtime2 test world, the configuration Runtime2’s own tests build, uses the dynamic loop unless a system property selects the other (test world default). Many closure tests run both loops, and some compare their results directly (example).

More than a set of field names.

A requirement belongs to a particular object occurrence, root, arguments, consumer, and condition. It can demand a value, an access decision, or both. Removing that context can change the meaning of the request.

Adapted from Andy Marek’s Viaduct guide. Its examples were run against the real Runtime2 resolution implementation. The claims on these pages were checked against the code the source links point to. The recorded results, such as call counts, step diagrams, and the “What execution confirms” tables, came from runs at an earlier revision. They weren’t re-run here.

Keep three questions separate: what is needed to construct a resolver’s inputs, what data its producer must return for downstream consumers, and what the client should finally see. Hidden input fields belong to the first two; adding them to demand does not add them to the GraphQL response. Closure also does not imply successful execution: required work may fail or form an invalid dependency cycle.

Reading the step diagrams

Most examples include a step-by-step diagram of one recorded run. Its left column shows one box per object engine result (OER), the engine’s working copy of one response object, and one row per field cell. Together the boxes form the OER tree. The other two columns show the orchestrators and resolver tasks that fill it.

Orchestrators, resolver tasks, and checker tasks

Orchestrator. Each object result gets one orchestrator. Creating the orchestrator closes the object’s demand: it lists every field the object needs, adds the inputs of each resolver and checker that will run there, and repeats until nothing new appears. Creation also makes a fresh associated Query OER for the inputs those resolvers and checkers read from Query; that Query OER shares the object’s orchestrator and gets none of its own. Passive values, fields the parent resolver already returned, are copied into their cells without calling a resolver; the resolver task that returned the object does this copying, between closure and launch. The orchestrator then launches a resolver task for each field that must run its own resolver and a checker task for each checker, which means it hands each task to the engine’s dispatcher. Finally it seals the object’s field list.

Resolver task. A resolver task produces one field’s value. It decides whether the field is included, waits for and reads its inputs, calls the field’s resolver once, and writes the value into the cell. When the value is an object, it creates a new object result with its own orchestrator. If the field is excluded, the task stops without calling the resolver.

Checker task. A checker task runs one checker beside the resolver tasks and records its access decision.

In the diagrams, an orchestrator’s close: line lists its closed demand, and its launch: line lists the fields that get resolver tasks. A cell marked + closure was added by closure rather than requested by the client; the mark gives way to the value once it arrives, and the step captions say what closure added. Teal boxes are OERs (dashed for an associated Query OER), solid purple boxes are orchestrators, and dashed purple boxes are resolver tasks. A solid purple arrow runs from an orchestrator to a resolver task it launches; a dashed teal arrow shows a resolver task writing its result into a cell. The red Checker tasks box at the last step lists all of the run’s checker tasks together; it does not show when each one ran. The steps follow one recorded run, not a required schedule. In the requirement trees, blue rows are fields the operation selected and orange rows are fields closure added, or paths to them.

Reading the annotated schemas

Show

RSS means required selection set: the inputs owned by one value resolver or checker. A directive belongs to the field or type on which it appears. For example, User.greeting @resolver(objectValueFragment: "display") means that the value resolver for User.greeting reads display from its containing User occurrence.

Notation for these tested worlds

The result and providerVars forms follow the Runtime2 test fixtures; @parent is a public Viaduct schema directive. These pages use the tenant API names objectValueFragment and queryValueFragment, alongside explicit variables, @fieldChecker, and @typeChecker, to display the registrations that each example’s Kotlin test made. These extended schemas document those fixtures; Runtime2’s resolver test domain-specific language (DSL) does not execute the added annotations. The Kotlin tests, not these schemas, were the executable source.

How this maps to tenant declarations

In the tenant API, schema definition language (SDL) @resolver marks a resolver field and codegen generates a base such as UserResolvers.Greeting. The implementing Kotlin class declares its RSS with @Resolver(objectValueFragment = "display"). These pages put those two declarations together on the schema field:

@Resolver(objectValueFragment = "display")
class Greeting : UserResolvers.Greeting() {
    override suspend fun resolve(ctx: Context): Int? =
        ctx.getObjectValue().getDisplay()?.plus(1)
}

These pages use the tenant annotation’s names for both objectValueFragment and queryValueFragment. Explicit variable sources correspond to Variable(fromArgument = ...), Variable(fromObjectField = ...), and Variable(fromQueryField = ...). A real VariablesProvider provides values represented here by providerVars. Public Viaduct’s @resolver directive takes only isSelective and isBatching (directive definition), so objectValueFragment, queryValueFragment, and variables inside @resolver(...) are shorthand for what the field’s @Resolver class declares in Kotlin.

@fieldChecker and @typeChecker are shorthand too, for a field or type checker registration with those inputs. Public Viaduct has no such directives: a CheckerExecutorFactory turns schema directives, such as a policy-check directive, into checkers, each with its own RSS (registration).

Reading the example panels

First follow how the requirements arise. Then read the explanation above each tree: a tree can show fields needed at an object, output paths requested from a resolver, added ancestor requirements, or fields present after execution. A path names a field; it does not show its value or say that one resolver computes every field below it.

The “What execution confirms” table gives observed values or call counts and explains each one. Those observations are separate from the required paths. The arrows explain dependencies; they do not prescribe execution order. The client response follows the operation’s selections.
