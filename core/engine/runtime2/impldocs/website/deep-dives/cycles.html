Deep dive

Cycles

What happens when two fields need each other. Runtime2’s registry assembly rejects cycles among resolvers and checkers. Anything that still reaches a request meets the cycle checker, which turns a would-be deadlock into an error.

The query asks for a booking’s customerPhone. Two rules on the Booking type read each other: status’s resolver reads customerPhone to mark bookings that have no contact phone, and customerPhone’s field checker reads status so that the phone is shown only on confirmed bookings. Each rule makes sense alone, but together they form a cycle.

# schema
type Query {
  booking(id: ID!): Booking @resolver
}

type Booking {
  id: ID!
  status: String
    @resolver(
      objectValueFragment: "customerPhone"
    )
  customerPhone: String
    @resolver
    @fieldChecker(
      objectValueFragment: "status"
    )
}
# query
query {
  booking(id: "b1") {
    customerPhone
  }
}

In this schema, objectValueFragment inside @resolver(...) is shorthand for what status’s @Resolver class declares: the resolver’s required selection set (RSS). Public Viaduct’s @resolver directive takes only isSelective and isBatching (directive definition). @fieldChecker(...) is shorthand too, for a field checker with that RSS. Public Viaduct has no such directive: a CheckerExecutorFactory turns schema directives, such as a policy-check directive, into checkers, each with its own RSS (registration · checker RSS).

The client never asks for status, but status’s resolver would run anyway: closure, which works out every field an object must produce, adds a checker’s inputs to the object’s demand (closure round). A resolver’s inputs are checked reads: status’s resolver sees customerPhone only after customerPhone’s check has finished (checked read). That check can’t run until it has read status. Neither side can go first, so left alone the request would wait forever.

Runtime2 has two guards of its own. Registry assembly stops this cycle before any request runs: it puts checkers in the same dependency graph as resolvers, and a checked read of customerPhone depends on customerPhone’s checker as well as its resolver (checked inputs · checker inputs · test). The second guard, the cycle checker, works inside the request, on waits that registry assembly can’t see.

The Access checks deep dive explains how checkers run.

What if two fields need each other?

If customerPhone’s resolver read status itself, the two resolvers would each read the other, and neither could ever be called. Runtime2’s registry assembly looks for such cycles once per schema, through checker inputs as well as resolver inputs. Inside the request, the cycle checker then turns any would-be deadlock that got past assembly into an error.

In today’s engine Today, a schema is rejected at bootstrap when status’s resolver reads customerPhone and customerPhone’s checker reads status, and it still is when Runtime2 is enabled. Today’s bootstrap validation, RequiredSelectionsAreAcyclic, rejects it because it follows checker RSSs as well as resolver RSSs, and Runtime2’s registry assembly now rejects it too. Today’s request runtime has no detector for wait cycles between fields. RequiredSelectionsAreAcyclic · bootstrap validation · Runtime2 receives the validated registry

So in a running service, the cycle checker is left with waits that no RSS declares, such as reads a resolver makes through ctx.query(), the tenant API’s nested query call (query). The resolver makes those reads while it runs, and they appear in no RSS, so no check before the request can see them or the waits they create. That nested query runs in a child scope that shares the request’s cycle checker, and the caller’s reads of its result are recorded with the calling resolver’s task as the reader (nested query · doc · shared checker). Runtime2’s tests also put declared cycles in front of it, by swapping in resolvers that skipped assembly, as in the scene below.

Where in code: dependencyOrder · CycleCheckState · a checked read checks the check slot, then the value · the runtime cycle as a test

A read can also come before its slot has a writer, because building a resolver’s input, such as its declared Query fragment, can reserve a cell before that cell’s producer is set up (doc). The cycle checker keeps such a read as a pending read and adds its edge when the writer registers. If that edge would close a loop, the registration throws instead (AbstractCycleCheckState).

So a cycle can’t leave a request stuck: it is either turned away before any request runs or turned into an error, never a hang.

Turn off cycle detection

A test resolver waits on its own cell, and the request runs with a cycle checker that does nothing. Normally the execution strategy, QPlanExecutionStrategy (the QPlan prefix comes from qplan, the development branch Runtime2 was built on; doc), builds each request’s real checker with CycleCheckState.create().

# QPlanRequestLifetimeTest schema
type Query { value: Int }
type Mutation { value: Int }
# value’s resolver is test code below the
# tenant API. Its RSS is empty, so registry
# assembly sees no cycle. It asks the cycle
# checker about a read of its own cell,
# then waits on that cell.
# The test runs Query, then Mutation.
# QPlanExecutionStrategy.kt, line 76
# create(): the real checker, which throws
#   on the read that would close a wait cycle
# createNOP(): records nothing, never throws
- ?: CycleCheckState.create()
+ ?: CycleCheckState.createNOP()

What happens when the test runs?

One test fails, on its Query run, at its check that the response finished (assertion). The test doesn’t wait for the response. It runs the request on a coroutine test dispatcher, and runCurrent() runs only the work that is ready, returning once the resolver is suspended on its own cell (test). With the no-op cycle checker that suspension never ends, and nothing else ends it: Runtime2’s main execution strategy sets no deadline of its own (doc). So the response is still unfinished when the test checks it. The failed assertion ends the test, so its Mutation run never starts. The resolver’s RSS is empty, so Runtime2’s registry assembly has nothing to reject (test). See NOPCycleCheckState.
