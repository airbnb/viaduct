Arguments and aliases

When a query selects the same field more than once, under different aliases or with different arguments, which of those selections are the same work?

The query below loads a venue page. It quotes the text of the first two reviews, shows a star card for the same two, lists as many reviews as an operation variable asks for, and shows the venue’s rating. Aliases, a default argument and a resolver input with its own variable all meet on one Venue, so Runtime2 has to decide which of these requests are the same work.

# schema
type Query {
  venue(id: ID!): Venue @resolver
}

type Venue {
  id: ID!
  reviews(first: Int): [Review] @resolver
  rating(sample: Int = 20): Float
    @resolver(
      objectValueFragment: "reviews(first: $k) { stars }"
      variables: [{name: "k", fromArgument: "sample"}]
    )
}

type Review {
  stars: Int
  text: String
}
# query
query VenuePage($n: Int) {
  venue(id: "V1") {
    quotes: reviews(first: 2) { text }
    card: reviews(first: 2) { stars }
    more: reviews(first: $n) { stars }
    rating
  }
}

# variables: { "n": 5 }

In this schema, objectValueFragment and variables inside @resolver(...) are shorthand for what rating’s @Resolver class declares in Kotlin: its required selection set (RSS), and a variable $k bound to the sample argument. Public Viaduct’s @resolver directive takes only isSelective and isBatching (schema reference).

The question is identity. When two selections look alike, too generous an answer lets different requests share one result, and too strict an answer runs a resolver twice for nothing. Runtime2 decides with keys.

Which selections share a cell?

Do two aliases of the same reviews get one cell or two? A cell is one field’s slot in an object engine result (OER), the engine’s record of one object in the response, and Runtime2 finds it by its key. In a query, the key is the field plus its argument values, with no alias. (Mutations are the exception: their keys add the response key.) So aliases with equal arguments share one cell and one resolver run.

A resolver’s RSS can hold variables of its own. A variable’s value for this request is its binding. So keys come in two kinds: a ground key has all its argument values known, while a symbolic key still holds a variable. A symbolic key names its cell for good, so a late binding never changes which cell it is. Each OER’s orchestrator declares the bindings when it is created.

In today’s engine Today, quotes: reviews(first: 2) and card: reviews(first: 2) get two cells in the Venue OER, because the key that finds a cell includes the alias. In code, that is the Key of an ObjectEngineResult. Each cell is fetched on its own, so the reviews resolver runs once per alias. Runtime2 drops the alias, except in mutation keys. When a binding is pendingSuppose instead that rating were selected only by another resolver’s RSS, say a summary resolver on Venue whose RSS reads rating(sample: $m), with $m bound to summary’s own argument. Then rating’s key would be symbolic, and $k would stay pending until rating’s resolver task works out its arguments. Readers would wait for it.

Where in code: argument coercion · alias-free keys · ground vs symbolic · binding declaration · awaiting bindings · completion lookup · identity rules

So in a query, a cell’s identity comes from its field and argument values, never from an alias or from a value that arrives late. One key means one cell and, for a resolver field, one task.

NoteEvery request follows this rule. Only test-only models of resolution, the reference resolver families, behave differently: some of them share a cell once keys become equal. They never serve requests and are not in the published library (GroundSelections · not published).
