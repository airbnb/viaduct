Deep dive

Selectivity

What Runtime2 does with a field resolver’s output. A selective resolver’s output is used without trimming, but checked: it must stay inside what was asked. A non-selective resolver’s output is trimmed to fit.

The examples use one query that asks for a booking’s start time and its customer’s first name. The booking resolver is selective and the customer resolver isn’t, so a single request shows both rules.

# schema
type Query {
  booking(id: ID!): Booking @resolver(isSelective: true)
}

type Booking {
  id: ID!
  startsAt: String
  endsAt: String
  status: String
  customerId: ID
  customer: User
    @resolver(
      objectValueFragment: "customerId"
    )
}

type User {
  id: ID!
  firstName: String
  email: String
  phone: String
}
# query
query {
  booking(id: "b1") {
    startsAt
    customer {
      firstName
    }
  }
}

In these schemas, @resolver(isSelective: true) is real schema definition language (SDL). objectValueFragment inside @resolver(...) is shorthand for the required selection set (RSS) that the field’s @Resolver class declares in Kotlin. Public Viaduct’s @resolver directive takes only isSelective and isBatching (schema reference).

The booking resolver returns only startsAt and customerId. The schema declares it selective, so the engine expects it to return no more and checks that it doesn’t. The customer resolver makes no such promise. Like many tenant resolvers, it loads the customer’s whole user record, email and phone included. What should the engine do with the extras?

What if a resolver returns more than it was asked for?

Every field resolver call comes with a successor demand, the set of fields later readers need from its output. So what happens when the output doesn’t match it? A selective resolver promises to honor its demand, so its output is used without trimming, but checked against the demand. A non-selective resolver makes no such promise, so its output is trimmed to fit. What remains becomes the new object’s object engine result (OER), the engine’s record of one object in the response.

Runtime2’s resolution always enforces both rules. The selective policy, the per-schema switch for them, is on by default, and Runtime2’s engine never turns it off (setting · engine · per-request setup). The off setting exists only for tests of some reference resolvers, test-only alternative engines that require it off (Resolver07). Runtime2’s resolution refuses to start with it off (check).

In today’s engine a non-selective resolver’s output isn’t trimmed. The engine creates an empty OER, keeps the whole returned object as its source, and fills a cell only when the query plan selects that field, reading the value from the source. Extra fields such as email stay in the source without a cell. empty OER · output kept as source · traversal
In today’s engine the public Viaduct docs let a selective resolver also return fields it wasn’t asked for, as long as no other resolver owns them. Viaduct records those values and may use them if one of those fields is needed later in the request. Runtime2 rejects them instead, so a selective resolver that returns unselected fields today must stop doing so before it runs on Runtime2. selective_resolution.md
Selective without the schemaA service can also mark fields selective without the schema, by passing a FieldSelectivityProvider, an engine interface that answers whether a field is selective, to StandardViaduct.Builder (interface · builder). Runtime2 treats a field as selective if either says so (either), and today’s engine takes the same provider in its configuration (EngineConfiguration).
