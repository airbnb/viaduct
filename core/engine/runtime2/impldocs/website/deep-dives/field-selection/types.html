Example 8 / 13

An interface branches by concrete parent type

Possible parent types and nominal fields survive flattening.

A nominal field is the field as declared on the type the selection was written against, here Node.id on the Node interface. The Node.id selection applies to either Team or User. The fields in the User and Team fragments apply only to their respective types. Merging at User filters out Team’s fields and specializes Node.id to User.id; merging at Team does the symmetric conversion.

Schema · Example 08GRAPHQL

type Query {
  user(id: ID = "u1"): User
  node(id: ID = "n1"): Node
}
interface Node {
  id: ID
  label: String
}
type User implements Node {
  id: ID
  label: String
  name: String
  friend: Node
}
type Team implements Node {
  id: ID
  label: String
  title: String
}

Operation · Example 08GRAPHQL

{
  node {
    id
    ... on User { label name }
    ... on Team { label title }
  }
}
Example 9 / 13

A child starts a fresh type context

A User parent can have a Team friend.

The User condition limits where friend applies. It does not constrain the object returned by friend: Node. Inside friend, Node.id has possible parent types Team and User, and Team.title applies to Team. The two child merges show the alternatives.

Example 10 / 13

Valid nested fragments can have no joint match

Pairwise type overlap does not imply a nonempty cumulative intersection.

I1 can be A or C, I2 can be A or B, and I3 can be B or C. I1 overlaps I2 at A; I2 overlaps I3 at B. The operation passes validation, but no concrete object implements all three interfaces. Flattening stores I3.x with an empty possible-types set.

Schema · Example 10GRAPHQL

type Query { triad: I1 }
interface I1 { x: Int }
interface I2 { x: Int }
interface I3 { x: Int }
type A implements I1 & I2 { x: Int }
type B implements I2 & I3 { x: Int }
type C implements I1 & I3 { x: Int }

Operation · Example 10GRAPHQL

{
  triad {
    ... on I2 {
      ... on I3 { x }
    }
  }
}
Example 11 / 13

__typename crosses a representation boundary

Construction and materialization selections can contain different fields.

The external operation’s construction forest contains User.name and omits __typename. Its recorded construction snapshot was the same as { user { name } }. The internal fragment used to demonstrate materialization selections, parsed with preserveSourceResponseKeys = true, contains User.V_A_typename under response key __typename as well as name. V_A_typename is not in the tenant schema. When Runtime2 lowers the schema for execution, that is, rewrites the tenant schema into the internal schema its engine runs, it adds this ordinary field to every object and interface, so that internal demand for __typename is stored like any other field. V_A marks the names that lowering adds.

Schema · Example 11GRAPHQL

type Query {
  user(id: ID = "u1"): User
  node(id: ID = "n1"): Node
}
interface Node {
  id: ID
  label: String
}
type User implements Node {
  id: ID
  label: String
  name: String
  friend: Node
}
type Team implements Node {
  id: ID
  label: String
  title: String
}

Operation · Example 11GRAPHQL

{ user { __typename name } }

Materialization selections

For resolver and checker inputs, materialization selections are an alternative representation of an object- or Query-rooted required selection set (RSS) that preserves the response keys used in its fragment: each field’s alias, or its field name when unaliased. The engine uses these selections to assemble the input object expected by the consumer.

The materialization selections below retain __typename as the response key for User.V_A_typename, alongside name. The internal fragment demonstrates this representation through materializeSelectionsFrom.

Runtime2 decodes each resolver’s required selection set directly from its complete GraphQL document with specFragmentFromDocument. The decoder follows named fragment spreads and preserves source response keys, including aliases and __typename. Its ParsedSpecFragment.fragment compiles the materialization selections once for reuse by the resolver and its from-field variables.

Internal fragment · Example 11GRAPHQL

fragment Response on User {
  __typename
  name
}
