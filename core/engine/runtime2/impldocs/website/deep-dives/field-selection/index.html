What the forests represent

A selection forest describes fields to obtain, their arguments, where they apply, and their nested subselections. It is a representation of requested work before values are returned. Here “field selection forest” names the topic; the actual Runtime2 code names are SelectionForest and ObjectSelectionForest.

Here construction means building the engine’s object results: which fields, with which arguments, the engine must produce. It is separate from naming fields in the response. The construction forest answers “which field and argument combinations contribute here?” Materialization selections also record “under which response keys does a consumer ask for them?” A query alias can change that second answer without changing the first.

The ordinary forests’ member order has no semantic meaning, and the API does not define whole-forest equality. The diagrams sort members for readability and compare explicit observations, rather than calling forest equality. Only the numbered mutation root shows meaningful order.

In today’s engine The operation and each RSS become a QueryPlan, which keeps response keys and fragment spreads. During execution, CollectFields runs at each object once its concrete type and variable values are known. It applies @skip, @include and type conditions, and groups field occurrences by response key. Runtime2 plans an object’s demand before anything there runs, so it needs a representation that drops response keys, groups by construction key, and keeps arguments open until their bindings are ready.
How this relates to demand closure

This page examines the operation’s selection representation. Resolver and checker required selection set (RSS) expansion adds further requirements later; see Demand closure. Closure builds further selection forests of its own, such as each object result’s construction demand. These examples called Runtime2’s real operation decoder (operationSelectionsFrom) and merge in tests. They inspected forest structure without executing value resolvers, access checks, or a complete GraphQL request.

Features behind the complexity

There are several independent dimensions. Two selections can share a field name while differing in arguments, response keys, type applicability, conditions, or child contributions. The examples introduce each distinction before combining it with the others.

Repeated fields and child sets

Flattening keeps individual contributions. Merging groups construction keys at one level and concatenates their child forests.

Type conditions and specialization

Filter the possible parent types, then specialize nominal fields to the concrete type. A nominal field is the field as declared on the type the selection was written against, such as Node.id on an interface; merge replaces it with the concrete type’s own field, such as User.id. Reading the diagrams

Each box is one stored field member. Its first line is the field coordinate and its decoded arguments. Parent types names the concrete types of the containing object where this member applies. Guard gives the inclusion condition for the chosen request variables; for a client operation it is already Always or Never (Example 6). Indented boxes are subselections.

The title above each tree states the API boundary and the object level being shown. A tree rooted at User starts inside Query.user: it is not another Query-level result. In a parsed forest the guard shown is local: a child marked Always can still sit beneath a parent marked Never, as Example 7 demonstrates. Merge then pushes each contribution’s guard into its own direct children, so in a merged forest a direct child’s guard includes its parent’s. Deeper descendants pick up that guard only when their own level is merged (Examples 7 and 13). The same coordinate appearing twice means two stored contributions, not two resolver calls. Gray dashed boxes are Never members. A member whose possible-types set is empty is marked ∅ and drawn in pink (Example 10).

The APIs behind the trees

Operation decoding and one-level mergingKOTLIN

val parsed: SelectionForest = world.schemas.operationSelectionsFrom(
    documentSource = operation,
    variables = requestVariables,
)
val query: ObjectSelectionForest = parsed.merge(queryType)
val user: ObjectSelectionForest =
    query.single().subselections.merge(userType)

The example tests used this pattern for a single user field, as in Example 1. world was a TestWorld built from the schema. The concrete type arguments choose the level being normalized. Merging Query does not recursively normalize the returned User.
