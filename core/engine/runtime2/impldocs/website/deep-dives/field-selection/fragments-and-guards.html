Examples 5 to 7 of 13: fragments, skip and include, and guards on overlapping parents.

Example 5 / 13

Fragments multiply field contributions

Flattening removes fragment boundaries, not repeated contributions.

Each Identity spread contributes id and name. The inline User fragment contributes another name. There are five children in the parsed forest, with no fragment nodes left. Merging at User leaves id and name.

Example 6 / 13

Guards travel through fields and spreads

A false contribution can remain stored as Never.

The three name contributions are governed by show, show AND NOT skip, and NOT skip. The middle one comes from an inline fragment with no type condition. The named spread gets its type condition from Name’s definition. A client operation’s variables are known when it is decoded, so each of these expressions is already reduced to Always or Never. The expressions are the logic that produced each stored guard; the boxes show only the result. The diagrams sort members, so the name boxes don’t follow this source order. Merging the children combines the contributions with OR, so name is Always when show OR NOT skip is true and Never otherwise.

Operation · Example 06GRAPHQL

query Guards($show: Boolean!, $skip: Boolean!) {
  user {
    id
    name @include(if: $show)
    ... @include(if: $show) { name @skip(if: $skip) }
    ...Name @skip(if: $skip)
  }
}
fragment Name on User { name }
Example 7 / 13

Overlapping parents must keep child guards distinct

OR the parent conditions; guard each contribution’s own children.

The raw children id and name each have Always locally; their restrictions are on their separate user parents. After merge(Query), the parent’s guard is the value of left OR right, while id receives the value of left and name the value of right. As in Example 6, each is stored as Always or Never. Select left = true, right = false to see one included child and one Never child beneath an Always parent.
