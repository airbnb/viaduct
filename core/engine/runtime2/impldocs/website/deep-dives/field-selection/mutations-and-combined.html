Example 12 / 13

Mutation roots keep order and response identity

Ordinary query coalescing would discard required mutation distinctions.

The mutation forest collects the repeated second response key at its first appearance. first and another remain separate even though they both call set(value: 1). The omitted contribution is removed because its skip condition is true. Unlike an ordinary forest, a mutation root requires every condition to be already Always or Never, so it can drop Never contributions up front. The numbered list below is the forest’s actual order.

Example 13 / 13

One operation combines the rules

Aliases, arguments, a union, guards, and a nested interface result interact.

The two aliases select the same entity construction key because $id defaults to "n1". The Entity union allows User or Team. The first contribution, left, adds guarded User fields and descends into friend: Node through a named fragment; the second, right, adds User and Team branches under a guarded parent. The parsed forest doesn’t store aliases and lists right’s entity first, so the diagram tags each entity with its alias. Merging Query combines their children. A merge pushes each contribution’s guard into its direct children only; it leaves grandchildren unchanged. So after merge(Query), the children under a Never User.friend (select left = false) still show Always; they change at the next merge, as the forest for an entity that is a User shows. Only the Query level is normalized: after merge(Query), User.label still appears twice, once from each contribution, and at left = true, right = false one is Always and the other Never. The next merge must choose User or Team, and merging friend must independently choose its result type. Merging at a concrete type rebuilds each key on that type’s own field, so Node.id under friend becomes Team.id after merge(Team).

Schema · Example 13GRAPHQL

type Query { entity(id: ID = "n1"): Entity }
union Entity = User | Team
interface Node {
  id: ID
  label: String
}
type User implements Node {
  id: ID
  label: String
  name: String
  friend: Node
}
type Team implements Node {
  id: ID
  label: String
  title: String
}

Operation · Example 13GRAPHQL

query Combined($id: ID = "n1", $left: Boolean!, $right: Boolean!) {
  left: entity(id: $id) {
    ... on User @include(if: $left) {
      label
      friend { ...Friend }
    }
  }
  right: entity(id: "n1") @include(if: $right) {
    ... on User { label name }
    ... on Team { label title }
  }
}
fragment Friend on Node { id ... on Team { title } }

Sources and verification

Adapted from Andy Marek’s Viaduct guide.

The diagrams show snapshots that were recorded when the examples were run: 13 passing JUnit tests, covering 25 input combinations and 106 assertions, with no skipped examples. Each test provided the schema, parsed its operation through Runtime2, and compared observed members against explicit field, argument, type, guard, and child observations. Variable variants ran separately within their example tests.

These claims were checked against the code the source links below point to. The recorded results came from runs at an earlier revision and weren’t re-run here.
