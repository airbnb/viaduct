Deep dive

Into the code

Where each concept lives, the few lines where each idea becomes code, and how the packages stack up.

The query below asks for a booking’s confirmation code and its customer’s first name. It has one parent resolver, for booking, and one child resolver, for customer, whose object fragment reads a field the client never selected. Assume the booking resolver returns only confirmationCode and customerId; if it returned customer too, customer’s own resolver wouldn’t run.

# schema
type Query {
  booking(id: ID!): Booking @resolver(isSelective: true)
}

type Booking {
  id: ID!
  confirmationCode: String
  customerId: ID
  customer: User
    @resolver(
      isSelective: true
      objectValueFragment: "customerId"
    )
}

type User {
  id: ID!
  firstName: String
  lastName: String
}
# query
query {
  booking(id: "b1") {
    confirmationCode
    customer {
      firstName
    }
  }
}

In this schema, objectValueFragment inside @resolver(...) is shorthand for what customer’s @Resolver class declares: the resolver’s required selection set (RSS). Public Viaduct’s @resolver directive takes only isSelective and isBatching (directive definition).

Runtime2 holds each object in the result as an object engine result (OER), with one cell per field to hold that field’s value. Each object also gets an orchestrator, a task that sets up the object’s work. For the Booking, closure adds customerId to the fields Runtime2 must produce, because customer’s resolver reads it. The orchestrator then claims the customer cell for customer’s resolver task. Where does each idea live in Runtime2’s source?

In today’s engine Today’s OER is ObjectEngineResultImpl in core/engine/runtime, which keeps its cells in a map. Runtime2’s ObjectEngineResult is a separate type in its own model package, and no Runtime2 source file imports today’s. ObjectEngineResultImpl · Runtime2’s ObjectEngineResult

Each concept has one type to start from, a few excerpts carry the Booking from demand to the User, and the packages are layered so you know which way to read.

Six steps, one Booking

A map shows where to start, not how the pieces hand off. The excerpts follow the customer field in the order things happen to it, from the Booking’s orchestrator to the customer’s User. Step 4 also looks back at the booking resolver task, which ran before all of them:

  1. Orchestrator ordering: creating the Booking’s orchestrator prepares its work before any task is dispatched.
  2. Closure: one pass adds customerId to the demand.
  3. One writer per cell: the customer cell is claimed for customer’s resolver task.
  4. Successor demand, a look back: before any of this, the booking resolver task worked out what to ask its resolver for, and customer’s task does the same.
  5. Invoke once: the task calls customer’s resolver.
  6. New occurrence: passive descent builds the customer’s User.

Orchestrator ordering. The booking resolver returns a Booking, which gets an OER and an orchestrator. The orchestrator works on two OERs: the Booking’s own, and its associated Query OER, a fresh OER for the Query type that it creates to hold the Query fields its object’s resolvers and checkers read (fresh Query OER). Creating the Booking’s orchestrator does four things synchronously, before any resolver or checker task is dispatched:

  1. Closure closes the Booking’s demand.
  2. Bindings are declared.
  3. Parent fields get their values. A field marked @parent, a public Viaduct directive, is one the engine provides itself, whose value is the object one level up, and each demanded @parent field gets its cell set to that OER now.
  4. Checker tasks are prepared. A checker is an access check: a field checker guards one field, and a type checker guards every object of one type. In public Viaduct, a CheckerExecutorFactory supplies checkers, turning schema directives such as a policy-check directive into them (registration). None of the Booking’s fields has a checker, but in general the cell of each key in checked demand (client selections and resolver inputs, whether or not the field has a checker) is reserved, and when the field has a checker, its field-check slot also gets a writer.

The first excerpt runs closure, producing closedConstructionDemand, and wraps each OER with its closed demand. Here source is the data the booking resolver returned, and the Query-rooted half of the starting demand is Demand.EMPTY, so the Query OER’s demand holds only what closure adds. The second does the other three steps. Its last call, observeQueryOER(), only reports the prepared Query OER and its declared Query fragments to the request’s resolver observer, whose default does nothing (default).

Closure. Closure has two loops, and closeSelectedConstructionDemand picks one from the world’s usePrecomputedConstructionDemand setting (switch). Engine2, Runtime2’s implementation of the engine API (Engine2), turns the precomputed loop on by default (default). That loop reuses input demand the registry prepared once per schema, and both loops produce the same ClosedConstructionDemandContext (doc). The excerpt below is a round of the dynamic loop, in ConstructionDemandClosure.kt, which spells out each step. Each pass turns newly found keys into input demand, the resolver fragments that the keys’ resolvers and checkers read. The loop breaks once a pass finds nothing new. Each round covers both OERs, the object’s own and its Query OER, with one context per field key found so far. In the highlighted lines:

  • objectResolverInputs holds the inputs of the object’s own resolver fields (line 160). Their object fragments become the object’s checked demand (line 170).
  • The inputs of field checkers and type checkers become unchecked demand (line 171).
  • The Query OER’s checked demand, queryInputSelections, gets the Query fragments of the object’s resolvers and both fragments of the resolvers demanded on the Query OER (line 175).
  • pendingDemand is the round’s new demand, which the next pass expands (line 181).

customer is one of the Booking’s own resolver fields, so its object fragment, its RSS, goes into objectResolverInputs.objectFragment and becomes the Booking’s checked demand. That is how closure adds customerId.

In today’s engine Each resolver’s and checker’s RSS becomes a separate child query plan, and a plan launches its child plans before its own selections. Runtime2 has no child plans: closure merges those inputs into the demand of the object, or of its Query OER for Query-rooted inputs, before any task is dispatched. childPlanIds · resolver and checker RSS plans

One writer per cell. The orchestrator’s run calls FieldResolverTask.prepareAll, whose prepare makes each resolver task its cell’s one writer before that task is dispatched. For the Booking, that task is customer’s:

  1. It reserves the task’s cell, or gets the one checker preparation already reserved.
  2. It claims the cell’s value promise.
  3. It registers the task as the writer of the cell’s value slot, named by the cell and CycleSlotKind.VALUE, with the cycle checker, which uses these writers to turn a wait cycle into an error.

What if a reserved cell never gets a writer? If the booking resolver leaves customerId out, nothing writes its cell. Checker preparation already reserved that cell, as it does for every key in checked demand (reserve). When the orchestrator freezes the Booking OER, freeze fails each reserved cell that no one claimed with a missing-cell error (freeze · unclaimed). A filled passive cell isn’t failed, because passive descent writes it with set(), which claims and completes it in one call (fill · set). So customer’s read of customerId fails instead of waiting forever.

Successor demand. It is what a resolver task asks its resolver to return. Just before calling the resolver, the task derives it from the construction demand below its field, using the registry: each included field that has a resolver adds that resolver’s declared inputs. So the booking resolver task adds customer’s RSS and asks the booking resolver for customerId, which the client never selected. The Booking’s OER and closure come only after that resolver returns. Closure derives customerId too, because the two answer different questions: successor demand tells the booking resolver what to return, and closure decides which cells the Booking OER holds, so that customer’s resolver has a customerId cell to read. The customer resolver task asks its resolver for firstName, the one field the client selected below customer. The unchecked part, checkers’ inputs, is converted the same way, and when the returned object may need a type check, the inputs of the type checkers for every type it could be are added too. Demand that @parent fields induce is worked out in the same walk (comment).

Invoke once. publishResult computes that demand first, then checks the cell’s activation, its include-or-skip decision. A task whose cell is not activated returns before any tenant code runs. Otherwise the demand becomes the resolver’s selections. runFieldResolver has just this one call site, and each task calls publishResult once (call). Since prepare made the task its cell’s one writer, a field’s resolver runs at most once for each occurrence of the field. The other branches skip runFieldResolver: a root-field reference, which the code after this excerpt hands to its root field’s resolver, or a PassiveValueOccurrence, a list of root-field references, such as node references, copied from the parent’s output under an inclusion condition, which a task holds until its activation is decided.

New occurrence. The customer resolver returns a User. Passive descent, the resolver task’s walk over the value its resolver returned, handles it. Like any returned object, the User gets a fresh OER, then its own orchestrator:

  1. The orchestrator is created, which runs its closure.
  2. materializePassiveFields fills the cells of the passive fields from the returned data, which for the customer is firstName. This writes cells, unlike materialization, which reads them to build a consumer’s input. User has no resolver fields, so no cell waits for a task.
  3. The orchestrator is dispatched. With no tasks to dispatch, its run only freezes the User OER and its associated Query OER, which seals each one’s set of cells, and that happens before dispatch returns. A run never suspends, so even an orchestrator with tasks has claimed, dispatched and frozen before dispatch returns.

This code lives in resolution/framework, which never imports the rest of resolution. createOrchestrationTask is an abstract hook that resolution’s subclass implements, and dispatchOrchestration belongs to the framework’s own dispatcher interface (subclass · interface).

The package layers

The packages form layers, with a shared vocabulary at the bottom, the resolution machinery on top of it, and above that the entry point that runs a request, with the bootstrap that builds the registry beside it. bootstrap imports the entry point, never the reverse. Imports only point one way, so you can read the code from the bottom up.

The resolution machinery’s framework subpackage holds the contracts and model operations that Runtime2’s main engine shares with all the reference resolver families. These are six simpler alternate resolution engines, kept in the unpublished src/testFixtures tree, which is not part of the published library (doc · publication check). A semantic change should become testable in the simplest family that applies, the depth-first reference resolvers before the coroutine ones, before it reaches the main engine (doc). Here a “reference resolver” means a whole engine, not a tenant’s field resolver. The Reference resolver families deep dive covers them.
