Deep dive

Access checks

Field and type checkers run beside resolvers, in their own tasks. Their verdicts are applied later, at the moment someone reads the value.

This query asks for a payment’s amount and the last four digits of the bank account it goes to. A payment is private financial data, so a checker guards every step of the request.

Runtime2 holds each object it builds in an object engine result (OER), like today’s ObjectEngineResult. An OER has one cell per field, which holds the field’s value and, separately, its field check’s verdict. The OER also has one slot for its type check’s verdict.

In the example schema, @fieldChecker and @typeChecker are shorthand for checker registrations, and their arguments declare each checker’s inputs. In public Viaduct, a service attaches checkers through a CheckerExecutorFactory, which returns the checker, if any, for each field and type. It may decide by reading a policy-check directive in the schema. Each checker declares its inputs as required selection sets (factory · inputs · policy-check directive).

# schema
type Query {
  viewerId: ID @resolver
  payment(id: ID!): Payment
    @resolver
    @fieldChecker
}

type Payment
  @typeChecker(
    objectValueFragment: "ownerId"
    queryValueFragment: "viewerId"
  ) {
  id: ID!
  ownerId: ID
  status: String
  amount: Int
  bankAccount: BankAccount
    @resolver(objectValueFragment: "ownerId")
    @fieldChecker(objectValueFragment: "status")
}

type BankAccount @typeChecker {
  id: ID!
  last4: String
}
# query
query {
  payment(id: "p1") {
    amount
    bankAccount {
      last4
    }
  }
}

On @resolver, objectValueFragment is shorthand for the required selection set (RSS) that the field’s @Resolver class declares in Kotlin. Public Viaduct’s @resolver directive takes only isSelective and isBatching (schema reference). On the checkers, objectValueFragment names inputs on the object the same way, and queryValueFragment names inputs rooted at Query.

Four checkers guard this data. The field checker on Query.payment receives the field’s id argument and decides whether the viewer may look up payments. The Payment type checker admits only the payment’s owner, by comparing ownerId with viewerId. The field checker on bankAccount hides the account while the payment’s status says it is under review, and the BankAccount type checker guards every bank account, wherever it appears.

That raises two questions. When does a check run, and who makes sure its verdict is respected? In Runtime2 a check runs beside the resolver, and whoever reads the value applies its verdict, including completion when it reads the response data.

Checkers decide who may see a value

Start with bankAccount, which has a field checker, and BankAccount, which has a type checker. A field checker guards one field, and a type checker guards every object of its type. Both are registered next to the resolvers, and both can declare inputs, just like a resolver: bankAccount’s checker reads status.

Checks run beside the resolvers they guard, in their own checker tasks, and each verdict waits in a slot of its own. Whoever reads the value applies the verdict through a checked read, while a raw read skips it.

In today’s engine Today, bankAccount’s field checker also runs beside its resolver, and BankAccount’s type check is folded into bankAccount’s access-check slot. In Runtime2 the type check is stored once, in the type-check slot of the BankAccount OER. Both engines apply verdicts when the value is read: today completion and resolver input reads check the access-check slot too (resolver reads). They differ when a field both fails and is denied. Either way the field fails with one error at its path, but today that error is the resolver’s own (FieldCompleter), while in Runtime2 it is the checker’s denial (doc).
In today’s engine Today’s engine runs a checker on a top-level mutation or subscription field before its resolver (fetchField). Runtime2 has no such checker-first rule (doc). Instead, Runtime2 fails a request that selects a mutation field with a field checker, or whose Mutation type, or a namespace type under it (a @namespaceType type that groups mutation fields), has a type checker. Checkers on the payload still run (see Mutations).

A checker runs only when some reader will apply its verdict. A client selection or a resolver input is a checked read, so it makes the field’s field checker run and, for an object value, that object’s type checker too. A checker’s raw read doesn’t. Suppose the Payment type checker also read bankAccount, so its object input were this, and the client didn’t select bankAccount:

# Payment type checker’s objectValueFragment
ownerId
bankAccount { id }

bankAccount’s resolver would still run, because the checker needs the raw value, but neither bankAccount’s field checker nor the BankAccount type checker would. The BankAccount OER’s orchestrator would set its type-check slot to null, which means no type check is needed, because no reader applies one (TypeCheckerTask, Demand.unchecked, doc).

Where in code: dispatched as peers · FieldCheckerTask · TypeCheckerTask · materializeCheckedValue

A denied input doesn’t stop a resolver. The resolver still runs, but its input holds an error at the denied field, and reading that field throws the checker’s error. A resolver that never reads the field can still return a value (doc). If the resolver lets the error escape, its own field fails with it (contract test).

In today’s engine Resolvers see the same thing today: the engine stores the checker’s error in the resolver’s input and throws it when the resolver reads that field (SyncEngineObjectDataFactory).

What if payment has access checks?

Now follow the request one level up, at the payment itself: the field checker on Query.payment and the type checker on the Payment object. The request runs twice, once with every check passing and once with the field checker denying. The question is where the denial takes effect.

Where in code: materializeCheckedValue · FieldCheckerTask

In today’s engine A check on payment doesn’t hold back the resolvers beneath it today either: they start once payment’s raw value arrives (FieldResolver). In both engines, completion turns a denied payment into an error and never reads the Payment’s fields, so no data below the denial reaches the client (FieldCompleter, QPlanWiringFactory).

So checks run without holding back the resolvers they guard, and a denial takes effect where the value is read, as an error at that field.

Try it

A field checker denies

The payment is under review, so bankAccount’s field checker returns Error. Every other check passes.

# schema
type Payment {
  status: String
    # "under_review"
  amount: Int
    # 120
  bankAccount: BankAccount
    @resolver(objectValueFragment: "ownerId")
    @fieldChecker(objectValueFragment: "status")
}
# query
query {
  payment(id: "p1") {
    amount
    bankAccount {
      last4
    }
  }
}

Does bankAccount’s resolver still run?

Yes. A field checker task never gates the resolver that produces its field’s value: the two tasks run side by side, and the denial takes effect only when the value is read (doc). The BankAccount type checker still runs too. Its task starts once the resolver’s value becomes a BankAccount OER, as part of that OER’s orchestration, and the field denial doesn’t stop it (doc · TypeCheckerTask).

What is the response?

{payment: {amount: 120, bankAccount: null}}, one error at [payment, bankAccount]. The denial fails only the guarded field, and its parent keeps its other fields (contract test; compare a checker on a root field: contract test).

Which reader ignores access checks?

A checker’s input. Checkers read their inputs raw, without checks (doc).

What does a checked read await?

Completion reads bankAccount while everything about it is still pending: its field check, its value, and the BankAccount’s type check.

# schema
type Payment {
  bankAccount: BankAccount @resolver @fieldChecker
}
type BankAccount @typeChecker {
  last4: String
}
# query
{
  payment(id: "p1") {
    bankAccount { last4 }
  }
}

In what order does the checked read of bankAccount await these?

  1. The cell’s field-check slot
  2. The cell’s value promise
  3. The object’s type-check slot

Field-check slot, value, then the object’s type-check slot, so a field denial returns before the value is awaited. The last await happens only because the value is an object (awaitCheckedValue).
