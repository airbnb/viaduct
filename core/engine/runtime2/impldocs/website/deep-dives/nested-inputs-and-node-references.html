Nested inputs and node references

Two cases where a field’s value takes more than one plain call: a list whose elements need a field nobody asked for, and a resolver that returns a node reference instead of an object.

The example

This query asks for a booking’s first two messages, each with a short preview, and for the name and city of the venue it books. Each message’s preview is computed from a body the client never asks for, and the booking’s venue resolver hands back only a reference that a node resolver turns into the Venue.

# schema
type Query {
  booking(id: ID!): Booking @resolver
  # built-ins
  node(id: ID!): Node
  nodes(ids: [ID!]!): [Node]
}

type Booking {
  id: ID!
  venueId: ID
  messages(first: Int): [Message] @resolver
  venue: Venue
    @resolver(
      objectValueFragment: "venueId"
    )
}

type Message {
  sentAt: String
  body: String
  preview: String
    @resolver(
      objectValueFragment: "body"
    )
}

type Venue implements Node @resolver {
  id: ID!
  name: String
  city: String
}
# query
query {
  booking(id: "b1") {
    messages(first: 2) {
      sentAt
      preview
    }
    venue {
      name
      city
    }
  }
}

In these schemas, objectValueFragment inside @resolver(...) is shorthand for the required selection set (RSS) that the field’s @Resolver class declares in Kotlin. Public Viaduct’s @resolver directive takes only isSelective and isBatching (schema reference).

The @resolver on the Venue type declares its node resolver, which loads a Venue from its ID. Query.node and Query.nodes are built in, and they reach that node resolver.

Both cases keep the same machinery: demand flows down, resolver tasks call resolvers, and values fill write-once cells. The cells of one object in the response make up its object engine result (OER), the engine’s record of that object while it is built. Each case adds one rule.

A field nobody asked for

Start with the messages. The client asks for each message’s sentAt and preview, but preview’s resolver reads the message’s body, which nobody asked for. The messages resolver returns only what it’s asked for. So who makes sure the body is there?

A parent’s demand carries the inputs its children’s resolvers need, and each object element of a list result becomes its own OER, with its own orchestrator and tasks.

Where in code: successor demand · declared input · list elements · omitted fields fall to their resolver · resolver input

In today’s engine preview’s RSS runs as a child plan, a part of the query plan that is planned ahead for preview’s inputs and launched over each Message OER, and body, which has no resolver, is read from the messages resolver’s output. In Runtime2, that input reaches the messages resolver as part of its demand. launchFieldChildPlans

A node reference

Now take venue. Its resolver reads venueId and only says which venue it means. What it returns is a node reference, which names a node by type and ID and has only its id readable. Something still has to turn it into a Venue.

No new task does that: the venue resolver task resolves the reference itself. One call that resolves one reference is a hop, and a resolver task keeps making hops in its tail loop while its value is still a reference. That happens when the field a hop calls has a resolver that itself returns a reference. Each hop uses its own invocation root, a fresh, empty Query OER that gives the call its own identity and holds no data. It needs none, because a reference’s target resolver isn’t allowed to declare an object RSS (no object RSS). A node resolver receives only an ID and the fields asked for (node resolver call).

Where in code: createNodeReference · ctx.ref passes the global ID · encoded ID · tail loop · invocation root · node dispatch · built-in node/nodes · list references

NoteThe target may still declare a Query RSS. Say the field a hop calls also reads viewerId from Query. The hop then builds viewerId in a separate Query OER with its own orchestrator, which runs Query’s resolvers for just that RSS. The invocation root only gives the call its identity and never holds data, so it stays empty (identity only · Query RSS input).
In today’s engine When venue’s resolver returns a node reference, a pending Venue OER is created at once and the node resolver runs in the background. Resolvers on Venue’s own fields may start before it finishes. If it fails, their results are thrown away and the whole venue field is treated as failed. A selective node resolver is the exception: its OER is made available only after the node resolver returns the fields the query selects on the node. Runtime2 treats both kinds the same way. The venue cell stays pending until the hop returns, and only then is the Venue OER created, so resolvers on its fields start after the node resolver. If the node resolver fails, the venue resolver task completes the venue cell with the error. In both engines venue fails, but in Runtime2 no work on Venue’s fields runs only to be discarded. lazyObjectEngineResult · pending OER · selective node · publishFieldError

What changed

Each case needed only one new rule. With the messages, a parent’s successor demand carries the inputs its children’s resolvers need, and each object element of a list gets its own OER and tasks. With the venue, a reference that a resolver returns directly is resolved inside that resolver task, and the object lands in the original cell.

Everything else stays the same: demand flows down, each cell has one writer, and readers wait on cells. The Into the code deep dive maps each concept to the types that carry it, so you can find these rules in the source.
