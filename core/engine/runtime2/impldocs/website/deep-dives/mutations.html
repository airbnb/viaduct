Deep dive

Mutations

Why a mutation’s root fields run one at a time under a single mutation orchestrator, what Runtime2 doesn’t allow on them, and when completion starts reading the result.

A query never changes anything, so Runtime2 can start its root fields together and let completion read their cells as they fill. A cell is one field’s slot in an object engine result (OER), Runtime2’s record of one object in the result, like today’s ObjectEngineResult. A mutation is different, because each root field may change data the next one reads, so the order the client wrote is part of what the request means.

What if the operation is a mutation?

GraphQL requires mutation root fields to run in order. For a query, the root orchestrator dispatches every root field at once. A mutation is run instead by one mutation orchestrator, which takes the root fields one at a time.

A field’s payload is its value plus every check and cell beneath it, except @parent fields (a public Viaduct directive), which return the object one level up (MutationCompletion). Before the next field starts, the orchestrator waits for the current field’s whole payload, not just its value.

Mutation fields can also sit inside a namespace: a field with no resolver whose type is marked @namespaceType, the public Viaduct directive that marks a type whose fields group related operations, such as venue here (MutationSelectionForest).

# schema
type Mutation {
  venue: VenueMutations
  publish: Boolean @resolver
}

type VenueMutations @namespaceType {
  create: ID @resolver
  update: ID @resolver
}
# query
mutation {
  venue {
    create
    update
  }
  publish
}

The fields inside a namespace run in order too. When the mutation orchestrator reaches venue, it creates a mutation orchestrator for that level and runs it to the end before moving on, so this request runs create, then update, then publish. The namespace field venue has no resolver task: the mutation orchestrator claims its cell itself and, once the nested level has run, completes it with that level’s OER (MutationOrchestrationTask).

Two aliases of the same mutation field, such as a: publish and b: publish, run separately, one after the other. Their keys include the alias, unlike keys in a query (MutationKey; see Arguments and aliases).

In today’s engine Each mutation field’s fetch, and every object below it, also finishes before the next mutation field starts. Today’s engine also runs a namespace’s fields one at a time (FieldResolver), and a failed field doesn’t stop the next one (FieldResolver). Runtime2 keeps that order. dispatchFieldsSerially Completion is different: today it runs alongside the fetch for a mutation too, while Runtime2 holds it back until every mutation has finished. What Runtime2 rejects on mutation fields

Runtime2 also limits what a mutation field may declare. Both rules cover the root Mutation type and any namespace type nested under it, not the payload a mutation returns.

  • No required selection sets (RSS). When Runtime2 builds its registry, it rejects a mutation resolver that declares an object or Query RSS. A mutation resolver reads other data by calling ctx.query() inside its body instead, which the error message suggests.
  • No checkers. As the mutation orchestrator prepares each namespace level, it fails the request if a selected field at that level has a field checker, or if that level’s type, the Mutation type or a nested namespace type, has a type checker. Checkers on the payload’s objects and fields still run as in a query. Runtime2’s initial mutation support doesn’t cover these checkers (resolution.md). The check runs when the orchestrator for that level is created, and the error reads “Mutation namespace field checkers are not supported” or “Mutation namespace type checkers are not supported” (prepare). A nested level’s orchestrator is created only when the run reaches it, so this check can fail after earlier mutation fields have run, and no code undoes their effects (run).
In today’s engine Today’s engine rejects an RSS on a mutation resolver too, with similar advice. ResolverSelectionSetsAreProperlyTyped Checkers differ: today a field checker on a top-level mutation field is allowed, and it runs first, so the resolver runs only if the check passes. Runtime2 has no equivalent: a request that selects such a field fails. fetchField

A query’s root fields start together, while a mutation’s go one at a time, each with everything it set off, and completion begins only after the last one.

Try it

Two mutations, one fails

The first mutation returns an error. The second one’s resolver suspends for a while, pausing without blocking a thread, before it returns a value.

# schema
type Mutation {
  failed: Int! @resolver
    # returns an error
  later: Int! @resolver
    # suspends, then returns a value
}
# query
mutation {
  failed
  later
}

Can the response finish before later does?

No. Completion waits for every mutation to finish, failed or not, so later runs to the end before the response is built (strategy). The response then has data null and one error at [failed]: failed is non-null (Int!), so its error nulls the whole result. A test checks both, and that the response isn’t done while later is suspended (test).
