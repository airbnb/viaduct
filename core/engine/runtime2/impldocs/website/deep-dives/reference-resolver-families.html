Deep dive

Reference resolver families

Beside Runtime2’s main engine sit six reference resolvers. They come in two families that schedule work in different ways, and one correctness model judges them all.

Runtime2 runs requests with one engine, its main engine. But six more resolvers sit beside it, numbered and kept in the repository, not in the published library.

Here “resolver” means something bigger than usual. A reference resolver is a whole alternate resolution engine, not a tenant’s field resolver: each one takes a query’s selections and builds the entire result tree its own way. That tree is the response under construction, one object engine result (OER) per object, much like the ObjectEngineResult tree in today’s engine. The code calls them resolvers (resolver06 … resolver23), so this page keeps that name.

Why keep them, and what must they agree on?

Why are there six more resolvers beside the main engine?

The main engine (Resolution) lives in src/main. Next to it, src/testFixtures, a separate source set that compiles against src/main, holds six numbered reference resolvers. The design notes call it the unpublished testFixtures tree. A build check fails if the published runtime JAR contains any of its output (publication check). The resolvers implement the same semantics and form a two-by-three grid. The numbers name source files, not a sequence of versions.

Each column is a family with its own execution structure, its way of running tasks:

  • 06–08 keep explicit depth-first tasks in a priority queue. A loop called the reactor pops the first task, runs it, and queues the tasks it creates.
  • 21–23 use structured coroutines.

Each row is one semantic stage, so you can recognize each role in both families. The first row (06, 21) is the base: resolvers may read Query fragments, the fields a resolver reads from Query, but no object fragments, and variables come from arguments or a variables provider. This row requires the selective policy off. The selective policy is a per-schema switch that holds every resolver’s output to the fields it was asked for. With it off, each resolver’s output is kept whole, so the result can hold more OERs than the query needs.

The second row (07, 22) adds object fragments, the fields a resolver reads from its parent object, still with the policy off. Query fragments fit the base row because each orchestrator builds them in a fresh Query OER of its own, which starts with no data. Its fields are built by their own resolvers, so no resolver above has to return them. An object fragment reads the parent object, and here the rows differ in what a resolver is asked to return: 06 asks a resolver only for the selections below its field (06), while 07 also follows the inputs of the resolvers beneath it, and adds only the paths in them that lead to fields with resolvers of their own (07 · rule). In the example below, name and friends read id, which has no resolver, so 07 doesn’t ask the user resolver for id. It doesn’t need to: with the policy off, each resolver returns its complete output, id included (grid). If name’s RSS instead read a field with its own resolver, such as a display field, 07 would add display to the user resolver’s request. That path marks a resolver boundary, so 07 can find display’s resolver as work to run (boundary). The third row turns the policy on (08, 23).

Some features don’t follow the rows. Both families handle root-field references, such as node references, and ordered mutations. Only 22 and 23 support @parent fields (a public Viaduct directive). Of the reference resolvers, only 21–23 support access checks: 21 allows checkers whose inputs have no fragments, and 22 and 23 add checker fragments. 06–08 need a registry with no checkers. Nested ctx.query() and ctx.mutation() calls work only in the main engine.

Both families, like the main engine, run two kinds of task: an orchestrator plans one object’s fields, and a resolver task runs one field’s resolver. All of them implement the same shared interfaces in the resolution.framework package for these tasks and their dispatcher. For mutations, both families and the main engine use the same shared class from resolution.framework, MutationOrchestrationTask.

Within a column, the resolvers share code. The reactor and its task classes live in resolver06, and 07 and 08 run the same reactor with their own rule for what a resolver is asked to return. Its orchestrator task freezes each object’s OER after dispatching its fields, so the OER can’t gain new ones. The coroutine family extends the main engine’s base classes for orchestrators and resolver tasks, so it freezes through the main engine’s orchestrator base. It also uses the main engine’s dispatcher, CoroutineTaskDispatcher, inside one runBlocking call, so all its coroutines run on the calling thread (runBlocking · dispatcher). Across a row, each coroutine resolver asks for the same output as its depth-first partner: 21 as 06, 22 as 07 (22), and 23 as 08. 23 uses a variant of 08’s rule that also adds checker inputs.

Why keep them? First, they protect the main engine’s design: each role must stay recognizable across both ways of running tasks, and any difference between families must have a stated reason. Second, they set the order of development. A new semantic feature should first become testable in the simplest family that fits, the depth-first tasks (06–08) before the coroutines (21–23), before scheduling and suspension come into play (ladder). Debugging follows the same ladder: reproduce a bug in 08, then 23, then the main engine, and drop to the base or fragment row when selective output isn’t involved.

The main engine always runs with the selective policy on (see Selectivity), so the design notes name the third row, 08 and 23, as the usual models to compare the main engine with: they run with the policy on, as the main engine does, but with simpler scheduling. That comparison guides design and debugging. One correctness model, correctResolution, defines the correct result.

correctResolution takes a finished result and the query, reapplies each resolver function to the inputs found in the result, and checks that the result agrees. That works because the model treats each resolver function as deterministic: the same inputs give the same output (replay · resolver function). It doesn’t check execution order or concurrency. Both families and the main engine run shared contract tests, and after each test a post-test policy checks every result with correctResolution. So the contract tests judge the main engine by the model, not by comparison with a family’s output.

The same task graph under three schedules

# schema
type Query {
  user: User @resolver
}

type User {
  id: ID!
  name: String
    @resolver(objectValueFragment: "id")
  friends: [User]
    @resolver(objectValueFragment: "id")
}
# query
{
  user {
    name
    friends {
      name
    }
  }
}

As on the other deep dives, objectValueFragment inside @resolver(...) is shorthand for the resolver’s required selection set (RSS), its object fragment, here id. Take this query. It makes one small task graph, with an orchestrator per object and a resolver task per resolved field.

Both families run that graph on a single thread, in a fixed order, but each picks the next task its own way. The main engine runs the graph on the request’s coroutine dispatcher, which may have several threads. The orders differ at one point; the question is whether the results differ too.

In today’s engine Today, name’s resolver runs whenever name is selected, even if the user resolver’s output already holds name. The one exception is a value marked as parent-managed (ParentManagedValue), which skips the registered resolvers below it until a nested StandardResolutionValue turns them back on. In Runtime2, and in every reference resolver, an argumentless field already in an ancestor’s output is passive, and its own resolver runs only where that output omits it. Whatever the schedule, the result is the same, and the tests hold both families to correctResolution. The same holds in the main engine, where the order of tasks may vary but the result doesn’t.

Remove a freeze

One reference resolver stops freezing its objects, and then the contract tests run. Recall that the reactor and its task classes live in resolver06, and 07 and 08 run that reactor. A contract test is a shared test interface in src/test/kotlin/…/contract. Each reference resolver has a ResolverContractTest, as does the main engine, and each mixes in contracts from that shared set, so they are all held to the same behavior. One contract, FrozenObjectResolutionContract, resolves a query and then expects reserving a new cell on any finished object to fail. Here, resolver06’s freeze() call is commented out:

# resolver06/DepthFirstOrchestrationTask.kt, line 130
- target.freeze()
+ // target.freeze()

# then run ResolverContractTest for
# resolver06, resolver08 and resolver21

Which contract tests fail?

Resolver06 and 08 fail the frozen-object contract, because a late reservation now succeeds (contract). 08 is caught too, because it runs resolver06’s reactor (resolver08), which queues resolver06’s orchestrator task (reactor). Resolver21 passes, because it shares the main engine’s freeze (base, resolver21).
