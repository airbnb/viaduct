Deep dive

Type hierarchies

Each of Runtime2’s actors is backed by a family of Kotlin types. This page covers them in roughly the order a request reaches them, and explains why each one has its shape.

Runtime2 builds each response as a tree of object engine results (OERs), one per object. An OER maps the object’s fields to slots that fill in as values arrive. Today’s engine has an ObjectEngineResult in the same role; Runtime2’s is a separate type with the same name.

Runtime2 is easiest to explain with a small set of actors: orchestrators, resolver tasks, the result tree, the registry. In the code, those actors and the data they pass around fall into families of Kotlin types, with sealed interfaces, private implementations and names that nearly repeat.

An orchestrator is a one-shot task that plans one object in the response. It works out every field the object must hold, including the inputs its resolvers read, and for each field whose resolver must run it reserves a slot and dispatches a resolver task. It never calls tenant code. A resolver task runs one field’s resolver: it reads the resolver’s inputs, calls it and fills the field’s slot. Before filling it, the task runs passive descent: it walks the returned value, fills each passive field (one whose value the output already holds) from that value, and gives each object it meets an OER and an orchestrator. The result tree is the tree of OERs, the response under construction. The registry maps each field to its resolver and checkers.

Each shape has a reason, and this deep dive explains them. It starts with the big map and how long each thing lives, then takes the families one at a time.

The examples use one query. It asks for a booking’s customer, its ten most recent messages under an alias, and its unread count over the last 50 messages, so it includes a list, arguments, a variable in unreadCount’s inputs and a field with both a resolver and a checker:

# schema
interface Node {
  id: ID!
}

type Query {
  booking(id: ID!): Booking @resolver(isSelective: true)
}

type Mutation {
  markRead(id: ID!): Message @resolver
}

type Booking implements Node {
  id: ID!
  customerId: ID
  customer: User
    @resolver(objectValueFragment: "customerId")
    @fieldChecker(objectValueFragment: "customerId")
  messages(last: Int): [Message] @resolver
  unreadCount(window: Int = 20): Int
    @resolver(
      objectValueFragment: "messages(last: $n) { read }"
      variables: [{name: "n", fromArgument: "window"}]
    )
}

type User {
  id: ID!
  firstName: String
}

type Message {
  id: ID!
  body: String
  read: Boolean
}
# query
query {
  booking(id: "b1") {
    customer {
      firstName
    }
    recent: messages(last: 10) {
      body
    }
    unreadCount(window: 50)
  }
}

In this schema, objectValueFragment and variables inside @resolver(...) are shorthand for what each field’s @Resolver class declares. objectValueFragment is the resolver’s required selection set (RSS), and variables is the annotation’s variables parameter, which here binds $n to the window argument (@Resolver). Public Viaduct’s @resolver directive takes only isSelective and isBatching (directive definition). @fieldChecker(...) is shorthand too, for a field checker with that RSS. Public Viaduct has no such directive: a CheckerExecutorFactory turns schema directives, such as a policy-check directive, into checkers, each with its own RSS (registration · checker RSS).

Everything here describes a query unless a paragraph says otherwise; mutation-only types appear in a few spots, each with Mutation in its name. The other deep dives cover mutations and the rest.

How it all connects

Every object in the response goes through the same four steps, and each pass builds that object’s OER:

  1. Creating the object’s orchestrator runs closure, which grows the object’s demand (what must be built) with the inputs the registry says its resolvers read. It also reserves a cell for each field that consumers read through access checks.
  2. Whoever created the orchestrator, usually the parent field’s resolver task, copies the passive fields from the parent resolver’s output into their cells, then dispatches the orchestrator.
  3. Once dispatched, the orchestrator claims the cell of each active field, which makes that field’s resolver task the cell’s one writer.
  4. It dispatches those resolver tasks and the object’s checker tasks (dispatch), then freezes the OER, without waiting for any value.

Fields read only without access checks, such as a field that only a checker reads, aren’t reserved up front. They get cells only when a writer comes: an active field when the orchestrator claims its cell for the resolver task, and a passive field when its parent copies the value in. So every demanded field that has a resolver or appears in the parent’s output has a cell before the freeze. Later reads, such as a checker reading its inputs, also reserve, but after the freeze a reserve only finds existing cells, and a key with no cell is an error. A reserved cell that nobody filled or claimed, such as a checked field that the parent’s output omits and that has no resolver, fails at the freeze with “Missing engine-result cell”: an error, not a hang.

When a task returns an object, that object gets its own pass. The root Query’s pass dispatches booking. The Booking’s pass dispatches customer, unreadCount and two messages cells, one for the query’s recent messages and one for the messages that unreadCount reads. Assume the booking resolver returns the Booking with its customerId, the customer resolver returns the User with its firstName, and the messages resolver returns each Message with its body and read. Those fields are then passive, so the User’s and each Message’s passes have nothing to dispatch.

One more name matters on this page: the associated Query OER. Each orchestrator creates a fresh one, separate from the operation’s root Query OER, and the Query-rooted inputs of this object’s resolvers and checkers get built there. Runtime2 identifies work by where it sits in the result tree, so these inputs belong to this object rather than to the operation’s root, and resolvers in this scope that ask for the same Query field with the same arguments share one result (occurrence identity). Its fields don’t come from any parent’s output, so none are passive: every demanded field on it is active and gets its own resolver task.

Sharing stops at the object. If each of 100 Messages had a resolver whose Query RSS read viewer, each Message’s orchestrator would create its own associated Query OER, and the viewer resolver would run 100 times. Each of those Query OERs is a separate root, an object result that paths start from. Other roots include the operation’s own Query or Mutation OER and the fresh result of a nested ctx.query() or ctx.mutation(), and root-field references get roots of their own, explained under Arguments (roots). The repeat is by design: Runtime2 doesn’t memoize declared Query work across roots. The design notes (Runtime2’s design docs in its source tree) treat caching, batching and deduplication as separate layers that must not change what counts as one occurrence, and Runtime2 doesn’t batch dispatch yet. Until it does, bootstrap rejects ENGINE2_BATCHING, the flag reserved for turning on batched dispatch under Runtime2 (flag · check). Bootstrap also refuses any field or node resolver whose executor reports isBatching, as a tenant batch resolver’s does, so a schema with batch resolvers can’t run on Runtime2 yet (refusal · batch resolver).

In today’s engine, in a query operation, a resolver’s Query RSS runs against the operation’s own root result: createQueryEngineResult reuses the root, and a resolver’s Query RSS plan targets that result, so Query work can be reused across objects.

Every demand, from the decoded operation to construction demand and successor demand, is a selection forest.

Demand sets which cells exist, promises say when their values are ready, and checks control who may read them.

Where in code: OrchestrationTask.create · FieldResolutionLogic.publishResult

What lives how long?

The registry serves every request. A firstName cell belongs to one User in one response. Runtime2’s state falls into three such lifespans: per schema, per request and per object occurrence, which is one position in the result tree.

The per-schema bundle is the world, and the per-request bundle is the operation context. Everything short-lived reads the same long-lived registry.

Where in code: Assumptions · QPlanExecutionStrategy.execute · resolvePassiveObjectValues

Seven families and their shared conventions

The seven families are results, keys, cells and promises, tasks, selections, the registry and arguments. Orchestrators and resolver tasks are tasks; the result tree is built from results, keys, cells and promises; the registry is its own family; and selections and arguments describe the demand and the inputs that resolvers are called with. Before the families, two conventions explain most of what you’ll see. First, most trees below are a sealed interface over a private …Impl class. The design notes ask this of Runtime2’s public types: the implementation stays private, and no code outside Runtime2 can add a variant. Interfaces that code outside Runtime2 may implement, such as the schema’s type definitions and the ResolverRegistry interface, follow their owning libraries’ rules instead (model.md). The task classes are ordinary classes because they are internal, not public.

Second, each public type has exactly one equality mode. It decides what you may compare, hash or use as a map key:

  • Structural: equal when the parts are equal. Keys and arguments work this way.
  • Reference: equal only to itself. Cells and OERs work this way, because their promises fill over time.
  • Schema-canonical: for schema definitions, such as the ViaductSchema.Field for Booking.customer. Two definitions may be compared only when they come from the same canonical schema; comparing definitions from two different schemas has no defined meaning.
  • Undefined: equality has no meaning. Selections, resolvers and Assumptions, the class that holds the per-schema world, are like this.

Results: a union, not a class tree

What can a cell hold? Whatever its field produces: a string for firstName, the Booking OER for booking, a list for messages, or an error in customer if the customer resolver threw. Those have nothing in common as Kotlin classes. So an engine result is a union checked at runtime, not a class tree. In the design notes’ words, it’s “a carrier representation for a mathematical domain, not a claim that the domain is untyped.”

In today’s engine a cell’s raw-value slot holds a FieldResolutionResult whose engineResult is also Any?: an OER for an object field, a list of item cells for a list field, otherwise a Kotlin scalar or enum value (fetch). Its errors sit beside the value in an errors list. In Runtime2 a field error is the cell’s value.

  • ListEngineResult

Three more sealed-interface members are leaves: IDEngineResult for GraphQL IDs (EngineResult.kt), JSONEngineResult for JSON (JSONEngineResult.kt) and BackingDataEngineResult for opaque backing data (BackingDataEngineResult.kt). Each sealed interface here hides a private implementation class. OERs share one implementation class, ObjectResultImpl. It has a mutation subclass, MutationObjectEngineResultImpl, which also implements MutationObjectEngineResult.

Keys: how much is known about a field coordinate?

How does a reader find customer’s cell on the Booking OER? By its key, a field coordinate: a field plus its arguments, with no alias. Runtime2 learns more about a coordinate as a request goes on, and each key type records how much it knows. In particular, a key can name its cell before its arguments are settled.

In today’s engine an ObjectEngineResult.Key holds the field name, the alias and the coerced argument values, and the alias is part of its equality. Runtime2’s keys leave the alias out, except for mutation keys.

An @parent field lets a child’s resolver read the object that contains it. Suppose User also had these two fields, and the query selected greeting:

booking: Booking @parent
greeting: String @resolver(objectValueFragment: "booking { id }")

The User’s booking cell holds the Booking OER. The selection booking { id } creates parent demand for the Booking’s id. Closure lifts it into the Booking’s construction demand, and successor demand lifts it onto the resolver of Query.booking, which produces the Booking. Both lifts are static: they read the query’s selections under the Booking, down to greeting, and the registered input of greeting’s resolver. So the Booking’s closure adds id before it freezes, while the User doesn’t exist yet.

In today’s engine @parent fields exist too: FieldResolver fetches one with fetchParentField instead of calling a resolver.

Cells and promises: write-once slots

A cell has to meet two needs: a reader may need it before its writer even exists, yet exactly one writer must own it. So each part of a cell is write-once, and the value promise is reservable.

Four verbs describe its value’s life:

  • To reserve a cell is to create it with an unclaimed value promise, so readers can wait before any writer exists.
  • To claim a reserved value promise is to make one writer responsible for completing it. Registering that writer with the cycle checker is a separate step.
  • To complete a claimed value promise is to write its value, once. set() claims and completes in one call, which is how passive descent fills a passive field’s reserved cell.
  • To freeze, which acts on a whole OER, is to seal its key set and fail every unclaimed reservation. Claimed promises can still complete.

In the example, the Booking orchestrator reserves and claims customer’s cell and registers customer’s resolver task with the cycle checker as its writer, all before it dispatches that task.

In today’s engine a Cell is a fixed array of slots, a raw-value slot and an access-check slot. One computeIfAbsent call sets every slot, and a later writer does nothing. Runtime2 gives each part its own write-once promise, adds an include-or-skip decision, and names the value promise’s one writer when it is claimed.

The cell

  • EngineResultCell
    Cell: an activation decision, a value promise and the field-check slot, implemented by a private class. EngineResult.kt

Every cell has the same three parts: an activation decision (include or skip), a value promise, and a field-check slot (fieldCheckerResult) that holds its access check’s checker result. A skipped cell counts as absent: awaiting its value throws. customerId and customer look exactly alike. What differs is who completes value, and when: the booking resolver’s task fills customerId from that resolver’s output, while customer’s own resolver task fills customer. The interface below highlights the three parts.

Promises

  • Promise
    Write-once value. Promise.kt
    • ReservablePromise
      Adds claim, set and freeze. Promise.kt

Private classes do the work behind these two interfaces. The plain promise is a small state machine that lets readers arrive early and wait. The reservable promise wraps one and adds the rules for its single writer. A cell’s value promise fails only when no value can come: its reservation was frozen without a writer, or its task was cancelled. A resolver that throws still completes the value, with an ErrorEngineResult.

One more layer sits on top. A cell wraps its two promises so they respect activation, using ActivationAwarePromise for the field-check slot and ActivationAwareReservablePromise for the value.

Tasks: two parallel chains

Now the actors themselves. Each object occurrence gets one orchestrator, and each cell of an active field gets one resolver task. The root Query’s orchestrator dispatches booking’s resolver task. The Booking’s orchestrator dispatches four resolver tasks, for customer, unreadCount and the two messages cells, plus a checker task for customer. The User and Message orchestrators dispatch none.

Both kinds sit at the bottom of a short chain: a shared contract, then a coroutine base, then the concrete class. Hollow arrowheads mean “extends or implements”. Which tasks stay outside both chains?

Selections: two families

Outside mutations, cells are keyed without aliases, so the query’s recent alias isn’t part of its messages cell’s key. Yet a resolver’s input must show the response keys the tenant wrote. Runtime2 solves this with two separate families of selections, one that drops aliases and one that keeps them, and neither extends the other.

Inclusion conditions

Every selection also carries an inclusion condition, the symbolic form of its @skip and @include. It’s an immutable directed acyclic graph (DAG) built from Always, Never and Requires, joined by internal Conjunction and Disjunction nodes. The @skip and @include deep dive shows how they’re decided.

  • InclusionCondition
    Inclusion condition for one selection occurrence. InclusionCondition.kt
    • Always
      Nested subtype of InclusionCondition; always included.
    • Never
      Nested subtype of InclusionCondition; never included.
    • Requires
      Nested subtype of InclusionCondition; included when each listed variable has its required Boolean value.

The internal Conjunction and Disjunction classes, declared at top level, join these into larger conditions.

Registry: targets, resolvers, variables

Runtime2 calls checkers resolvers too, as in the class names FieldCheckerResolver and TypeCheckerResolver. Booking.customer has both a resolver and a field checker, and each could declare its own fragments and variables. So a bare schema field can’t identify “the” resolver. Instead, each resolver is owned by an explicit resolver target, the slot that owns a resolver and its variables, and there are three kinds: field value, field checker and type checker. In the design notes’ words, “A field-value target and field-checker target for the same schema coordinate identify different resolver slots.”

In today’s engine DispatcherRegistry keeps field resolvers and field checkers in separate maps keyed by the same type-and-field coordinate, with more maps for node resolvers and type checkers. Runtime2’s registry keeps a separate lookup per kind too, and each resolver carries a target that names its slot.

In the example, the customer resolver sits in the field-value slot of Booking.customer and its checker in the field-checker slot. Each declares customerId as its object fragment:

customer: User
  @resolver(objectValueFragment: "customerId")
  @fieldChecker(objectValueFragment: "customerId")

A FieldValueResolver wraps one of two function types, and it has a factory function for each: FieldValueResolver.of takes a nonselective function and FieldValueResolver.ofSelective a selective one. Both take the object input, the Query input, the arguments, an application value (data that the parent object’s data carries to child resolvers without exposing it as a GraphQL field) and an execution context (function type · application value). The function of a selective resolver, a selective function, also takes the field’s successor demand, and a returned field outside that demand is an error (see Selectivity). Today’s FieldResolverExecutor.isSelective marks the same kind of resolver.

      Field-value slot, for the resolver that computes the field’s raw value; a FieldTarget.

Variables: declared, then compiled

A resolver’s variables start as declarations. Registry assembly compiles each one into a canonical definition. Two names appear on both sides, so keep the sides apart: declarations are classes in the registry package, and definitions nest inside VariableDefinition.

In today’s engine FieldResolverExecutor lists a resolver’s variables by source: argumentVariables, objectFieldVariables, queryFieldVariables and variablesFromFunctionProvider. Runtime2 merges the object-field and Query-field sources into one FromField form.

Arguments: open, ground, template

Arguments split the way keys do. A tuple is open while it holds variable instances, variables already tied to one resolver occurrence (defined below); there is no Open type, so an open tuple is an Arguments that is neither Ground nor Template. It is ground once its variables are resolved, when it is either Resolved or a tuple-level Error. A third form, the registry template, holds variables not yet tied to an occurrence.

One rule matters most: “Equality and hashing never inspect a variable’s eventual binding”. That’s why the messages(last: $n) cell from unreadCount’s fragment keeps its identity when $n is bound to 50.

The rule has a cost. If the query also asked for messages(last: 50), that ground key and the symbolic messages(last: $n) key would still differ, so the Booking would hold two messages cells and call the messages resolver twice with equal arguments. The design notes accept this so that closure can name cells before bindings exist. The alternatives were to wait for every binding, which needs cycle rules strong enough to rule out deadlock, or to widen demand for keys that might merge later, which makes the work depend on timing.

Three related terms:

  • A template holds registry-side arguments whose variables aren’t yet tied to an occurrence, such as last: $n in unreadCount’s registered fragment.
  • A variable instance is a template variable tied to one resolver occurrence by its VariableInstanceId, such as $n for unreadCount on booking b1.
  • A resolver occurrence ID (ResolverOccurrenceId) is a root plus a path that identifies one resolver call. The resolver’s fragments and variables are instantiated from it.

The root matters for node references. A resolver can return one in place of an object: an instruction to resolve a Query field such as Query.node.

  • What a hop is. Resolving a node reference calls that Query field’s resolver, and each such call is a hop (see Nested inputs and node references). The value goes back to the task that made the hop. That task calls every hop’s resolver before passive descent, so its cell completes, and the returned object’s orchestrator starts, only after the last hop returns.
  • What root it gets. A hop’s resolver occurrence ID uses a fresh, empty Query OER, the invocation root, and a path to node (source). That root is immutable: it stores nothing and can’t gain cells. It gives the hop its own identity, so the target’s fragments and variables are instantiated for that call alone.
  • Where its Query fragment is built. The invocation root is only an identity witness, not a Query-fragment root. It can’t gain cells, so it can’t hold the cells a Query fragment needs. A target’s Query fragment is built in another fresh Query OER with its own orchestrator.
In today’s engine a returned node reference gets a pending OER in place, holding data already known such as the node ID, and the node resolver runs in parallel with that object’s field resolvers. In Runtime2 the object’s orchestrator, and so its field resolvers, start only after the last hop returns.
  • Arguments
    Argument tuple for an output field. Arguments.kt
    • Ground
      Nested subtype of Arguments; no variables left.
      • Resolved
        Nested in Arguments, subtype of Ground; every value resolved.
      • Error
        Nested in Arguments, subtype of Ground; the whole tuple is an error. Arguments.kt
    • Template
      Nested subtype of Arguments; registry template. Arguments.kt
  • Arguments.Variable
    Nested in Arguments; not a subtype. Arguments.kt

Arguments, Resolved and Template are backed by private implementation classes, such as ArgumentsImpl. Ground only groups Resolved and Error, and Error is a single data object. A variable is either a template variable or an instance variable, and the instance variable class, InstanceVariableImpl, carries its VariableInstanceId.

Looking back

Seen from the code, the engine still works the way its actors suggest. The registry lives for the schema, the operation context for the request, and cells and tasks for one occurrence. Results are a checked union, and keys sharpen from open to ground. Each part of a cell is written once, and each value promise is claimed by one writer. Selections and materialize selections stay apart, and targets own resolvers and their variables. Every actor in a request is one of these families at work.
