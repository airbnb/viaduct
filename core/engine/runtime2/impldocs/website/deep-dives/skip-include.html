Deep dive

@skip and @include

How @skip and @include turn into inclusion conditions, and why a skipped resolver field in a query still gets a task, one that stops before the resolver runs.

A client can ask for a field only sometimes, with @skip or @include and a variable. A skipped field never reaches the response, but how much work does Runtime2 do for it first?

There is a harder case, too: a resolver’s own declared input can carry a condition on a resolver variable, one the resolver defines for its own inputs, rather than an operation variable the client sends. Its value may stay unknown until the request is running.

The fragment case also touches variables and bindings, which Arguments and aliases covers in depth.

What if a field sits behind @skip or @include?

Runtime2 holds each object it builds in an object engine result (OER), like today’s ObjectEngineResult, with one cell per field. Normally, a field with a resolver gets a resolver task that owns the field’s cell. The task’s first decision is the cell’s activation, a write-once include-or-skip decision that comes from the field’s inclusion condition. The inclusion condition is the symbolic form of the field’s @skip and @include: Always, Never, or Requires when it depends on a resolver or checker variable.

The examples use one schema. A venue has an owner, and the owner’s venues and blurb fields have resolvers. In it, objectValueFragment inside @resolver(...) is shorthand for the required selection set (RSS) that the field’s @Resolver class declares in Kotlin. Public Viaduct’s @resolver directive takes only isSelective and isBatching (schema reference).

Conditions come from two places, and the client’s own are the simpler case. This query includes the owner’s venues only if the operation variable $v is true, and the client sends false:

# example schema
type Query {
  venue(id: ID!): Venue @resolver
}

type Venue {
  id: ID!
  title: String
  owner: User @resolver
}

type User {
  id: ID!
  firstName: String
  venues: [Venue]
    @resolver(objectValueFragment: "id")
  blurb: String
    @resolver(
      objectValueFragment:
        "venues @include(if: $withVenues) { title }"
    )
    # $withVenues from a variables provider
}
# query
query($v: Boolean!) {
  venue(id: "V1") {
    owner {
      firstName
      venues @include(if: $v) {
        title
      }
    }
  }
}
# variables: { "v": false }

Runtime2 gets the operation already parsed and validated, and decodes it into its own selections. The operation variables are coerced by then, so decoding decides every client condition, literal or variable: each selection gets Always or Never. With $v false, venues is Never.

In a query, a Never resolver field still gets a task. Runtime2 doesn’t special-case it: closure keeps every selected resolver field, and the field’s resolver task is the one writer of its cell’s activation. A Never field takes the same path as a Requires field whose variable turns out false; its task just knows the answer at once. So both share one code path, at the cost of one short task per skipped resolver field, which calls no tenant code (closure).

In today’s engine Today’s engine also evaluates @skip and @include with the coerced variables, but while it collects fields. A skipped field is dropped there, so it gets no resolver call and nothing else is scheduled for it. CollectFields

Mutations differ. A mutation’s root fields go to the mutation orchestrator, which runs only the fields in its ordered list. Its conditions are all decided at decoding, so only Always fields enter that list, and a Never mutation field gets no cell and no task at all (MutationSelections).

The harder case is a condition inside a resolver’s own fragment, whose variable may stay unknown until the request is running. In the schema above, User.blurb’s resolver includes venues only if its resolver variable $withVenues is true. blurb’s variables provider, a function that computes its resolver variables, supplies that value.

The guard on venues carries over to what venues needs. Closure adds its resolver’s declared input, id, to the User’s demand with the same condition, and it would add a field checker on venues the same way. Demand that carries a condition like this is guarded demand (closure). Every task it leads to waits for $withVenues, like the venues resolver task. If the value is false, none of them does any work: a resolver among the inputs is never called, and the checker never runs (resolver task, checker task).

blurb’s resolver task calls the provider right after blurb activates, before it reads its inputs. If $withVenues is false, blurb’s resolver gets an input without venues: a selection whose condition is false is dropped before the input is built (resolver input · fetchIncluded). If the client also selected venues itself, the two selections would combine with OR, so venues would run whatever $withVenues is.

In today’s engine Today’s engine runs blurb’s RSS as a child query plan. It first resolves that plan’s variables, calling blurb’s variables provider, and then runs the plan with them, so venues is collected or dropped like any other field (FieldResolver).

Where in code: decodeCondition · fragment conditions · activation

So in a query, a condition never removes a resolver field’s cell or task; sometimes the task’s only job is to mark the cell skipped.

Try it

@skip on a resolver field

# schema
type Query {
  venue(id: ID!): Venue @resolver
}
# query
query($s: Boolean!) {
  venue(id: "V1") @skip(if: $s) {
    title
  }
}
# variables: $s = true

Is a task created? Does tenant code run?

In a query, decoding keeps the field and makes its inclusion condition Never (parser). A Never field adds no inputs, so closure adds nothing for it (closure). Its task still starts, sets the cell’s activation to skip and returns before tenant code (task).

What about the same @skip(if: true) on a mutation field?

It’s dropped. The mutation orchestrator runs only the fields in its ordered list, and only Always fields enter it (source).
