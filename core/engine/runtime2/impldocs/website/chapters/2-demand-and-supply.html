Chapter 2

Demand and supply

In the running example, every value comes from one of two places: a parent resolver’s output, or a resolver task of its own.

Chapter 1 ended with three choices unexplained: title needed no task, location got one, and lat and lng joined although the client never asked for them. This chapter gives the rules behind them.

The rules are about demand, which is what each object engine result (OER) must build. Orchestrators and resolver tasks pass it down the tree as they hand off. They are also about supply, which is where each demanded value comes from. At each OER, every demanded field is either passive, its value coming from data already resolved, the parent resolver’s output, or active: it has its own field resolver, which runs in a resolver task whose cell the orchestrator claims. That split decides when work is created and what each resolver is asked for, and it explains why one call per occurrence is enough.

Demand is a selection forest (SelectionForest), unordered except in mutations. Each selection also carries an inclusion condition that records any @skip or @include. The decoded query, the inputs that closure adds and what a resolver is asked for are all selection forests.

The running example’s schema and query are on the overview page. Each resolver reads, is asked for and returns:

# what each resolver reads, is asked for and returns
# Venue node resolver (Query.venue)
reads:      the ID "V1", taken from venue(id:)
asked for:  title lat lng location { displayName city country }
returns:    { title: "Loft", lat: 48.86, lng: 2.35 }

# location’s resolver (Venue.location)
reads:      lat 48.86, lng 2.35 from the Venue
asked for:  displayName city country
returns:    { city: "Paris", country: "France" }

# displayName’s resolver (Location.displayName)
reads:      city "Paris", country "France" from the Location
returns:    "Paris, France"

Demand flows down the result tree

The client writes all its demand at once, at the top of the query. Each OER needs only the part below the field that produced it, so the query’s demand moves down the tree one level each time a resolver returns.

Every demand has two parts, and the engine must produce the values in both. Reads of checked demand apply access checks, while unchecked demand is read raw.

Supply: passive fields and active fields

Once demand reaches an object, each demanded field must be supplied with a value, and supply has only two sources: the parent resolver’s output, or a resolver task of its own. A field already in the output is passive: passive descent fills its cell from that output. A missing field with a resolver is active, so its resolver must run, while a field with no resolver can only come from the parent’s output, and leaving it out is an error. The root Query object starts with no value at all, so every demanded root field, such as venue, is active.

In the running example, Location is not a Node and has no ID, so location’s resolver computes it by reverse-geocoding the venue’s coordinates, lat and lng.

location takes no arguments, so if venue’s output had contained location, location would be passive at this occurrence and its resolver wouldn’t run. Only argumentless fields can be passive: if a resolver’s output includes a field that takes arguments, Runtime2 rejects that output, so a field that takes arguments is never passive.

In today’s engine Today, location’s resolver runs whenever location is selected, even if venue’s output already holds location. The one exception is a venue value marked as parent-managed (ParentManagedValue), which skips the registered resolvers below it until a nested StandardResolutionValue turns them back on. In Runtime2 an argumentless location already in venue’s output is passive, and its resolver does not run. ParentManagedValue

Closure: demand the client never wrote

The client never asked for lat or lng, but location’s resolver reads them. Before the Venue orchestrator creates any resolver task, it must know every value those tasks will read; otherwise a task could wait on a cell with no writer.

So it runs closure, which works in passes. The first pass looks at the demand the object received, and each later pass looks only at what the pass before it added. Each pass adds the declared inputs of whatever will run, and closure stops after a pass that adds nothing new. So the Venue example takes two passes, the second adding nothing. The result is the object’s construction demand, the demand the object received plus what closure added.

In today’s engine Today, location’s inputs (its RSS, lat and lng) are planned ahead of time, as a child plan of location in the query plan, but FieldResolver launches that plan only when location itself starts fetching. In Runtime2 the Venue node resolver is asked for lat and lng along with title, because location declares them as input, so they are fetched like requested fields. launchFieldChildPlans

A resolver’s Query fragment needs a Query object to be read from, so every orchestrator also creates its associated Query OER: a fresh, empty Query OER beside its object, where the Query-rooted inputs of that object’s resolvers and checkers are built. The root Query orchestrator creates one too, a second Query OER beside the root, so the root’s Query-rooted inputs aren’t built in the root OER itself (every create). An associated Query OER gets no orchestrator of its own: the orchestrator that created it plans it beside its object (OrchestrationTask). Closure closes that Query OER’s demand too. In the running example no resolver reads Query, so each of these Query OERs stays empty, and the diagrams leave them out.

In today’s engine Every Query-rooted input in a query is read from the request’s one Query OER, the root itself. In code, each queryValueFragment reads that root. In Runtime2 each orchestrator builds its own fresh Query OER, so the Query inputs of one object’s resolvers are not shared with other objects. createQueryEngineResult

That has a cost. A Query-rooted input is built once for each object that reads it, not once per request: if two objects each have a checker that reads the same Query field, that field’s resolver runs twice, once in each object’s Query OER (Demand closure: inputs, example 4a). Runtime2’s design accepts it on purpose. The identity of a piece of work is its place in the result tree, a root OER plus a path, so equal fields on different roots are never merged. Sharing work across objects is left to caching and batching layers, which Runtime2 doesn’t have yet (Runtime2 design principles · one Query OER per orchestrator).

Input demand vs successor demand

Closure tells an object what it must contain. A resolver task needs two narrower answers: what its resolver reads, and what the resolver should be asked to produce. So the location resolver task holds two demands. Its input demand is what its resolver reads in order to run. Its successor demand is what the resolver is asked to produce, so that everything below it can run.

Successor demand is worked out before the resolver runs, so nobody yet knows which fields below will be active. It assumes every resolver below may run and includes all their inputs, at every level below, including the inputs that those inputs need in turn: the Venue node resolver is asked for lat and lng, even though it could return location itself, which would make location passive and its resolver unnecessary. Closure is the exact version. It runs after the resolver returns, looks at the returned value, and adds only the inputs of resolvers that will actually run.

What may the resolver send back? Runtime2’s main engine requires its selective policy on, so every resolver’s output is held to its successor demand. The policy is one setting for the whole schema; whether a single resolver is selective is set for its field, in the schema or by the service. A selective resolver may return only fields within its demand, and returning a field nobody asked for is an error. A non-selective resolver may return more, and Runtime2 first trims that output to the demand (see Selectivity).

In today’s engine Today, a non-selective resolver must return its whole output selection set, the fields below it that no other resolver owns, and a value it returns for a field another resolver owns is ignored. A selective resolver may also return unselected fields that it owns, and Viaduct records them for later use. Viaduct docs: selective resolution
In today’s engine Today, location’s resolver gets lat and lng once the engine has waited for the lat and lng cells in the Venue OER, and reads them as ctx.objectValue, built from the Venue’s ObjectEngineResult. Runtime2 builds location’s input from those cells the same way, and also tells the cycle checker that location’s resolver task read lat and lng. ResolverDataFetcher

Demand flows down, and closure adds what resolvers and checkers will read. Each field is either passive, resolved from its parent’s output, or active, claimed for a resolver task of its own.
