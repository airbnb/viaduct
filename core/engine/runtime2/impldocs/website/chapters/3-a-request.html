Chapter 3

A request, end to end

One query from parsing to response: demand descends, tasks are dispatched and cells fill, and completion reads them out.

Chapters 1 and 2 looked at the engine one object at a time. In a real request the steps overlap: completion reads cells while resolver tasks are still running, and a dispatched task may run while the task that dispatched it keeps going.

This chapter replays the running query through all three resolvers, in the order the code runs it and with the overlaps the code allows. It answers the question the earlier chapters set aside: when does each thing happen?

The example: a venue and its location

Three fields have resolvers: Query.venue, Venue.location and Location.displayName. Venue implements Node, and as in the overview, this tour treats the resolver behind Query.venue as the Venue node resolver. All three are declared selective, with isSelective: true in the schema, so each returns only what it’s asked for (chapter 2). Every other field has no resolver, so it can only be a passive field, passively resolved from the output of the resolver above it.

Location is not a Node and has no ID. Its resolver builds it by reverse-geocoding the venue’s coordinates, which it reads from the lat and lng fields of the Venue.

# what each resolver reads, is asked for and returns
# Venue node resolver (Query.venue)
reads:      the ID "V1", taken from venue(id:)
asked for:  title lat lng location { displayName city country }
returns:    { title: "Loft", lat: 48.86, lng: 2.35 }

# location’s resolver (Venue.location)
reads:      lat 48.86, lng 2.35 from the Venue
asked for:  displayName city country
returns:    { city: "Paris", country: "France" }

# displayName’s resolver (Location.displayName)
reads:      city "Paris", country "France" from the Location
returns:    "Paris, France"

How does one query become a response?

Here is the whole request laid out in time, with completion, the result tree and the tasks side by side. There is one orchestrator per object engine result (OER) in the response and one resolver task per active field, and each one does the steps from chapter 1.

What’s new is the timing. Completion starts reading as soon as resolution starts, so it reads cells while the tasks below them are still running, and it waits only on cells that are still pending.

# the running query
query {
  venue(id: "V1") {
    title
    location {
      displayName
    }
  }
}
In today’s engine Today, location’s resolver is called through a loader shared by the whole request, a request-wide FieldDataLoader, so a batch resolver can resolve several locations in one call. Node resolvers share a request-wide NodeDataLoader, which also caches results unless caching is turned off. Runtime2 gives every call a fresh loader that calls its resolver at once, even a batch resolver, so it has no batching or caching across calls yet. The code calls this a transitional policy. fieldDataLoader · NodeDataLoader · fresh loader · Runtime2DispatchStrategy

Where in code: OrchestrationTask · FieldResolverTask · FieldResolutionLogic · SharedPassiveValueResolutionLogic · CoroutineTaskDispatcher · QPlanWiringFactory

A resolver task completes its own cell last, only after any child object it built has dispatched its tasks and frozen.

What just happened

Three orchestrators, one for each of the Query, Venue and Location OERs, ran closure, claimed cells, dispatched resolver tasks and froze. Three resolver tasks each called their resolver once. Completion only read cells: complete ones right away, pending ones once they completed.

In short, Runtime2 plans each object before anything below it runs and calls each resolver once per occurrence, while readers wait on cells rather than on each other.

The running query is a simple case: venue and location each returned a single object, not a list or a reference to one. Two deep dives go further: Nested inputs and node references covers lists and node references, and Into the code finds this trace in the source.
