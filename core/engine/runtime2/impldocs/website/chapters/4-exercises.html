Exercises

Six short exercises on the running example and a few small schemas. Every answer follows from chapters 1 to 3.

Chapter 3 traced the whole request; in this chapter you make the predictions. First, predict what the rules from chapters 1 and 2 say about a few small cases. Then take the running example and make the engine’s decisions yourself, one at a time.

Before the request runs

These exercises cover planning. Given a schema and a query, work out what the engine will ask for and which fields will need a resolver of their own. They are mostly about what is asked for, and only briefly about what runs when.

What does greeting pull in?

Here one resolver reads another resolver’s output.

# schema
# objectValueFragment is shorthand for the resolver’s inputs
type Query {
  user: User @resolver
    # returns { first, last }
}

type User {
  first: String
  last: String
  display: String
    @resolver(objectValueFragment: "first last")
  greeting: String
    @resolver(objectValueFragment: "display")
}
# query
{
  user {
    greeting
  }
}

After closure, what is the construction demand of User’s object engine result (OER)?

All four fields: greeting, display, first and last. greeting’s resolver reads display, and display’s resolver reads first and last, so closure adds both layers. See the design notes.

How many passes does closure make?

Three. Pass 1 adds display, pass 2 adds first and last, and pass 3 adds nothing, which is the fixed point. See where the loop stops.

Suppose user also returned display (display is in user’s successor demand, so returning it is allowed). What happens to display’s resolver?

display is now a passive field, so closure skips it: its resolver doesn’t run, so closure never adds first and last on its behalf. See the rule in code.

Which fields are passive, and which are active?

This exercise uses the running example, with what each resolver returns. Location is not a Node and has no ID: location’s resolver computes it by reverse-geocoding the venue’s coordinates.

# schema
type Query {
  venue(id: ID!): Venue @resolver(isSelective: true)
    # returns { title, lat, lng }
}

type Venue implements Node {
  id: ID!
  title: String
  lat: Float
  lng: Float
  description: String
  location: Location
    @resolver(
      isSelective: true
      objectValueFragment: "lat lng"
    )
    # returns { city, country }
}

type Location {
  city: String
  country: String
  timezone: String
  displayName: String
    @resolver(
      isSelective: true
      objectValueFragment: "city country"
    )
}
# query
query {
  venue(id: "V1") {
    title
    location {
      displayName
    }
  }
}

Which fields come from their parent’s output, and which need a resolver task of their own?

Passive: from the parent’s output

Active: needs its own resolver task

title, lat, lng, city and country arrive in their parent resolver’s output, so they are passive, and passive descent fills them. venue, location and displayName have resolvers and nobody returned them, so each one is active and needs its resolver to run: it gets a claimed cell and its own resolver task. See passive descent · see the claim.

While the request runs

Now follow the running example as it executes. Each question asks you to make one of the engine’s decisions yourself, in the order the engine makes them.

}

What is the Venue node resolver asked to produce, its successor demand?

The venue call is asked for everything the client wants below it, plus every input the resolvers below will read: location’s lat and lng, and displayName’s city and country. Nobody asks for description or timezone. See successor demand.

Who fills the title, lat and lng cells?

The venue resolver task’s passive descent. It creates the Venue orchestrator, fills title, lat and lng from the resolver’s output, and only then dispatches the orchestrator. See passive descent.

Who claims the location cell?

The Venue orchestrator’s run. It claims location’s reserved cell, registers location’s resolver task as the cell’s writer with the cycle checker, and only then dispatches the task. See the run · see the claim.

What is location’s resolver asked to produce?

The client’s displayName, plus city and country, which displayName’s resolver will read. See successor demand.

Does the location cell wait for displayName’s value?

The location cell completes once the Location OER is built and its orchestrator has run. By then displayName is already claimed and its task dispatched, but its value may still be pending. See the code · the design notes.

When can completion first read title?

As soon as the venue cell completes. Completion starts reading when resolution starts and waits only on pending cells, and title was filled before the venue cell completed. See the execution strategy.

What does location’s resolver task do, and in what order?

This exercise looks at location’s resolver task, whose steps chapter 1 walked through.

# location’s resolver task
reads:      lat 48.86, lng 2.35 from the Venue
asked for:  displayName city country
returns:    { city: "Paris", country: "France" }

Put the task’s steps in order.

  1. Compute the successor demand
  2. Decide activation (stop if skipped)
  3. Ground the arguments
  4. Read the inputs, lat and lng
  5. Call the resolver once
  6. Passive descent: build the Location
  7. Complete the location cell

Everything is gathered before the one call, and the cell completes last, once the Location OER below it is built and its orchestrator has run. See the task · the resolver call.

Now order everything from creating the Location OER to completing location’s cell.

  1. Create the Location OER
  2. Create the Location orchestrator, which runs closure
  3. Fill city and country
  4. Dispatch the Location orchestrator
  5. Complete the location cell

The Location gets its orchestrator, and with it its closed demand, before any cell is filled. Dispatch comes after filling, and the location cell completes last. See the Location created · passive descent · the cell completing.

Why isn’t greeting expanded twice?

Back to the User from the first exercise, with its closure written out pass by pass.

# closure at the User, from the first exercise
pass 1: greeting   # adds display
pass 2: display    # adds first last
pass 3: first last  # adds nothing, stop

Why doesn’t pass 2 expand greeting again?

Pass 2 looks only at display, the demand that pass 1 added; greeting was expanded in pass 1, before any task exists. Each pass expands just what is new, so pass 3 looks only at first and last, which have no resolver, and closure stops. See the closure loop.

Can a frozen object still fill a cell?

The Venue orchestrator’s run has just returned.

# the Venue OER
Venue:  frozen
location: claimed, still pending

Can location’s cell still complete?

Yes. Freezing fixes which cells Venue has and fails only the reservations that nobody claimed. location’s cell is claimed, so its task completes it later. See freeze.
