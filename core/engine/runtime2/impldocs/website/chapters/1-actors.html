Chapter 1

The actors

How the four actors hand work to each other.

This chapter zooms in on steps 4 to 8 of the overview’s diagram, where the request moves from the Query level down to the Venue level and location’s resolver runs. It then looks at the cells those steps fill and at the registry they consult. In the running query, the chapter starts where venue has its value and location is next:

# the running query
query {
  venue(id: "V1") {   # resolved: returned title, lat and lng
    title
    location {          # next: still needs its resolver
      displayName
    }
  }
}
# Venue node resolver, already called
reads:      the ID "V1", taken from venue(id:)
asked for:  title lat lng location { displayName city country }
returns:    { title: "Loft", lat: 48.86, lng: 2.35 }

Each object engine result (OER) holds one cell per field: the slot where that field’s value will be written. So far, the Query orchestrator has handed the Query OER’s venue cell to venue’s resolver task and dispatched that task, and the Venue node resolver has been called once. Below venue nothing exists yet: there is no Venue OER, and neither location’s nor displayName’s resolver has run.

Three jobs remain: build the Venue OER, recognize location as an active field, and call its resolver. The hard part is calling it exactly once: if two pieces of code both believed location was theirs, its resolver would run twice and its value would have two writers.

Runtime2 prevents that by giving each kind of work to one actor, so that each cell value has at most one writer, each occurrence of a resolver-backed field calls its resolver at most once, and each OER is planned once. An occurrence is one position in the response: in a list of venues, each element’s location is its own occurrence, with its own cell and its own call. There are four actors:

  • Orchestrator: plans one OER.
  • Resolver task: fills one cell, calling its resolver at most once.
  • Result tree: the shared workspace where tasks write and read values.
  • Registry: the static map of who produces what.

The orchestrator plans one OER

The Venue node resolver returned plain object data holding title, lat and lng. That data has no cells, so nothing else can read it or wait on it. Before anything below venue can run, it has to become a Venue OER, with a decision for each field: title, lat and lng are copied straight in, while location, which has its own resolver, needs exactly one resolver task. ResolverOutputData

The venue resolver task creates the Venue OER, plus Venue’s orchestrator, which exists only to plan this one OER and makes those decisions. The orchestrator doesn’t run on its own: the resolver task, which is still running, drives it through three steps that together make up the resolver task’s passive descent. The orchestrator does the first and the last step, and the resolver task does the middle one itself:

  1. Prepare. Creating the orchestrator runs Prepare, which works out everything Venue must contain. It checks the returned value to tell passive fields from active ones: title, lat and lng are in it, but location isn’t, so location is active and its resolver must run. Because that resolver will run, the inputs it declares, lat and lng, are added. Last, it reserves an empty cell for each field in its checked demand, the fields read through access checks.
  2. Fill. The venue resolver task sets title, lat and lng from the returned value: each cell is claimed and completed in one step, so these fields need no task. Fill has to come after Prepare, because it uses the demand that Prepare completed, and before Run, because Run’s freeze fails every cell that hasn’t been set or claimed.
  3. Run. The venue resolver task dispatches the orchestrator, which runs at once and finishes before the venue resolver task continues. Dispatching a resolver task is different: it launches the task to run concurrently. The orchestrator claims location’s cell for a new resolver task, dispatches that task, and freezes Venue so that no new cells can appear on it.

The orchestrator only plans. It never calls a resolver or checker itself and never waits on anything, so by the time the venue resolver task moves on, Venue is frozen and location’s resolver task has already been dispatched.

The resolver task fills one cell, calling its resolver at most once

The orchestrator has claimed location’s cell and dispatched a resolver task to fill it, and that task is where tenant code runs. location’s resolver task has one job: to call location’s resolver once, asking that one call for everything the fields below location will read.

Location is not a Node and has no ID, so there is nothing to look it up by. Its value comes from location’s resolver, which reverse-geocodes the venue’s coordinates, lat and lng, read from the Venue OER.

The task works through a fixed order of steps: everything is gathered before the call, and the cell is completed last, once the object below it is ready. Completing a cell means writing its value; it is separate from completion, which reads the cells to build the response.

Runtime2 also decides a client’s @skip/@include while decoding, but it keeps a skipped field in the demand, marked never-included. A skipped resolver-backed location still gets its cell and task, and the task marks the cell skipped. Conditions inside a resolver’s RSS work differently (see @skip and @include). CollectFields

The result tree is the shared workspace

The venue resolver task wrote lat and lng and the location resolver task read them, yet neither task called the other, because tasks share values through the result tree. Each OER maps keys to cells, where a key is a field plus its argument values, with no alias.

A cell holds one field’s result at one place. It has three parts, each written once: the activation decision, a value promise that readers can wait on, and a field-check slot for the access check. A cell’s value only moves forward, from reserved to claimed to completed, and freezing fixes which cells an object has.

The registry is the static map of who produces what

Closure, claims and successor demand all ask the same question: does this field have a resolver, and what does it need? The resolver registry answers it; it is built once per schema, before any request starts, and by default every request shares it. It also keeps each resolver’s inputs prepared ahead of time, so closure can reuse them instead of working them out again for every object. precomputeConstructionDemand

A resolver declares its inputs as its required selection set (RSS), which has two parts, also called resolver fragments. The object RSS (objectValueFragment) is read from the field’s parent object, and the Query RSS (queryValueFragment) is read from Query. A field with no resolver can only be passive: its parent resolver’s output is the only place its value can come from. Checkers are registered too; see Access checks.

  • The orchestrator picks which cells get a resolver task but never writes resolver values.
  • location's resolver task computes its successor demand first, calls its resolver once, and completes its cell last.
  • Each value has one known writer, and readers wait on its promise, not on another task.

This chapter took some of the actors’ choices as given: title needed no task but location did, and lat and lng joined although nobody asked for them. Chapter 2 explains the rules behind those choices: what each object must build, and where each value comes from.
