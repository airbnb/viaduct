Overview

Viaduct’s Runtime2 engine

Every Viaduct request involves the same parties. The client writes a query, and tenants write the resolvers. Tenants are the teams whose modules contribute schema and resolver code to a Viaduct service. Each resolver can declare what it needs to read through its required selection set (RSS). Somewhere in between, something has to decide which resolver produces each value, what that resolver is given, and when it runs. That something is the engine.

Runtime2 is a reimplementation of that engine. Viaduct itself stays the same, and Runtime2 implements the same engine contract as today’s engine; what changes is how the work gets done. Runtime2 is designed so that its behavior can be reasoned about precisely. Its central design choice is that it plans before it runs. Because every resolver declares its inputs up front, Runtime2 can work out in advance what each resolver call must provide.

Differences from today’s engineThe contract is the same, but some behavior differs, and the pages that cover each case say so: batching and caching across resolver calls (chapter 3), Query-rooted inputs (chapter 2), fields already in the parent’s output (chapter 2), checkers on mutation fields and types (Mutations), and selective resolvers that return extra fields (Selectivity).

The running query

Here is a venue, its location, and the location’s display name. It’s small, but it has three resolvers, and two of them need data that another one produces.

# schema
# objectValueFragment is shorthand for the resolver’s inputs
type Query {
  venue(id: ID!): Venue @resolver(isSelective: true)
}

type Venue implements Node {
  id: ID!
  title: String
  lat: Float
  lng: Float
  description: String
  location: Location
    @resolver(
      isSelective: true
      objectValueFragment: "lat lng"
    )
}

type Location {
  city: String
  country: String
  timezone: String
  displayName: String
    @resolver(
      isSelective: true
      objectValueFragment: "city country"
    )
}
# query
query {
  venue(id: "V1") {
    title
    location {
      displayName
    }
  }
}

Venue implements Node, so it has a node resolver, which loads a venue by its ID. In a real tenant, Query.venue would have its own small field resolver that returns a node reference for the ID (ctx.ref), and Runtime2 would resolve that reference through the built-in Query.node field, which calls the Venue node resolver. This tour folds those steps into one and calls the resolver behind Query.venue the Venue node resolver.

Each objectValueFragment argument lists the fields a resolver reads from its parent object, its RSS. Public Viaduct’s @resolver directive takes only isSelective and isBatching, so objectValueFragment here is shorthand for what the field’s @Resolver class declares in Kotlin. isSelective is a real argument of the directive. All three resolvers are declared selective (isSelective: true), which means each one promises to return only the fields it was asked for.

Each resolver reads its inputs, is asked for a set of fields, and returns the ones it produces. The Venue node resolver loads venue V1 by its ID. Location doesn’t implement Node and has no ID, so location’s resolver computes the location instead: it reverse-geocodes the venue’s coordinates, lat and lng. displayName’s resolver builds the name from that location’s city and country. The client never asks for lat, lng, city or country; they appear in what a resolver is asked for because a resolver below it reads them. Every chapter uses these values:

# what each resolver reads, is asked for and returns
# Venue node resolver (Query.venue)
reads:      the ID "V1", taken from venue(id:)
asked for:  title lat lng location { displayName city country }
returns:    { title: "Loft", lat: 48.86, lng: 2.35 }

# location’s resolver (Venue.location)
reads:      lat 48.86, lng 2.35 from the Venue
asked for:  displayName city country
returns:    { city: "Paris", country: "France" }

# displayName’s resolver (Location.displayName)
reads:      city "Paris", country "France" from the Location
returns:    "Paris, France"

Runtime2 arranges this chain so that each resolver is called at most once and gets what it needs.

Resolution, not completion

Executing a query splits into two jobs. Runtime2 does resolution: it obtains every value the client’s selections need and writes it into a result tree. GraphQL Java does completion: it builds the response from that tree as values arrive. Runtime2’s entry point is its execution strategy, QPlanExecutionStrategy.

In today’s engine The work is already split in two: one part fetches venue, location and displayName into result objects, and another reads them out to build the response. In code, ViaductExecutionStrategy calls ExecuteRootSelectionSet, which runs FieldResolver to fetch into ObjectEngineResults and Viaduct’s own FieldCompleter to read them. Runtime2 keeps the split but drops FieldCompleter: completion reads Runtime2’s cells directly. ExecuteRootSelectionSet

The two share the result tree while the request runs: completion reads values out as soon as Runtime2 writes them, and waits for any value that isn’t written yet.

Runtime2 works out what everything below a resolver needs before it calls that resolver. So it can call each resolver once for each place its field appears in the response, and ask that one call for everything the fields under it need.

Where in code: QPlanExecutionStrategy · QPlanWiringFactory

The big picture: one tree, two kinds of task

Runtime2 builds the response as a tree of object engine results (OERs), one per object in the response. Each OER holds a cell for every field it must build, and a cell is a write-once slot. Writing a cell’s value is called completing the cell. That is not GraphQL completion, the step that reads the cells to build the response.

In today’s engine Today, venue, location and displayName each get a cell in their parent’s OER too, holding the value and the access-check result, and both are filled in one step. In code, that is a Cell in an ObjectEngineResult. In Runtime2 the two slots fill independently, and the cell also records whether @skip/@include let its field run. ObjectEngineResultImpl

What an OER must build is its demand. Demand is a selection forest, a collection of selections, each one field requested at that place with its arguments and subselections but no alias. Each demanded field then has one of two sources. If the parent resolver’s output already holds it, it is a passive field, passively resolved from that output. If it is missing and has a resolver, it is an active field, which needs its field resolver to run.

Two kinds of task take turns growing the tree. An orchestrator plans one OER in two phases: Prepare closes the result’s demand, and Run claims a cell for each active field. A resolver task calls one field’s resolver and fills that field’s cell.

In today’s engine The engine fetches venue first and then fetches each field of the Venue object separately and in parallel, title, lat and lng included, each run by FieldResolver. In Runtime2 the venue resolver task copies title, lat and lng straight from the resolver’s output and then hands the Venue object to its own orchestrator. executeField

Where in code: startResolve · OrchestrationTask.create · publishResult · resolvePassiveObjectValues

  • Runtime2 does resolution and completion builds the response; the two share one result tree, where Runtime2 writes values and completion reads them.
  • The response is built as a tree of OERs, and each OER holds a write-once cell for every field it must build.
  • An orchestrator plans one OER: it closes the result’s demand, claims a cell for each active field, dispatches a resolver task for it, and freezes the result.
  • A resolver task calls its field’s resolver once, fills the passive fields from what it returned, and dispatches the orchestrator of any child OER.
  • The two kinds of task take turns down the tree until every demanded field has a value.
