# Resolution Design

## Role

Resolution is Runtime2's production field-resolution implementation. It is a selective query resolver based on structured concurrency and synchronous symbolic closure.

Dispatched Resolution field-resolver-task roots terminate their owned field and binding promises when their `Job` reaches cancelled completion, including when cancellation prevents the task body from entering. Field-resolution and helper computation boundaries convert ordinary `Exception`s into modeled outcomes; unexpected non-cancellation exceptions escaping a launched orchestration task fail the request. `Error`s escape without a cleanup guarantee. [Failure And Cancellation Protocol](#failure-and-cancellation-protocol) distinguishes the rules shared with Resolver21-23 from Resolution-specific mechanisms.

## Root-field references

All maintained resolver families implement the common reference semantics summarized in [Resolver families and alignment](resolver-families.md). This section specifies production Resolution's additional closure, condition, runtime-binding, task, and observation machinery; it is not the capability boundary for Resolver01–23.

`ResolverOutputData ::= EngineOutputData | RootFieldReferenceData`. `RootFieldReferenceData` is therefore an opaque symbolic resolver instruction in the resolver codomain, not engine data available as resolver input. Its canonical path starts at Query, crosses only singular argumentless object namespace fields, and ends at a registered object-field resolver whose target returns a singular composite, scalar, or enum; its target arguments are already grounded and variable-free. A composite reference target conforms to its consumer only when the target's possible concrete object types are a subset of the consumer's possible object types. This conservative check occurs before invocation: an abstract target with only partial overlap is rejected even if one runtime result could have conformed. Unlike the old engine's object-only `LazyEngineObjectData` carrier, Resolution may publish referenced scalar and enum values because it resolves the instruction before constructing the consumer result. The descriptor itself has no object fragment, Query fragment, or direct `@parent` relationship. Runtime2 requires every resolver invoked as a reference target to have an empty object fragment and no `FromObjectField` variables. A target may retain Query RSS and `FromQueryField` variables, including namespace-relative input expressed by prefixing the selection with its Query-to-namespace path. This deliberate fragment restriction matches the audited tenant usage and is narrower than the old engine's boundary.

Ordinary active fields and checked field-checker occurrences participate in `closeOrchestrationConstructionDemand`'s fixed point. Source presence takes precedence over registry membership: when a source supplies a root-field reference for a field with a registered resolver, that reference owns the occurrence and the field's standard resolver and its input demand are not activated. Once the fixed point stabilizes, closure scans directly demanded source fields for embedded references and creates root-reference occurrence contexts. A reference occupying a list-element position is likewise valid when the containing list field has a registered resolver and is being passively supplied. References nested in lists do not add closure bookkeeping: passive-value recursion reaches each concrete element occurrence and assigns it a stable pending list cell.

A reference occurrence separates stable publication state from replaceable invocation state. `ValueSourceOccurrence` is the sealed input to `FieldResolverTask`: ordinary resolver, direct root-reference, and conditioned passive-value occurrences expose their consumer selection, publication path, expected type, and construction demand. A conditioned passive-value occurrence lets the same field-resolver task activate a reference-bearing list before passive materialization begins; it does not introduce another coroutine task kind. `FieldResolverTask` extends `CoroutineFieldResolverTaskBase<SymbolicFieldPublicationOccurrence>` and owns Resolution setup and structured coroutine lifetime. The abstract base implements `SharedFieldResolverTask`, retains the typed publication context and field scope, and provides the common run/error boundary for Resolver21–23 and Resolution. `FieldResolutionLogic` holds that concrete task as a constructor property and owns invocation and publication logic. The task retains its private `FieldResolutionLogic` and prepared `SymbolicFieldPublicationOccurrence`, which holds the operation, containing OER occurrence, value-source occurrence, single publication cell, and provider reads; the containing OER occurrence supplies the structural parent and publication root. For each reference hop, the resolution logic uses `prepareRootFieldReferenceInvocation` to create an invocation context whose occurrence ID uses a fresh empty Query OER plus the reference path, whose object input is an empty EOD of the target field's containing type, and whose Query fragment runs in an independently rooted Query execution as a child of the same field-resolver task. Ordinary declared fragments reached inside that execution use its orchestration's singular associated Query OER. The grounded reference arguments immediately bind any `FromArgument` definitions; `FromProvider` and Query-fragment-sourced bindings retain their ordinary lifecycles. No namespace OER chain, detached orchestration task, object-demand closure, or target publication cell is created. The returned ordinary value is materialized only at the consumer occurrence, so simple values are published directly while object descendants and parent fields use the consumer structure.

`FieldResolverTask` ownership means that its request-root job supplies the cancellation boundary and terminal lifetime for all field-local work. `FieldResolverTask.fieldTaskScope` exposes that same structured child scope to logic executing within the task; it does not confer request-root launch capability or create a second owner. Auxiliary launches may therefore be issued by `FieldResolutionLogic` or task-owned helper operations when they are children of `fieldTaskScope`; Kotlin class placement does not determine coroutine ownership. The shared `SharedFieldResolverTask<P>` interface exposes only `publication: P`. Resolution supplies `SymbolicFieldPublicationOccurrence` as its type argument, retaining concrete `OperationContext` access through that context. The coroutine scope stays on the task; operation, publication cell, provider reads, and occurrence metadata are accessed through their owning contexts. `FieldResolutionLogic` receives only the task and follows the same ownership path rather than storing forwarding properties or accepting a second publication-cell argument.

`FieldResolverTask` implements `ResolutionExecutionContext` and is passed explicitly to every registry function it invokes. An execution adapter may wrap that capability in an invocation-local `EngineExecutionContext`, so `resolveSelectionSet` delegates directly to the owning task without coroutine-context lookup or shared mutable binding. The task derives construction demand from the supplied materialization forest and resolves it in a fresh root OER using a child `OperationContext` whose dispatcher is derived from `fieldTaskScope`; the child context shares the logical operation's world, variable-binding state, cycle checker, binding-declaration state, and observer. Nested selection execution and every task it dispatches are consequently cancelled with the calling field-resolver task rather than becoming another top-level request.

Ordinary fields, object-field references, and list-element references use the same `FieldResolverTask`. Their occurrence context supplies the stable publication path, expected type, and construction demand; the retained publication context's cell and containing OER occurrence supply the value promise, structural parent, and publication root. For an ordinary field the task launches its prepared provider readers, then asks `FieldResolutionLogic` to perform the publication occurrence's inclusion and activation step, materialize the owner-local Query projection from the associated Query OER, branch between ordinary symbolic-argument invocation and an already-grounded initial reference, follow one tail loop for every direct reference result, and publish normally.

If a referenced resolver directly returns another root-field reference, the shared tail-resolution loop creates another resolver occurrence with a fresh identity root, invokes the next target, and keeps the original publication identity. Every sibling reference and every tail hop has distinct root identity. The eventual value is materialized under the selection and demand of the position into which the reference was inserted, so ordinary recursive object results are bounded by that selection. Runtime2 intentionally does not share invocation roots or deduplicate equivalent descriptors; physical caching can be layered above this semantic occurrence model. A resolver that dynamically returns an infinite reference tail has the same tenant-code nontermination status as recursive `ctx.query()` or any other infinitely recursive resolver behavior and has no reference-specific cycle detector. This is distinct from declarative object- or Query-fragment dependency cycles, which registry validation rejects.

Resolver observations record both the stable publication identity and every independently rooted invocation. Correctness replay re-evaluates the source-owning resolver, consumes the exact canonical reference-hop chain needed by that output, re-evaluates each target with its empty object input, arguments, canonical completed-output demand, and Query witness, and finally checks the ordinary output at the consumer position. It does not trust the observer's recorded supplied demand; exact runtime-demand validation remains a separate application-witness property. Every invocation path must exactly equal the descriptor's grounded path, every invocation root must be fresh across the request, and every observation published beneath the result root must be consumed by one replayed chain. Application accounting uses only the observations justified by this source-ownership replay; a reference identity root contains no executable namespace occurrences or object-fragment dependencies to traverse.

## Resolver Identity

Every OER is a map whose keys compare by canonical field and argument expression. Ground keys with equal values coalesce. Symbolic keys coalesce when they contain equal variable instances in equal expression positions. A variable-bearing resolver-fragment selection retains that symbolic `ObjectKey` as its permanent cell identity; completing its bindings makes the key contextually grounded but never rekeys the cell.

Registry variables are templates. Instantiating a resolver fragment replaces all uses of each template with one variable instance identified by the concrete resolver path. Equal uses of that instance therefore coalesce within an OER, including duplicate selections and aliases that project the same canonical key. Different variable names, defining fields, or resolver paths remain distinct even when their completed bindings have equal values, so the same grounded field arguments may be invoked more than once.

Keys need no child-occurrence localization. Each object and list element owns a distinct OER, so the same symbolic key can be reused in multiple containing objects without conflating their cells. A nested resolver receives its own concrete path when its fragment is instantiated.

Resolver input materialization filters source occurrences to the concrete object type and collects them by response key. Each response group awaits every argument binding, requires its symbolic construction key to be contextually grounded, and reserves or reads that exact OER cell without substituting arguments into its identity. Checked materialization reads the field result from the selected cell, follows its raw value through list wrappers, reads the type result from each reached OER occurrence, combines applicable results through the production `CheckerResult` contract in type-then-field order, and evaluates resolver applicability. Duplicate occurrences in one response-key group contribute one input entry with their combined subselections. Distinct aliases remain distinct input entries even when they project one shared construction key.

Shared correctness validation has no resolver-family addressing mode. Every stored key it traverses must be contextually grounded. To validate demanded selections and reconstructed resolver input, it prefers the exact symbolic key when that cell exists and otherwise accepts the key's grounded projection, which keeps validation compatible with earlier resolver families without weakening Resolution's runtime identity.

## Request And Task Ownership

One root `coroutineScope` owns the request. The request-scope ownership rule is normative: only orchestration-task, field-resolver-task, field-checker-task, and type-checker-task roots MAY launch directly on the request scope, and every independent reference-target Query producer, provider reader, binding producer, or other auxiliary coroutine MUST be a child of its nearest owning task. Each orchestration owns an object OER and one associated Query OER; active work on either side retains one orchestration request-root task, while a pair with no active work freezes synchronously without launching one. Adding another request-root task kind requires an explicit update to this design and to the narrow root-task-launch capability; directly exposing or launching on the raw request scope is prohibited. `RequestScopeOwnershipTest` enforces that the raw scope is used only inside `CoroutineTaskDispatcher` and checks the permitted dispatch call sites. The coroutine dispatcher accepts prepared orchestration, field-resolver, field-checker, and type-checker publication handles and couples every asynchronously produced field publication, checker publication, and provider binding to its owning job's terminal state, so cancellation before coroutine entry cannot strand a synchronously declared promise. Successful synchronous return therefore means all request work has reached quiescence.

Task completion is not a cross-task readiness protocol. Cross-task reads use OER value promises, binding promises, or an OER's bindings-declared signal. The dispatcher changes scheduling only; it does not change resolver, variable, path, or task identity.

### Failure And Cancellation Protocol

#### Rules shared by Resolver21-23 and Resolution

The [tenant failure and progress policy](principles.md#isolate-tenant-failure-without-stranding-work) governs these boundaries. Ordinary resolver, checker, and variables-provider failures remain local; aborting the request is never a fallback for handling them. The operation may nevertheless wait for slow or hanging tenant work, including work whose output becomes unnecessary after another failure. Required error publication and explicit cancellation cleanup remain separate obligations.

Field-resolution failures are result values. Unexpected exceptions in the field-resolver task's main coroutine propagate to its `run` boundary, which completes the field's value slot with `ErrorEngineResult`. This boundary covers synchronous task setup, input materialization, resolver invocation, and passive resolution. The error does not exceptionally complete the slot or fail the request; unrelated fields can continue.

Prepared publication metadata is validated first inside that boundary, before any provider-reader or Query-producer setup. Resolver21–23 validate the applicable grounded metadata there too. Keeping validation at field-task entry limits a malformed publication to its owned field; moving these checks into orchestration preparation would widen the failure. Resolution completes unstarted provider-read bindings with `VariableBinding.Error` before forwarding a validation exception to the field-error publisher, which terminates the remaining invocation bindings and value/checker-absence slots. DFS intentionally retains its preparation preconditions and fail-fast behavior.

Independent reference-target Query-fragment producers are child coroutines of the owning field-resolver task. They must catch their own computation exceptions: an exception escaping a child can cancel its parent before the parent's `run` boundary can publish a field error. Instead, a Query producer returns a `Deferred<EngineObjectOrErrorData>` carrying `Success | Error`; the owning reference invocation enters its resolver body only after receiving the successful object variant. Ordinary declared Query fragments use the orchestration's associated Query OER and therefore surface producer field errors through materialized input values.

Unexpected non-cancellation exceptions escaping a launched orchestration task fail the request. This describes an engine installation or invariant failure, not an allowed way to handle an ordinary tenant exception; letting a local tenant failure escape here would violate failure isolation. Neither coroutine implementation path has an error-conversion catch in orchestration's `run`. Orchestration with active work runs as an independent request-root coroutine, even when a field-resolver task or Query producer dispatched it. `CoroutineStart.UNDISPATCHED` preserves synchronous installation timing but does not put that coroutine inside the dispatching caller's catch boundary. Resolver21–23 and Resolution therefore propagate an installation or freeze failure through the request job.

Synchronous orchestration preparation follows the caller's boundary. The factory's closure and initialization, `checkDispatch`, and `run` for an orchestration pair with no active work execute inline. Their exceptions fail primary request setup, become the owning field's error during passive resolution, or become an independently rooted reference-target Query producer's error during Query setup. A failure partway through orchestration installation can leave promises claimed before their producers were dispatched; the producer cancellation guarantee below does not cover that unfinished installation.

At each error-conversion boundary, `currentCoroutineContext().ensureActive()` distinguishes an ordinary failure from actual coroutine cancellation. If the coroutine is active, a caught `Exception`—including a task-local `CancellationException`—becomes the appropriate error value. If the coroutine has been cancelled, `ensureActive()` throws the coroutine's cancellation so Kotlin structured concurrency can propagate it. Orchestration has no such conversion boundary; cancellation there follows Kotlin's ordinary job-cancellation rules.

The canonical field-resolver-task boundary is:

```kotlin
catch (cause: Exception) {
    currentCoroutineContext().ensureActive()
    publishFailure(cause)
}
```

The same catch pattern applies inside independent reference-target Query producers, substituting a Query-error outcome for `publishFailure`. Exceptions from the error-publication code itself or from job-completion handlers remain outside that catch; declaration, ownership, and terminal-publication defects are not guaranteed to become field errors.

Cancellation is initiated on the request or a task-root `Job` and propagates to helper coroutines through Kotlin structured concurrency. Explicit cancellation cleanup for separately allocated promises belongs to task-root completion handlers; helpers do not install cancellation-cleanup handlers on their child jobs. The root handler cancels outstanding owned promises so `await()` throws `CancellationException`, including when cancellation prevents task entry. An independent reference-target Query `Deferred` gets its cancellation lifecycle from Kotlin. `Promise.complete(value)` and `Promise.cancel(cause)` report atomically whether the caller performed the terminal transition; root cleanup tolerates an already-completed promise.

Stopping request-owned work in the object or associated Query OER early because one consuming field or checker failed is a non-goal, even if that consumer was the work's only demander. A slow or hanging tenant producer may continue to delay the operation. The required guarantee is that Query-side tasks do not remain suspended on bindings whose producers exited or were bypassed by owner failure or cancellation. Bindings still needed by those tasks must receive an error or cancellation. `QueryFragmentBindingTerminationTest` checks these exits, including "variables provider throws" and "variable missing from variables provider map"; separate producer tests retain the independent reference-target boundary.

Unused bindings of negatively activated work need not complete because every task that could read them is excluded by the same activation condition. Those tasks check the condition and finish before attempting to fetch the bindings, so pending bindings cannot prevent request completion. When a consumer fails or is cancelled, its Query tasks can remain active and need error or cancellation values to unblock them. With negative activation, the dependent work is also excluded, so there are no remaining readers to unblock.

None of these resolvers catches or converts `java.lang.Error` into a modeled result. An `Error` escapes unchanged for a broader fault-tolerance boundary; there is no cleanup or quiescence guarantee after such a failure. Successful synchronous resolution, by contrast, waits for request quiescence.

`CoroutineResolverContract`, exercised by all four resolvers' `CoroutineResolveTest` adapters, checks field and errors producing the associated Query OER, cancellation, JVM errors, and request failure from both object- and Query-rooted orchestration. Resolution-specific tests retain independent reference-target Query producers.

#### Resolution-specific mechanisms

A nested `ctx.query` call is distinct from a resolver's declared Query fragment. The nested call runs resolver-requested selections through `FieldResolverTask.resolveSelectionSet` and returns the projected result through `viaduct.engine.runtime2.resolution.framework.materializeResult`, which reads installed cells and value promises while allowing their values and bindings to remain unfinished. Result projection and runtime resolver inputs within the nested query use the child operation's checker, so the caller's reads participate in runtime cycle rejection. The declared Query fragment is a resolver dependency; its runtime input uses Resolution's `materializeResolverInput`, which can reserve symbolic cells and value promises before their producers install them. Both materializers apply the same slot-driven field-check rule. Correctness replay of either object or Query-fragment inputs uses shared `materializeResult` with the default no-op cycle checker on existing results, preserving symbolic key identity after bindings resolve.

Resolution prepares one associated Query OER during orchestration, prepares every ordinary object- and Query-side publication before their dispatch, and dispatches conditioned passive-list publications registered during descent alongside them, and lets each ordinary owner materialize its own projection from that shared result. Object- and Query-rooted provider readers run as children of their owning field-resolver tasks and publish occurrence-local bindings directly from their absolute provider OERs. This preserves concurrent progress between the two fragments without an operation-wide Query-result registry. Each independently rooted reference hop still starts and awaits its own Query producer before invocation. Resolver21-23 have only grounded `FromArgument` bindings.

The field-error boundary completes `FromProvider` and `FromArgument` bindings for the current resolver invocation. Each reference hop updates that invocation while retaining the original field's publication cell, so an unexpected exception releases Query tasks waiting on the failed hop's bindings and publishes the error at the original field.

Resolution additionally has runtime provider-binding producers. A provider reader catches failures from both inclusion-condition evaluation and path traversal and completes its binding with `VariableBinding.Error`; a false condition skips the read. A tenant variables-provider failure completes its bindings with error values and supplies an error for its owning field. Independent reference-target Query-production failure also completes that fragment's outstanding path-variable bindings with error values. These error-conversion boundaries retain the same `ensureActive()` rule; they do not perform cancellation cleanup. The field-resolver-task root owns cancellation of object-provider, Query-provider, `FromProvider`, and delayed `FromArgument` bindings. Its dispatch-time completion handler covers the original occurrence before task entry, while invocation setup registers additional handlers on that same root job for bindings introduced by later reference hops. Query producers and provider readers rely on the root for cancellation cleanup. Resolver21-23 have no runtime binding producers, so their root cleanup only needs to terminate the field publication.

#### GraphQL execution bridge

The `CompletableFuture` translation belongs to the GraphQL execution adapter that uses Resolution, not to the shared resolver protocol. Kotlin cancellation remains a `CancellationException` until the owning `Job` has reached its terminal cancelled state; wrapping it earlier in a non-cancellation exception would turn cancellation into task failure. After job completion the bridge completes its Java future exceptionally with `CoroutineCancellationBridgeException`, whose cause is the original Kotlin cancellation but which is not itself a `CancellationException`. Consequently Kotlin cancellation does not accidentally set that future's `isCancelled`, while explicit cancellation of the bridge future cancels its task in the opposite direction. Cancellation propagation from GraphQL Java's downstream public future is an unresolved alpha integration boundary documented in [Engine API integration](../integration/engine-api.md).

### Resolution Operation State

`OperationContext` is the interface for this scope's stable reference bundle. It explicitly extends `SharedOperationContext<CoroutineTaskDispatcher>`. The dispatcher retains only the request scope; each value or checker publication implements `CoroutinePublicationOccurrence` and owns its task-specific launch and cancellation boundary. The context's `create(...)` factory returns an anonymous implementation delegating the shared operation properties and retaining the shared resolver observer and adding `cycleChecker: CycleCheckState` and `bindingsState: BindingDeclarationsState`. The context neither implements those state protocols nor owns their mutable storage. `forChildScope` changes the dispatcher scope while retaining the same logical operation state. `SymbolicFieldPublicationOccurrence` is a class implementing `OperationContext by operation`; `FieldResolverTask` supplies that occurrence through its typed `publication` property. The concrete task also retains its shared coroutine lifecycle base, original publication, and execution-bridge capability.

`OEROccurrence` bundles the root OER, exact root-relative structural path, target OER, and optional immediate parent occurrence that remain unchanged while Resolution orchestrates or resolves one object occurrence. Primary-operation, associated Query, and independently rooted reference-target results create self-rooted occurrences without parents. Passive object materialization creates descendant occurrences at the exact field-and-list path where each new target is published. The occurrence context is shared across resolver families, preserving the same root, path, and structural-parent identity through their common passive resolution.

## Construction Demand Closure

`OrchestrationTask` extends the shared `CoroutineOrchestrationTaskBase<O>` base and supplies its `OperationContext` through `operation`. Resolver21–23 use the same lifecycle base with their own concrete operation type. The base retains the concrete operation and paired OER contexts; owns the atomic one-shot guard; calls the dispatch-validation hook after claiming dispatch; and prepares and dispatches field publications before freezing both OERs. Resolution supplies the active-work predicate, passive-field validation, and field-installation hook, while retaining its private closure and binding-declaration guard. The shared guard preserves each family's diagnostic contract: duplicate dispatch raises `IllegalStateException` in Resolver21–23 and `IllegalArgumentException` in Resolution.

`OrchestrationTask.create` allocates one associated Query OER and synchronously closes object- and Query-rooted symbolic demand together. It establishes both binding-declaration domains, installs demanded parent backedges on both sides, and returns a prepared task with stable `objectOER` and `queryOER` contexts. Construction and preparation are private to this factory: callers cannot observe an unprepared task, and the factory does not dispatch active work.

The fixed point accumulates shared `OrchestrationConstructionDemand` values, separating newly discovered resolver/checker key-inclusion pairs from their fixed fragment contributions. Discovery retains symbolic occurrence contexts even for excluded or argument-error reservations; only new satisfiable expansion events extend demand. An expansion event with empty fragments still advances bookkeeping. Grounded closure has the corresponding discovery/collection/routing shape, but grounds keys and binds argument variables during each pass. Its `groundWithLiftedParentDemand(operation, ...)` analyzes accumulated demand; symbolic `withLiftedParentDemand(world)` analyzes initial demand and each new contribution without consulting runtime bindings.

After the fixed point, `finalizeClosedOERConstructionDemand` normalizes selections and finishes the occurrence, variable-provider, and root-reference descriptions needed by task preparation. Those descriptions remain part of the closure result; finalization neither installs promises nor dispatches work. Resolver and checker descriptions share the same provider-read construction helper. This additional construction work is needed because runtime bindings remain unresolved, whereas the grounded family can prepare tasks from grounded selections.

Closure repeatedly expands each newly seen resolver `ObjectKey` whose field is absent from its side's source EOD. An object-side resolver contributes its object fragment to the object OER and its Query fragment to the associated Query OER; a Query-side resolver contributes both fragments back into the Query OER. As part of the same fixed point, `liftParentConstructionDemand` analyzes parent selections in requested descendants and reachable resolver inputs, transposes their variable-free demand across the matching producer edge, and adds the resulting ancestor demand to the same side. A source-present argumentless field remains unexpanded by the local closure loop and is materialized from the source even when the registry contains its standard resolver. Expansion does not await argument bindings. It records the resolver template, its fixed input demand, and one definition for each instantiated variable.

The local expansion loop on either side does not expand resolver keys on descendant OERs. A parent lift from a grandchild can first add demand to an intermediate descendant, whose resolver inputs can in turn require fields on the current OER. Parent lookahead follows those newly lifted selections and their reachable resolver inputs before that side closes; the local loop alone would miss that further ancestor demand. It returns only parent-induced additions and their containing paths, rather than a complete expansion of every ordinary resolver input it visits. [Why the depth-first resolvers do not support `@parent`](examples.md#why-the-depth-first-resolvers-do-not-support-parent) illustrates the cross-occurrence dependency shape that motivates this analysis.

Fixed descendant RSS analysis runs before its occurrence-local condition bindings exist. It uses `withoutInclusionConditions` to replace unresolved guards with `Always`, while omitting selections already reduced to `Never`. Guards inherited from the supplied selections still constrain the lifted additions. This is a separate step from instantiating a resolver's actual input fragment: that fragment retains its conditions, and the symbolic closure loop propagates each newly discovered key-inclusion alternative through it. Thus `@skip(if: true)` contributes no parent demand, while an unresolved descendant RSS guard cannot be used to prune ancestor construction in advance.

Every source occurrence carries a conjunctive inclusion condition. Merging equal keys disjoins those occurrence conditions locally and pushes each occurrence's condition into only its own descendants. Closure therefore remains unconditional and structural: it discovers and installs every possibly needed resolver task before any condition binding must be ready. Provider reads retain the defining fragment's own path conditions, and registry assembly rejects cycles through those conditions. An excluded step binds null without waiting for a value; provider reads add no construction demand beyond the original conditioned fragment.

Every resolver key in closed value selections is represented either by the expansion map or by an argumentless source-provided field. Successor-demand construction still transposes parent selections into selective producer output before returned objects exist, while construction-demand closure independently ensures the required ancestor cells have writers. Repeating the one-level transposition through parent-demand analysis handles grandparents without recursively traversing parent backedges as structural children or reopening an ancestor task.

An open resolver key contributes its object-fragment dependencies before its arguments ground. If those arguments later become an error, those dependencies may have executed speculatively. That conservative over-work is part of the alpha model.

## Field Checks

Each orchestration closes four forests: checked and unchecked construction demand for its object OER and its associated Query OER. `ClosedOERConstructionDemandContext.constructionDemand` retains both components; its `closedValueSelections` projection is their value union. Client and ordinary resolver selections contribute checked demand. Checker object and Query fragments contribute unchecked demand. An active resolver reached through unchecked demand contributes its own checked inputs. Parent lifting, passive descent, lists, and reference publication preserve this provenance; successor demand exposes only the required value shape to a producer. Successor expansion memoizes each resolver/checker fixed fragment only when no recursion cut made the result stack-dependent. It coalesces producer demand recursively by concrete key, retaining each alternative’s guard on its descendants; duplicate named pairs therefore do not multiply the passive output forest. Statically excluded requested fields remain in the producer forest as selection metadata, without contributing fixed dependency expansion.

`FieldCheckerOccurrence` retains the exact symbolic selection, paired fragments, and existing provider-read descriptions. Checked inclusion is evaluated independently of value activation: an unchecked owner may require a physical value while the checked occurrence is excluded. A registered checker then publishes absence without invoking its providers or function. A negatively activated cell publishes neither value nor checker result. Arguments ground only at invocation; equal grounded arguments do not merge distinct symbolic checker keys.

`FieldCheckerTask.prepareAll` returns a `FieldCheckerPreparation` recording every claimed checked slot, executable checker publications with kind-qualified writers, and delayed absence slots before passive descent can dispatch children. Orchestration dispatches executable checker publications beside field-resolver publications. After dispatch, `publishReadyAbsences` completes absent-checker slots whose passive values are already materialized; pending values leave that terminal decision to field-resolver activation or cancellation. Preparation never decides dynamic activation. This is the symbolic counterpart of grounded preparation returning all claimed publications, including null-checker entries. The checker task binds arguments, starts ordinary from-field readers, invokes each named variables provider once, and materializes each named object/Query pair raw using the existing symbolic materializer. All owners share exact production in the orchestration's associated Query OER and retain their own projections. Raw value-slot reads participate in cycle detection; ordinary resolver boundaries restore checked reads. Checker exceptions exceptionally complete the checker slot and terminate pending bindings, while request cancellation cancels owned slots and bindings even before task entry.

Named pair variables use pair-prefixed names in the existing binding domain. Their original response paths determine from-field inclusion, so an excluded alias binds null even if another pair supplies the same physical cell. Selected null intermediates and terminals bind null; included errors, including errors inside scalar lists, bind an error. Static provider exclusion and dependency cycles through arguments or inclusion are rejected during registry assembly.

Checker `ctx.query()` starts an independently rooted unchecked execution under the checker task. Value resolvers inside it still introduce checked inputs. Declared checker Query fragments never create independent roots. Synchronous closure rejects a fragment expansion that repeatedly instantiates the same root/field/executor-kind site through its own variable lineage; a statically excluded reservation contributes no fragment expansion and is not registered in that lineage. Tenant callbacks that suspend forever may keep the operation pending; the bounded nontermination witness exercises explicit cancellation, not a guarantee of completion without cancellation.

Checker-aware correctness replay reconstructs named raw inputs and verifies from-field bindings from their materialized response paths independently of compiled guards. Replay caches are scoped to one judgment and shared by result identity across owners, whose projections remain separately validated. Duplicate-preserving checker invocation accounting is a distinct judgment.

## Symbolic Type Checks

`TypeCheckerOccurrence` retains one concrete OER's target-qualified fragment instances, checked incoming condition, and raw provider paths. `SymbolicTypeCheckerPublicationOccurrence` owns its type-result promise and bindings without borrowing a producing field's key or activation. Orchestration declares those bindings and installs the exact OER cycle writer before passive descent or local producer dispatch. Checker-only passive objects count as active work. Cancellation of the task root terminates the result and every owned binding even when the task body never enters; ordinary provider, materialization, or checker exceptions fail the type result and complete remaining bindings with errors.

`Demand.typeCheckCondition` refines the grounded `typeCheckDemanded` bit for Resolution. Descending through a checked field retains that field's effective condition, joining incoming alternatives disjoins their conditions, and local checked fields do not by themselves demand their root's type check. The type task evaluates independently ready alternatives before invoking providers or checker code. Excluded checked demand overlapping raw demand therefore leaves an OER with a null type result and null terminated checker bindings. Statically excluded and raw-only occurrences need no task. Where parent relationships exist, allocation reserves a possible type result until synchronous closure has established whether a checked backedge demands it; preparation publishes absence before exposing a raw-only OER.

Schema validation prohibits parent backedges to Query and `@namespaceType` objects. The associated Query OER therefore cannot acquire incoming type-check demand: it is allocated with an immediate null type result, contributes no type-checker context to closure, and owns no type-checker task. The object side still handles type checks for ordinary checked roots and returned objects.

Joint closure expands each newly discovered type-check inclusion alternative as unchecked object/Query input demand. Named projections remain separate and Query inputs use the orchestration's associated Query OER. Active value resolvers reached through those raw inputs restore checked input demand. Selective successor analysis includes possible concrete type-checker object inputs before producer invocation and uses a separate type boundary for recursion cuts. Parent lookahead also follows type-checker object fragments before ancestor freezing, including a checked parent edge that demands an initially raw ancestor.

Type variables use the concrete type target and full OER occurrence path, including list indices and symbolic producing keys. `FromObjectField` and `FromQueryField` readers use their named defining fragment's response paths; providers receive the empty argument tuple. `FromArgument` remains rejected by the type-checker model. Runtime materialization and completed-result correctness reuse the existing raw/checked traversal and target-qualified checker replay. The latter independently compares from-field bindings with named raw projections and provider bindings with a fresh evaluation of each named provider relation. Reference-target Query inputs are independently checked execution roots; the correctness judgment requires their type result separately from cached raw validation and associated Query-root projections. Runtime witnesses check execution counts and binding identities before replay so relation evaluation does not inflate execution evidence.

## Binding Declaration

After closure, orchestration declares every open binding before dispatching local field work.

`FromArgument` definitions owned by an already-ground key read their canonical input paths and complete immediately. A null input-object intermediate produces a null binding. Definitions owned by symbolic keys complete after the owner's arguments resolve, while the owner key itself remains unchanged.

Each `FromObjectField` definition launches a provider reader that follows its compiled path through the defining occurrence's object OER promises. Each `FromQueryField` definition launches an equivalent reader through that orchestration's associated Query OER. Query-side resolver occurrences use the associated Query OER for both provider kinds. Provider path templates retain response names for alias-specific compilation. Their occurrence-specific read descriptions contain only canonical keys and effective inclusion conditions, with undefined equality. Each source occurrence's guards propagate into its own descendants before alternatives are disjoined. Provider arguments may be grounded from literals, defaults, the owner's arguments, or other acyclic from-field bindings of either kind. All binding promises are declared before provider readers and field resolvers launch.

Before reading a provider component inside an OER, its reader awaits that OER's bindings-declared signal and every argument binding needed to make the component key contextually grounded. `OrchestrationTask.create` marks bindings declared immediately after synchronous demand closure declares every binding in the OER's binding domain, before recursively materializing passive children or launching local field work.

`BindingDeclarationsState` owns these per-OER readiness signals, while `VariableBindingsState` owns actual variable-instance bindings. Binding completion reports whether it performed the terminal transition, and consumers never manufacture undeclared bindings. Ordinary field-resolver tasks receive the prepared associated Query OER and materialize from it; only independently rooted reference-target invocations launch a child Query producer.

Nested provider keys resolve their argument values against the owning resolver occurrence and use the original symbolic key for OER lookup. The separately resolved arguments are a readiness and invocation witness; they do not replace the key.

Readers never insert undeclared binding promises.

## Passive Values

`OperationContext.passiveValues` owns one `PassiveValueResolutionLogic` collaborator for its execution scope. Field resolution calls `publication.operation.passiveValues.resolvePassiveValues`, matching the grounded coroutine family and exposing the recursive edge back into orchestration. The collaborator retains no traversal-local mutable state. DFS keeps its depth-parameterized factory because Query-OER depth participates in its scheduling.

Every argumentless field present in a resolver's source EOD is read by canonical field name through resolution's local `resolvePassiveValues` path, including fields that have standard resolvers in the registry, except that an engine-provided `@parent` entry is ignored in favor of the structural backedge. Source-provided argument-bearing fields are errors. A demanded registry field absent from the source uses its standard resolver; a demanded non-registry field absent from the source remains an error.

The field-resolver task uses `shared/SharedPassiveValueResolutionLogic` to resolve passive values before publishing the containing value. Resolution's adapter supplies symbolic demand collection, its prepared orchestration factory, list-element reference dispatch, and registration of prepared conditioned passive-list publications with their owning orchestration. The shared traversal owns object/list recursion and demand propagation; all earlier maintained resolvers also use this traversal with grounded closure and synchronous, queued, or coroutine dispatch. For each OER, the factory closes construction demand, declares and marks bindings, and installs demanded parent backedges before returning. Invocation demand separately validates selective output and guides passive descent. The traversal resolves passive fields using the returned closed construction demand, then hands the prepared task to `SharedOperationContext.dispatcher.dispatchOrchestration`. Preparation belongs to orchestration; the caller controls when passive resolution is complete and dispatch may occur.

After passive children have been dispatched, the dispatcher validates the materialized passive cells and enforces one-shot dispatch. An orchestration pair with no active expansions freezes synchronously without creating a coroutine. Otherwise, it launches one request-root orchestration task with undispatched entry; that task calls `FieldResolverTask.prepareAll` to claim and register every active publication on both OERs, then explicitly dispatches the returned value publications, conditioned passive-list publications registered during descent, and previously prepared checker publications, synchronously completes applicable absent-checker slots, then freezes both OERs. The orchestration root is the stable ownership and suspension boundary even though its present task body does not suspend. Undispatched entry ensures that `dispatchOrchestration` returns with both OERs' complete cell shapes installed and frozen even when the request dispatcher is queued; any suspension resumes through the orchestration root's context.

## Publication Preparation And Freeze

For list-element references, `FieldResolverTask.prepareAndDispatchListElement` owns the value-promise claim, cycle-writer registration, and dispatch together. Passive traversal supplies the reference occurrence and exact list-element cell. The grounded coroutine family uses the same helper name and ownership boundary; list cells are already activated by allocation, so preparation does not activate them again.

Orchestration delegates ordinary value publication preparation to `FieldResolverTask.prepareAll`, which reserves every closed active selection's original symbolic cell on both OERs, claims each value promise, registers each writer, and returns the publications without dispatching. Its `prepareAndDispatchFieldWork` hook then dispatches the prepared value, conditioned passive-list, and executable checker publications before both OERs freeze, matching the grounded coroutine preparation/dispatch boundary. Checker preparation remains earlier, during orchestration creation before passive descent, so passive consumers can observe claimed checker slots. Ordinary value preparation does not decide activation. List-element references retain their own combined preparation/dispatch helper: passive value resolution may discover those positions after the containing OER freezes. The helper claims the element promise before dispatch. Conditioned passive-list fields instead prepare and register their publication during passive descent and wait for orchestration-owned dispatch. Each ordinary task launches its prepared provider readers, then its resolution logic awaits argument bindings, derives the invocation `Arguments.Ground`, completes delayed `FromArgument` bindings, evaluates the selection's merged inclusion condition, and materializes its owner-local Query projection. Negative activation returns without invoking tenant code; positive activation permits the already-claimed promise to be used. Keeping reservation and writer registration synchronous preserves discoverability before freeze while moving readiness work into the conservatively launched task.

Resolution's `CycleCheckState` is explicit operation state. Installation registers each active cell's exact writer through `operation.cycleChecker`, and provider and resolver-input reads record their dependency through the same property. Other resolvers and correctness materialization may supply a separate state or the NOP implementation; `OperationContext` does not masquerade as a cycle checker.

`reserveCell` explicitly creates a cell with an unclaimed reservable value promise when needed. `cell.value.claim()` assigns that promise to the writer. Strict claiming makes disagreement between readers and writers observable.

After every active key on both sides has claimed its symbolic cell, orchestration freezes both OERs. Freezing seals each key set and completes any unclaimed reader placeholder with a strict missing-cell exception. Claimed promises may complete or their cells may be negatively activated after their OER is frozen. When equal shared keys carry alternatives from different owners, activation evaluates those alternatives concurrently: any independently ready true alternative activates the cell without waiting for or inheriting another alternative's ordinary failure, while request cancellation and JVM errors retain their structured propagation.

## Field Resolution

After task-local producer setup, `FieldResolutionLogic`:

1. grounds its arguments and completes any delayed `FromArgument` bindings;
2. awaits and evaluates its inclusion condition, negatively activating the cell and returning when false;
3. materializes the resolver's condition-filtered input demand from exact OER cells;
4. derives invocation successor demand from the key's closed construction demand;
5. materializes its owner-local Query input from the associated Query OER;
6. emits `ResolverObserver.onResolverInvocation` with the occurrence and prepared inputs;
7. invokes the selective resolver once;
8. builds the passive result shape while synchronously launching one orchestration lifecycle per OER; and
9. publishes the containing value.

Parent publication does not wait for descendant orchestration to finish. Readers independently derive and reserve the same symbolic child keys; variable-instance equality and strict reservation rules make disagreement fail rather than silently create another identity.

Query fragments reuse the defining resolver occurrence's variable bindings and retain their complete response-preserving symbolic selection tree. Ordinary owners contribute construction demand to one associated Query OER during joint closure, while each field-resolver task later materializes only its occurrence-local projection. Object- and Query-provider readers may progress concurrently, so a `FromQueryField` binding can ground the object fragment and a `FromObjectField` binding can ground the Query fragment without imposing an artificial fragment order. Query-provider readers complete their bindings as soon as their exact paths resolve; the owning field resolver separately awaits materialization of its complete Query input. A Query-only `FromArgument` use binds directly from the owning resolver arguments, while a binding used by both fragments is declared and completed only once. Materialization resolves arguments only to establish contextual grounding and invocation values. Observation records the associated Query OER once and associates every nonempty eligible owner with it.

The owning selection condition guards ordinary Query-fragment construction demand and provider reads. Each provider read additionally evaluates the local condition at every path step, returning null at the first exclusion or selected null value. Query-fragment materialization removes false source occurrences before response-key collection. Thus a conservatively launched Query task may produce an empty resolver-visible object and physical inactive cells without invoking the suppressed dependency resolvers.

Argument errors complete the value promise with `ErrorEngineResult` without invoking the resolver. Successful values complete the value promise once. Every cell owns a field-checker-result promise, published independently of its value. A checked field with no registered checker receives a synchronous null result after positive activation, including activation-error publication and passive parent backedges. Unchecked-only demand also terminates that promise with null. Every concrete OER owns one type-checker-result promise. Construction uses an immediate null promise when the concrete type has no checker and a deferred promise otherwise; orchestration contributes an applicable checker's object and Query fragments as unchecked construction demand, dispatches the checker alongside peer field work, and completes its deferred result. Parent backedges reuse the ancestor OER and its completed or pending type result rather than scheduling another application.

Resolver observations are semantically passive evidence. Every orchestration emits `onQueryOERPrepared` once for its associated Query OER and associates each nonempty ordinary owner through `onQueryFragmentPrepared`, including both the owning object occurrence and a separate concrete owner address; independently rooted reference targets emit `onIndependentQueryFragmentPrepared` for their own Query input result without assigning it the associated-Query-OER role of the fresh root occurrence. Both role-specific events delegate through the two-argument `onQueryFragmentPrepared` compatibility callback. `onResolverInvocation` occurs immediately before ordinary and reference-target resolver entry, and the reference-hop association event retains the stable publication/invocation relationship. Resolution uses this shared observer without a model callback. Query events retain live OERs, not completed materialization; invocation events retain attempts, not return values. These records support validation, but replacing a normally returning, non-mutating observer with a NOP preserves semantic resolution results. Because callbacks are synchronous, an observer that throws or blocks can still change failure or latency and violates the intended instrumentation contract.

## Successor Demand

Successor demand describes the output requested from a producer; construction-demand closure determines the work required for each returned object. It retains passive selections and argumentless resolver-bearing selections that the current resolver may supply. Argument-bearing resolver fields remain necessarily active.

Each boundary resolver's fixed object fragment contributes its passive predecessor demand transitively, conservatively including argumentless resolver-bearing fields that may be supplied by an ancestor. The original downstream construction demand continues separately into each returned child OER, where source-sensitive synchronous closure assigns only unresolved work to standard resolvers.

Successor-demand construction uses the shared `liftParentSuccessorDemand` to transpose a selected child's `parent { ... }` demand into the containing producer selection. The helper returns additional demand, which the caller combines with its original selections. This static lift ensures a selective producer returns the necessary ancestor coordinates before child identity exists. The lifted portion is also included in the returned ancestor's one-shot construction-demand closure so absent fields can use their standard resolvers. Variables are prohibited beneath parent selections, so the lifted shape is fixed before occurrence-specific binding. List and nested-list child results are transparent to the ancestry relation: every contained child OER whose parent is demanded points to the same containing parent occurrence.

Sometimes-passive active fields can make transitive ancestor demand speculative. If a grandchild field with `parent.parent` demand is later supplied passively, its standard resolver need not run but the lifted ancestor demand may already have caused extra resolution or materialization. Resolution deliberately accepts this marginal over-work rather than making demand closure depend on a later dynamic ownership decision.

## Strictness

Binding declaration, cell reservation and claiming, writer ownership, and OER freezing are strict. Promise, cell-activation, cell-value, and binding completion operations atomically report whether each caller performed the terminal transition. Producer call sites explicitly check that result where losing would be a protocol defect; cancellation and terminal-cleanup paths intentionally tolerate losing to another terminal transition. Invalid values, missing ownership, undeclared state, and prohibited writes still throw rather than becoming a `false` completion result.

## Deliberate Scope

Resolution models query resolution with canonical field identity and synchronous source values. It supports runtime `FromObjectField` and `FromQueryField` bindings within their stated provider restrictions.

The alpha correctness contract requires an error result to agree with the resolver value's error variant but does not establish exact `EngineErrorData` carrier identity or metadata agreement. Node lowering and other derived resolver boundaries may replace the carrier while preserving the modeled error outcome. Exact metadata validation therefore remains outside `correctResolution` until each boundary specifies whether it preserves identity or constructs a derived carrier.

Runtime2's Engine API integration excludes mutations, subscriptions, custom scalars, EOD aliases, and asynchronous EOD variants. These are alpha integration limits rather than missing concepts in the Resolution relation. The execution feature-test adapter also rejects `FromQueryField` recipes; that adapter boundary does not limit Resolution's semantic capability. [Engine API integration](../integration/engine-api.md) owns the complete supported and rejected surface.

## Checker failure cleanup

The required behavior is local failure publication on the checker's result and outstanding required bindings. Execution may wait for tenant work supplying its inputs after that failure, even when the checker was its sole consumer. Retracting demand to make the operation finish sooner is not required, and aborting the request is not an acceptable alternative.

Field and type checker tasks publish their exception and complete pending bindings with `VariableBinding.Error`. They do not retract input demand or cancel otherwise running producers because their output is no longer needed. Request completion waits for those producers and their readers; explicit cancellation still uses the existing task-root completion handlers.
