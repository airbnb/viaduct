# Graphql-java Normalized Document on the Schema-4 Stress Query, 2026-11-16

This experiment compares Runtime2's current validated-AST-to-`SelectionForest` path with a prototype using graphql-java [PR #4562](https://github.com/graphql-java/graphql-java/pull/4562) at `69c7bfbef920e5b95b7c295b60ef0652523eef3d`. Both paths run against the same PR jar and the same upstream schema-4 full query. The candidate consumes a `NormalizedDocument` built during validation, walks its shared selection graph, and creates a construction forest directly without Viaduct `SpecSelection` or `MaterializeSelectionForest` intermediates. It decodes each shared field key once per conversion in an identity cache that is discarded after the operation. The [benchmark guide](../../../testing/normalized-document-benchmark.md) describes the implementation and build boundary.

The JMH run used the Hetzner performance server with an AMD Ryzen 5 3600 (6 cores, 12 threads), Ubuntu OpenJDK 25.0.5.0.3, JMH 1.36, one benchmark thread and G1GC with `-Xms2g -Xmx8g`. Every case used two forks, each with two 30-second warmup iterations and three 60-second measurement iterations. The scheduled JMH iteration time was 48 minutes; the run began at 2026-11-15T17:13:08Z (2026-11-16 03:13:08 Australia/Brisbane) and JMH completed in 50:54. No results were discarded or rerun. Errors are JMH 99.9% confidence half-widths, and allocations are the GC profiler's normalized bytes per operation, shown below as decimal MB/op.

| Stage | Current AST path, ms/op | Normalized-document prototype, ms/op | Current allocation, MB/op | Prototype allocation, MB/op |
| --- | ---: | ---: | ---: | ---: |
| Validation | 4.733 ± 0.057 | 5.633 ± 0.241 | 6.564 | 7.555 |
| Forest conversion | 149.623 ± 4.734 | 23.272 ± 0.228 | 227.866 | 42.409 |
| Validation plus conversion | 154.096 ± 4.997 | 29.838 ± 0.384 | 235.607 | 49.944 |

For the complete measured preparation path, the prototype lowers the mean by **124.258 ms/op (80.64%)** and allocation by **185.663 MB/op (78.80%)**. Creating the normalized document adds **0.899 ms/op** and **0.991 MB/op** to validation, while direct forest conversion saves **126.352 ms/op** and **185.457 MB/op**. These are separate JMH cases; stage means are diagnostic and need not add exactly to the complete case. The existing conversion baseline, 149.623 ms/op, is close to the preceding Hetzner measurement of 150.234 ms/op on the same fixture with published graphql-java 26.0.

The query has 4,278 source field AST nodes and 272 named fragment definitions. The PR normalized document stores 4,278 field nodes and 1,410 selection sets; graphql-java counts 259,832 field occurrences after fragment expansion. Runtime2's construction forest contains 187,215 selections after erasing introspection fields. In trial setup, each fork recursively compared the current and prototype forests by key, possible types, inclusion condition and subselections before measuring; all 12 forks passed. The field-occurrence count was checked at graphql-java limits of 259,831 (rejected) and 259,832 (accepted) with the merged-field limit raised. This query exceeds the default field-occurrence and merged-field limits, so both measured validation paths use `QueryComplexityLimits.NONE`.

Parsing, schema building, variable coercion, resolver execution and GraphQL response completion are excluded from every measured case. The prototype covers query construction for this schema-4 operation; it does not establish replacement of Viaduct's resolver materialization representation or mutation handling. Its per-conversion key cache and direct construction are part of the prototype, so the result is the saving of this combined integration approach, not an isolated benefit attributable solely to the normalized-document data structure. The fixture is a large synthetic stress query, not a production workload distribution. The PR is still draft, and Viaduct's older runtime uses graphql-java APIs removed by it; the PR jar was therefore substituted only on the experimental JMH classpath.
