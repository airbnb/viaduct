# Performance Testing

Runtime2 performance testing separates stable JMH measurements from diagnostic JFR profiles. The fixed current-profile overhead corpus combines broad generated Query workloads with small deterministic sections for parent traversal, sometimes-passive fields, complex variable bindings, general root references, conditional demand, and successful or denying access checks. The full Resolution benchmark retains its generated profile. Their query-generation configuration disables named GraphQL fragments. These Query workloads do not measure ordered mutation effects, nested execution, or production dispatcher/service integration. The property-test benchmark uses its own frozen case; inspect that recipe before attributing a feature cost to its timings.

This document owns maintained benchmark, profiling, corpus, and reporting practice. Dated measurements and investigation findings live in the [performance history](../evidence/profiles/performance-history.md) beside their exported profile evidence.

The `qplan.PropertyTestPhase` JFR event name retains the historical upstream project prefix. Its definition is in [`PropertyTestBenchmarkSupport.kt`](../../src/jmh/kotlin/viaduct/engine/runtime2/benchmark/PropertyTestBenchmarkSupport.kt); it records Runtime2 benchmark phases in the current build.

## Running And Reporting

Run benchmarks from the repository root:

```shell
./gradlew :core:engine:runtime2:resolutionFullBenchmark --console=plain
./gradlew :core:engine:runtime2:resolutionOverheadBenchmark --console=plain
./gradlew :core:engine:runtime2:guardedCheckerResolutionBenchmark --console=plain
./gradlew :core:engine:runtime2:correctResolutionBenchmark --console=plain
./gradlew :core:engine:runtime2:propertyTestBenchmark --console=plain
```

The full benchmark measures the generated workflow, the overhead benchmark isolates Resolution over a fixed corpus, the guarded-checker benchmark is a focused diagnostic for inclusion-condition amplification, the correctness benchmark isolates `correctResolution`, and the property-test benchmark measures one frozen end-to-end generated case.

After every run, report each measured iteration, the final JMH score and error, units, the number of top-level resolutions, property cases, or correctness judgments in one JMH operation, and mean time per resolution, case, or judgment. For overhead runs, also report every emitted corpus statistic with its actual percentile label rather than describing all percentiles as P90.

Run closeout controls serially on an otherwise idle host with default parameters unless the investigation explicitly requires and records an override. Comparisons must identify the tested revision, host and relevant hardware, JVM and JMH versions, benchmark parameters, corpus revision or hashes, and any semantic change that altered the measured workload. Do not infer a speedup across different hosts, JVMs, parameters, or corpora.

## Choosing A Profiling Target

Use the narrowest JFR target that still contains the behavior under investigation:

| Target | Use it to investigate | Deliberately excluded |
| --- | --- | --- |
| `resolutionOverheadProfile` | Resolution itself over the fixed current-profile corpus | Query-resource loading and parsing, request preparation, correctness oracles, and statistics reporting |
| `correctResolutionProfile` | The `correctResolution` judgment over prepared diverse inputs | Resolution execution, query generation and parsing, witness preparation, fragment merging, and binding instantiation |
| `propertyTestProfile` | One frozen end-to-end Resolution property case, including its correctness oracles | Resource decoding and `TestWorld` assembly |

The full Resolution benchmark intentionally has no dedicated profiling task. It includes generation and validation and is useful as an end-to-end performance indicator, but it is too broad to explain most hotspots. Start with the property-test profile when the expensive phase is unknown, then move to the Resolution-overhead or `correctResolution` profile when its phase events identify one of those components.

Profile timings include JFR overhead and only one measured iteration. Use the matching JMH benchmark, not the profile duration, to report an improvement. Increase the target's loop-count property when more samples are needed without admitting setup work.

## Optimization Workflow

Performance optimization follows a probe-first methodology that separates hypothesis testing from implementation:

### Iteration cadence

Use `compileKotlin` (~7s) as a fast syntax check during development. The benchmark task itself is a strong smoke test: it runs 100 real queries with full correctness verification via the reporting pass. Reserve `runtime2:check` (full test suite, lint, detekt, boundary checks) and `resolutionStress` (10K generated cases) for commit-time validation, not per-edit feedback.

### Probe-driven hypothesis testing

Before implementing a speculative optimization, add temporary counters to the hot path that measure how often the optimization's precondition holds. Run the benchmark once with probes and read the hit rates. This answers "is this optimization worth building?" in minutes rather than hours.

Typical probes include: fast-path hit rate (empty, singleton, or trivially compact inputs), cache hit rate, branch frequency for rare features (parent fields, variables), and per-call input sizes. Make each probe a single counter increment at the relevant call site. Report probes by adding their output to the benchmark's reporting pass (e.g., in `ResolverBenchmark.reportOverheadStatistics`). Remove probes before committing.

Explore multiple hypotheses simultaneously. One probed benchmark run can test five to ten hypotheses at once, which is faster than implementing and benchmarking each optimization separately. Prioritize hypotheses that probe data shows have >80% hit rates, then implement those and discard the rest.

### Before/after measurement

For a controlled comparison, stage or stash the change, run the benchmark task (not the profile task) on the baseline, restore the change, and run the same benchmark again. Use `resolutionOverheadBenchmark` which runs three measured iterations and reports mean ± error. Single-iteration profile timings are insufficient for improvement claims; they include JFR overhead and run-to-run variance. Record the exact commit, parameter overrides, and host for both runs.

### Structural changes

When a structural refactor (e.g., traversal fusion) creates a new code shape that does not immediately improve benchmarks, commit it with its measured results and then search for optimizations enabled by the new structure. Structural changes often expose new fast paths (empty checks, singleton specialization, cache opportunities) that produce larger cumulative gains than the structural change alone.

```shell
jfr summary core/engine/runtime2/build/reports/resolver-benchmarks/property-test.jfr

```

Replace the path with the Resolution-overhead or `correctResolution` recording as appropriate. Java Mission Control is useful when call-tree, allocation, or timeline exploration needs more context than the command-line views provide. Each profiling task deletes its configured output before recording, so set its output property to a unique path before a comparison run when the previous recording must be retained.

Run benchmarks and profiles from a clean committed Runtime2 tree. Record the exact commit and confirm that `git status --short` is empty before measurement. If exceptional circumstances require profiling a dirty tree, preserve its complete patch and state explicitly that the recorded commit is insufficient to reproduce the run.

Create one checked-in directory under `impldocs/evidence/profiles` for each profiling round and add its dated interpretation to the [performance history](../evidence/profiles/performance-history.md). The history entry must record the timestamp, host and relevant hardware, agent session ID, tested revision, targets used, findings, retained or rejected changes, and controlled before/after results where available. The round README must record the commands, JVM, benchmark parameters, corpus hashes, and raw benchmark iterations or point to the history entry containing them. Export each JFR with:

```shell
core/engine/runtime2/export-resolver-profile.sh \
  RECORDING.jfr \
  core/engine/runtime2/impldocs/evidence/profiles/ROUND/TARGET
```

The exported bundle retains phase events, hot methods, allocation sites, GC pauses, aggregated execution and allocation stacks, and the raw recording checksum. Raw JFR files are optional; retain them outside Git until the investigation closes in case additional views are needed. Preserve emitted workload statistics and identify semantic commits that materially change them so timing discontinuities remain interpretable.

## Full Benchmark

`resolutionFullBenchmark` runs the complete generated property-testing workflow. One JMH operation generates and validates 100 schemas by two registries by five queries, for 1,000 property cases and top-level resolutions. Generation, world assembly, resolution-witness capture, resolution, and post-resolution validation are all timed.

## Overhead Benchmark

`resolutionOverheadBenchmark` loads one checked-in schema, registry, and ordered batch of 100 exact query sources. Before each measured invocation, JMH setup parses the fixed query batch against those shared static objects, creates a fresh immutable `Assumptions` value and `SharedOperationContext` for every resolution, and stores the prepared calls in an array. JMH excludes that setup; the measured method iterates the array, invokes the resolver, and consumes each result. Each resolver invocation obtains its canonical Query source through `ResolverRegistry.createRootQueryInput()` inside the measured call.

The overhead benchmark uses fully prepared callback outputs. Each field callback returns its fixed value-plan output, materialized during registry assembly, and ignores its input and arguments. Each node callback looks up a prepared output by the requested ID. An untimed discovery pass over the query batch records the required IDs once per trial using constant field outputs and a separate registry. Each invocation then builds a fresh registry and eagerly materializes its canonical node outputs for those IDs; an undiscovered ID raises an error rather than generating an output during measurement. The discovery registry's engine caches are not reused. Node identity, resolver fragments, variable providers, checkers, and ordinary engine output lowering and projection remain active. Field-resolver input/argument fingerprinting and fixture object/list construction are outside the measured body.

This deliberately changes the callback semantics from the corpus's input-sensitive programs to prepared outputs. The full, property, and correctness benchmarks retain their input-sensitive callbacks. Treat the overhead change as a measurement correction, not an engine speedup, and record both timing and workload statistics across this boundary. Prepared callback outputs alone preserve the original workload statistics; replacing the checker fixture subsequently changes hidden demand and checker activity.

Overhead checker callbacks likewise return their setup-chosen result without running the fixture's input assertions or fingerprint comparisons. The engine still prepares every named checker input and invokes the checker; ordinary generated test worlds retain those assertions.

The overhead fixture uses one China-active checker profile, independent of the resolver-fragment recipe. The generated business fields receive a successful checker, including passive fields; hash and policy-helper fields are excluded. About a third receive custom China rules, approximating the 956 eligible fields among 3,123 declarations on custom-rule types in the private source census. The others retain fragmentless default-block checks. This is a conservative synthetic policy surface, not a measured traffic distribution or a reproduction of production denial behavior. Identifier fields use fragmentless checks to avoid artificial self-dependencies. The generated Query fields receive privacy checks only, and generated type checkers remain privacy-only. The feature sections add bounded checker denials and variable interactions.

Custom China checks use approximately 94% Query-plus-object-ID inputs and 6% named-null inputs. One named input carries both an aliased, guarded object identifier and a guarded Query lookup, with an unconditional Query `__typename` selection. A constant variable provider returns `shouldSkipForChinaAccess=false`; a `FromField(OBJECT)` variable supplies the actual identifier to the lookup. The thirteen corpus objects use a passive ID, String, or Int field as their identifier. Setup-built helper Query outputs model user country/allowlist/data-scope, listing location/address, reservation host/guest, and a bounded two-user list tail. Helper types have no checkers, and their callback outputs are built once per registry. The list tail is deliberately larger than the source census's rare list rule.

About 42% of business field policies add privacy inputs, with occasional three-input composites, following the custom-China subset's approximately 58%/41%/1% one/two/three-policy mix. Privacy inputs are mostly scalar identifiers, with context-only/null slots and a small Query lookup tail. Type privacy uses three context-only, four scalar, four null, one Query, and one two-input composite checker across the thirteen objects. Standalone context/default-block checks have zero named inputs; a fragmentless policy inside a composite keeps its named empty pair. The previous `left`/`right`/`empty`/raw-root correctness fixtures remain in ordinary generated worlds and the full benchmark.

Changing the checker profile or deterministic feature sections changes hidden engine demand, resolver activations, and projection counts. Treat the timing difference as a workload correction, not an engine optimization. The report counts activated fields in the primary result, including its hidden object demand, and stops at parent backedges. Excluded cells contribute no fields. Associated Query roots contribute to resolver and checker execution statistics; field counts are not the final client response size. A fixed-corpus regression compares the generated client-selected values across all queries before and after the checker replacement. Each deterministic feature section separately passes independent result correctness, exact application accounting with its known supplied-field exemptions, and from-field binding validation. Whole-corpus coverage and binding checks run against fresh prepared registries; the bulk corpus is not claimed to pass whole-result correctness replay, whose closed Query-OER validation currently encounters failed guards on non-invoked checker owners. Reports include actual installed checker counts, named inputs and populated roots per query, and composite input sizes so comparisons across that boundary remain interpretable.

The direct Resolution full and overhead benchmarks accept a `precomputedConstructionDemand` JMH parameter. The benchmark and profile tasks default to `true`, measuring the production precomputed construction-demand path. Override with `-PresolverBenchmarkPrecomputedConstructionDemand=false` to measure the non-precomputed path, or `-PresolverBenchmarkPrecomputedConstructionDemand=false,true` to compare both closure algorithms in separate JMH forks. Always use `precomputedConstructionDemand=true` for optimization work and regression detection: it is the production path, and the non-precomputed path is a correctness reference, not a performance target. Both use identical corpus resources and eagerly compiled registries. Overhead measurement also reports JVM-wide allocated bytes sampled after invocation setup and before teardown, excluding query parsing, registry construction, and operation preparation. Small unrelated JVM allocations can contribute to that counter. The `ResolverBenchmark.registryStartup` JMH method measures complete fixture schema/registry assembly, including eager templates and prepared field outputs; use the GC profiler to measure its allocation cost. Startup is independent of the execution selector.

Control the repetition count with `-PresolverBenchmarkLoopCount=M`. One overhead JMH operation contains exactly `100 * M` top-level resolutions.

After the measured trial, an untimed reporting pass resolves the 100 queries once more with application observation enabled. It reports average, percentile, and maximum statistics for fields returned, resolvers executed, result depth, and three variable-workload measurements:

- Resolver executions with any variable-bearing arguments, using P50 because the corpus target is a median of at least 10 per query. Higher medians are preferred.
- Variable-bearing arguments per such resolver execution, using P90. An argument is variable-bearing when its open value recursively contains at least one variable.
- Maximum variable stack depth per query, using P50. A dependency edge connects an executed resolver application to another executed resolver application whose result supplies one of the first application's argument variables. Stack depth is the longest such chain, counted in dependency edges; independent or `FromArgument`-only applications have depth zero.

The report also separates active from passive result fields, reports their ratio, counts executed field and type checkers, and describes the fixed registry's active/passive fields per non-Query object, object-fragment recursive selection counts and depths, and resolver/checker/Query-fragment/variable-source feature counts.

For Resolution, each benchmark trial creates one configured dispatcher before any resolution-performing setup, reuses it across every iteration and resolution in the trial, and closes it at trial teardown. Dispatcher creation and cleanup remain outside measured work. Each measured call includes `runBlocking` on that trial-owned dispatcher, the 15-second request timeout, coroutine launch/join work, successor-demand computation, Query-source and result allocation, promise and access checks, and request-local cycle protection. Cycle bookkeeping registers each slot writer and records historical reader-to-writer edges under one graph monitor before a potentially blocking read. The bounded Resolution entry point collects edges without traversing the graph; only its own request timeout triggers an iterative cycle scan. Known writers bypass the pending-reader index and immutable task hashes are cached. The eager checker remains available through `CycleCheckState.create()` for direct startup and coroutine-family controls. The ordinary benchmark uses the operation's no-op `ResolverObserver`, but Resolution still constructs and submits each invocation observation. Variable-argument statistics are computed only when an instrumented consumer reads them. Statistics and full/property benchmark runs configure that same operation observer to collect compact invocation records and generated witnesses; there is no separate observed resolver entry point or model callback. Query-resource loading and parsing, `Assumptions` construction, resolution-witness capture, correctness validation, and statistics traversal are outside the measured method.

To profile only the Resolution measured body, run `./gradlew :core:engine:runtime2:resolutionOverheadProfile -PresolverBenchmarkLoopCount=M --console=plain`. The recording starts after invocation setup and stops immediately after the measured method, so it excludes query parsing, request preparation, the warmup, and the reporting pass. It is written to `core/engine/runtime2/build/reports/resolver-benchmarks/resolution-overhead.jfr`; override that location with `-PresolutionOverheadProfileOutput=PATH`.

`generateResolverBenchmarkQueries` replaces the checked-in query snapshot by running the query generator against the checked-in bulk schema and registry, then appending the deterministic feature selections. Both corpus writers use the same decoration step. `ResolverBenchmarkFixture` assembles that bulk recipe, the checker helpers, and `ResolverBenchmarkFeaturePartition` into one canonical schema and registry; the additional SDL and callbacks live in support code rather than an alternate serialized world. `generateResolverBenchmarkCorpus` writes a new schema, minified gzip registry, and matching query snapshot together. The registry may omit its redundant embedded SDL and use the standalone schema resource when loaded. Their query-generation controls are `-PresolverBenchmarkQueryCount=N` and `-PresolverBenchmarkQuerySeed=S`; ordinary benchmark and profile tasks never regenerate their inputs. Regenerating the snapshot changes the benchmark workload and must be recorded in the performance history.

## StandardViaduct Engine Comparison

`standardViaductBenchmark` executes a separate workload through `StandardViaduct`, stored under `src/jmh/resources/viaduct/engine/runtime2/benchmark/engine-comparison` and adapted from the overhead benchmark's ordered 100-query corpus. Unrelated object fields have globally distinct names (`ObjectN_fieldM`, `ObjectN_hash`); interface-shared `common`, Node `id`, and built-in fields retain their names. Schema metadata, resolver coordinates, output recipes, required selections and provider paths use the same renames. Three argument conflicts on `common`, at query indices 0, 18 and 43, have explicit aliases. All 100 operations validate, preserving all 26,252 field occurrences and every original explicit alias, argument, type condition and repeated selection; aliases rise from 5,669 to 5,672. The operation wrapper preserves stored response keys, allowing compatible repeats to merge. The original tuning corpus and generator replay coordinates are preserved. Earlier timings used blanket aliasing and should not be compared directly with this workload.

Both engines use the same schema, prepared output recipes, resolver object and Query fragments, variable sources, and comparison-specific China-active checker inputs. Identifier fields used by checker RSSes have no field checker. Every field selected by those RSSes and every object type reached through them is unchecked; checker root types retain their client-facing type checkers. Each privacy Query lookup in a checker slot uses its own numbered `benchmarkPrivacyXYZ` field, preventing reuse across distinct checker slots. China lookup fields retain their existing argument-dependent behavior. These adaptations apply only to the engine-comparison harness; the tuning harness retains its original checker fixture. Synthetic resolver-output errors become nulls for nullable types or deterministic valid values for non-null types; ordinary output recipes remain unchanged. The JMH `engine` parameter selects `old` (`core/engine/runtime`) or `new` (`core/engine/runtime2`) by setting `ENGINE2_ENABLED` at service construction.

```shell
./gradlew :core:engine:runtime2:standardViaductBenchmark --console=plain
./gradlew :core:engine:runtime2:standardViaductBenchmark -PstandardViaductBenchmarkEngine=old --console=plain
./gradlew :core:engine:runtime2:standardViaductBenchmark -PstandardViaductBenchmarkEngine=new --console=plain
./gradlew :core:engine:runtime2:standardViaductBenchmark -PstandardViaductNodeCache=disabled --console=plain
./gradlew :core:engine:runtime2:standardViaductBenchmark -PstandardViaductBenchmarkEngine=new -PstandardViaductCycleChecker=nop --console=plain
```

The new-engine comparison accepts `-PstandardViaductCycleChecker=deferred` (default) or `nop`; the JMH parameter is `cycleChecker`. Both modes select a checker through request-scoped GraphQL instrumentation. Deferred mode creates a fresh dependency graph per request and collects edges without scanning them. No-op mode skips graph storage and registration while retaining task/slot construction and caller-owned cancellation; it measures the cost of graph collection rather than all cycle-related work. The control applies only to the new engine; ordinary engine requests retain eager cycle checking. An engine-owned request timeout remains future work. The profile task accepts the same property.

Each fork uses one JMH driver thread; both engines dispatch execution to `Dispatchers.Default`, using the coroutine scheduler's default worker pool unless its JVM properties are explicitly overridden. Trial setup prints the JVM-visible processor count and any `kotlinx.coroutines.scheduler.core.pool.size` / `kotlinx.coroutines.scheduler.max.pool.size` overrides. `viaduct.resolution.threadcount` controls the direct Resolution harness and does not constrain either engine through `StandardViaduct`; these comparisons are not single-thread engine measurements.

The default runs both engines in separate JMH forks. `-PstandardViaductNodeCache=disabled` disables the old engine's per-request node-result cache, including in-flight reuse; `enabled` preserves the default behavior. The JMH parameter is `nodeCache`. Resolver IDs, selectivity, batching metadata, output recipes, query-plan caching, and required-selection plan caching are preserved. The service builder exposes this control as `withNodeResolverCaching(false)`; Runtime2 already uses independent node invocations and ignores the setting. `-PresolverBenchmarkLoopCount=M` repeats the same batch, for `100 * M` service executions per JMH operation. Schema assembly, output materialization, document parsing and validation, a preparation execution of each query, and request construction are untimed. Preparation discovers and caches node outputs separately for each engine, then freezes the node and document caches before measurement. The measured loop includes service and engine execution, per-request node and root-reference construction, GraphQL completion, and Blackhole consumption. Prepared documents use normal GraphQL Java validation and are reused during measurement. These measurements compare execution of this adapted synthetic workload; they do not measure parsing or validation of ordinary client requests.

Preparation reports how many queries return GraphQL errors and prints a sample. `StandardViaductBenchmarkTest` compares both engines' responses for all 100 queries and reports differing indices without treating response differences or GraphQL errors as test failures. Opt in to `-PstandardViaductStrictValidation=true` to reject preparation GraphQL errors in benchmarks and profiles and to reject response differences or GraphQL errors in the corpus comparison test. For a strict untimed comparison, run `./gradlew :core:engine:runtime2:test --tests '*StandardViaductBenchmarkTest' -PstandardViaductStrictValidation=true --console=plain`. This is a validation control; ordinary runs remain diagnostic-only. The existing direct-resolution benchmark retains its original measurement boundary and workload statistics.

`standardViaductWorkloadReport` executes an untimed diagnostic and writes per-query and aggregate sizes plus one representative query/response pair. It defaults to the new engine; select the old engine with `-PstandardViaductWorkloadEngine=old`. Use the same `-PstandardViaductNodeCache=disabled` setting for diagnostics of the old engine without node reuse. It reports original, adapted, and compact query bytes; AST field/argument counts and depth; compact response JSON bytes; returned fields, objects, lists, scalar values, nulls, and depth; actual fixture field/node resolver and field/type checker callback counts; object/Query input getter calls; and distinct versus repeated node resolver IDs per request. Response field counts traverse the client-visible data with list expansion and omit hidden resolver/checker inputs. Callback counters and getter wrappers are installed only for this diagnostic. `field-resolver-calls.json` records actual callbacks by field coordinate and coerced argument map for each query. JSON encoding measures response size outside engine timing. Override the report directory with `-PstandardViaductWorkloadOutput=PATH`.

Fixture field callbacks return prepared outputs without inspecting their input values, but `MockFieldUnbatchedResolverExecutor` invokes both input getters before calling them. The comparison therefore exercises complete declared object/Query input materialization in both engines: Runtime2 prepares inputs before executor entry, while the old engine's suspending getters materialize them during mock executor entry. An experiment with unread inputs would require an executor that deliberately skips those getters; it is a different workload.

The untimed report also counts stored-fragment versus wrapped-operation aliases. `checker-calls.json` records checker kind, coordinate, arguments and execution attribution for each query; old-engine entries include the execution path, request-local parent-object identity, containing field arguments and originating input-plan kind. The input-plan kind records which execution claimed the result first; it does not prove that no other consumer needs the check. Object identity labels and first-claim origins can vary with scheduling. These observations are absent from ordinary JMH runs.

`standardViaductProfile` records only a measured new-engine invocation after one unrecorded warmup. Trial preparation, parsing/validation, and request construction remain outside the recording. It runs one fork and one measurement; use `-PresolverBenchmarkLoopCount=M` to collect more samples over `100 * M` requests. The default output is `reports/resolver-benchmarks/standard-viaduct.jfr` under the project build directory; override it with `-PstandardViaductProfileOutput=PATH`. Recording is disabled in ordinary comparison runs. Use the same JFR views and export script as the other profiling targets; profiled timings include recording overhead.

```shell
./gradlew :core:engine:runtime2:standardViaductWorkloadReport --console=plain
./gradlew :core:engine:runtime2:standardViaductProfile -PresolverBenchmarkLoopCount=10 --console=plain
```

## Guarded Checker Diagnostic

`guardedCheckerResolutionBenchmark` executes a focused query whose registry-defined resolver chain contributes one active `@include` path and one active `@skip` path at every level before reaching a terminal field checker. Its `depth` parameter is 3, 6, 9, or 12. Increasing this parameter changes the registry and its fixed transitive demand, so this diagnostic detects regressions that distribute the compact Boolean-condition DAG but is not evidence that a client can create superlinear work by growing a request against one fixed registry. Keep it while the superlinear investigation needs a sensitive comparison; decide whether it belongs in the maintained suite after the repairs close.

## Correct Resolution Benchmark

`correctResolutionBenchmark` loads the checked-in benchmark schema and registry, generates 50 distinct queries from a fixed seed, and prepares one completed Resolution result, `SharedOperationContext` with completed variable bindings, and grounded root `ObjectSelectionForest` per query during trial setup. Setup also verifies each prepared judgment once. The measured method invokes only `correctResolution` over the prepared corpus and consumes each Boolean result; query generation, parsing, Resolution execution, witness capture, fragment merging, binding instantiation, and every other validation remain outside measurement.

Control the input corpus with `-PcorrectResolutionBenchmarkInputCount=N` and `-PcorrectResolutionBenchmarkQuerySeed=S`, and repeat the prepared corpus with `-PcorrectResolutionBenchmarkLoopCount=M`. One JMH operation contains exactly `N * M` correctness judgments. The prepared results and operation contexts are reused because `correctResolution` is read-only; changing that purity contract requires changing the benchmark setup.

Each correctness judgment scopes resolver replay and completed-output-demand memoization to its own validation state. Output demand is reconstructed from result cells, with object and list subtrees cached by identity and parent backedges excluded. A fresh judgment reconstructs demand again, including any fields completed since an earlier judgment.

To profile only the correctness judgments, run `./gradlew :core:engine:runtime2:correctResolutionProfile --console=plain`. This runs one unrecorded warmup iteration, then starts a JFR recording after trial setup and immediately before the single measured iteration. The recording therefore excludes query generation, Resolution execution, correctness-witness preparation, and the warmup. It is written to `core/engine/runtime2/build/reports/resolver-benchmarks/correct-resolution.jfr`; override that location with `-PcorrectResolutionProfileOutput=PATH`. Resolver and object-materialization frames can still legitimately appear: `conformsToResolvers` invokes each activated field resolver as part of the correctness judgment.

Inspect the recording with `jfr view hot-methods core/engine/runtime2/build/reports/resolver-benchmarks/correct-resolution.jfr`, `jfr view allocation-by-site core/engine/runtime2/build/reports/resolver-benchmarks/correct-resolution.jfr`, and `jfr view gc-pauses core/engine/runtime2/build/reports/resolver-benchmarks/correct-resolution.jfr`.

## Property Test Benchmark

`propertyTestBenchmark` replays one checked-in snapshot of Resolution broad campaign round 46's `symbolic-identity` case at `S=10 R=4 Q=3`. The resource records property seed `2026081300464`, the exact generated schema, executable registry recipe, and exact query source. It therefore remains the same workload when property-test generators, profiles, and random-consumption order change.

One measured property case creates a fresh immutable `Assumptions` value and semantic operation context, parses the frozen query, invokes Resolution, runs `correctResolution`, reconstructs and compares all 12,777 resolver-application identities, and validates from-field bindings. Identity reconstruction reuses reference ownership established by that case's successful correctness judgment, avoiding a second resolver-conformance replay; ordinary application identities and inputs are still reconstructed independently. The standalone identity oracle performs its own ownership replay. Resource decoding and `TestWorld` assembly happen once during trial setup. Two warmup cases precede five measured cases. Repeat the frozen case within each measured JMH operation with `-PpropertyTestBenchmarkLoopCount=M`; the default is one.

To profile the full measured property case, run `./gradlew :core:engine:runtime2:propertyTestProfile --console=plain`. This runs one unrecorded warmup case, then records one measured case to `core/engine/runtime2/build/reports/resolver-benchmarks/property-test.jfr`. Override the output with `-PpropertyTestProfileOutput=PATH`, and repeat the case inside the recording with `-PpropertyTestBenchmarkLoopCount=M`. The recording includes `qplan.PropertyTestPhase` duration events for request preparation, Resolution, witness snapshotting, application-identity reconstruction, `correctResolution`, and from-field binding validation.

`generatePropertyTestBenchmarkCorpus` is the provenance-preserving snapshot writer, not part of ordinary benchmark execution. It regenerates the historical coordinate through the current property generator and will intentionally fail if that generator no longer reproduces 12,763 applications. Do not regenerate the checked-in snapshot when generator evolution changes the coordinate; the benchmark's purpose is to retain the original serialized workload.

## Corpus Search

Run `./gradlew :core:engine:runtime2:generateResolverBenchmarkCorpus -PresolverBenchmarkCorpusSeed=S -PresolverBenchmarkCorpusSize=Schemas:Registries:Queries`. The task writes the winning schema and registry together with the exact overhead query snapshot selected by `-PresolverBenchmarkQueryCount=N` and `-PresolverBenchmarkQuerySeed=S`.

The default search evaluates 10 schemas, 5 registries per schema, and 10 random queries per pair. Search generation exposes controls for object-output frequency, scalar-biased nested query breadth, ordinary and long-tail object-fragment selection counts, and argument-field preference inside object fragments.

The search uses Resolution to measure actual expanded result size, depth, resolver and checker applications, variable-bearing resolver activation, variable stack depth, owner dependencies, and query diversity. Registry eligibility targets roughly two active and fourteen passive fields per non-Query object, an overall passive/active field ratio between 4:1 and 7:1, object fragments averaging 3.5–5 recursive selections with P90 at least 10 and maximum at least 30, Query fragments, and all four variable-source kinds. Workload eligibility requires at least 300 average result fields, at least 100 average resolver executions, actual activation of all four variable-source kinds and both checker families, and nonzero stacking; scoring then targets roughly 1,000 fields and 300 resolver executions while strongly rewarding a median of at least 10 variable-bearing resolver executions. Resolution timeouts and resolution-witness bound overflows disqualify a candidate. The winner is written under `src/jmh/resources/viaduct/engine/runtime2/benchmark/current-profile`; the SDL is human-readable, while Jackson stores the executable registry and query-generation recipe as explicit tree DTOs.

## Benchmark Workload Contract

- Runtime coverage requires at least three distinct queries per supported feature category. The categories and observation predicates live in `ResolverBenchmarkCoverage`; a registered feature alone cannot satisfy the gate. Coverage is checked during the untimed reporting pass and the frozen-corpus regression test. The corpus is synthetic and makes no production-frequency claim.
- The expensive schema/registry search is offline and reproducible. It writes one winning GraphQL SDL schema and one JSON registry recipe as checked-in resources; benchmark invocations do not repeat that search.
- An ordered batch of 100 exact query sources is checked in; regeneration permits 100–250. Each invocation parses and prepares that fixed corpus outside the measured method and executes it `M` times.
- Every measured invocation reuses one parsed schema and resolver registry across its `100 * M` resolutions, so static decoding and registry assembly are never part of per-resolution timing. Each resolution receives a fresh `SharedOperationContext`, whose variable bindings are monotonic per-operation state and must not leak across resolutions; setup currently also constructs a fresh immutable `Assumptions` value. The public resolver entry obtains a fresh root Query object from `ResolverRegistry.createRootQueryInput()`.
- The timed loop contains resolution and Blackhole consumption, including Resolution's ordinary runtime instrumentation described above. Query-resource loading and parsing, setup, witness capture, correctness validation, and statistics reporting remain untimed.
- Overhead field callbacks return fixed prepared outputs and node callbacks perform prepared ID lookups. Callback output materialization and input-sensitive fixture fingerprints are untimed; engine-owned input materialization, output lowering, and demand projection remain timed. Other benchmarks and generated correctness tests retain the original resolver programs.
- Queries should be deep, with paths reaching about ten layers, and large enough to return a few hundred fields on average with a bounded list-derived tail, without making one JMH operation excessively long.
- A representative non-Query object should have about two active fields and fourteen passive fields. The ten additional feature objects each retain exactly that shape, alongside the thirteen bulk objects; policy helpers are reported separately. The accepted overall schema ratio is approximately five passive fields per active field, with the search currently allowing 4:1 through 7:1.
- Bulk resolver object fragments should average about four recursive selections and have a long tail: P90 at least 10 and maximum at least 30. Fragment depth is measured separately; reports distinguish the bulk distribution from the combined registry, whose feature and policy helpers also include empty fragments.
- The workload must activate `FromArgument`, `FromObjectField`, `FromQueryField`, and `FromProvider` variables in complex combinations, plus both checker families. At least 10 resolver instances in the median query should have one or more variable-bearing arguments; the number of variable-bearing arguments per such resolver remains a reported characteristic rather than a hard target.
- The workload should execute a few hundred resolver instances per query rather than the earlier roughly 2,000-instance shape. Field count remains mostly list-derived, while non-list fields and result depth are reported to make that expansion legible.
- The report must include average, requested percentile, and maximum values for result fields, active and passive fields, passive/active ratio, resolver and checker executions, variable-bearing resolver executions, variable-bearing arguments per such execution, stack depth, result depth, schema active/passive fields, object-fragment selection count and depth, and registry feature counts.

## Feature Sections

Sixteen short selection sections are appended to three different generated queries each. The remaining queries retain the broad generated workload. Dedicated failure sections cover field and type denials, null and error provider traversal, null argument traversal, and excluded demand. Successful and failing activations are reported separately. Ten additional objects preserve the ordinary two-active/fourteen-passive shape; recursive input types, abstract types, and Query entry points support these sections without introducing a separate schema or registry.

Parent sections exercise three ancestor links, interface-typed parents, diagonal demand, source-supplied active descendants whose standard resolvers are skipped, resolver-supplied parent fields that cannot override structural ancestry, and mixed argument/object/Query/provider variables in a resolver reached through a parent. Reference sections exercise namespaced targets, scalar reference tails, enum, concrete, interface and union outputs, list-element publication, normal registered-resolver fallback, source-reference override, and target Query fragments with argument and Query-field variables. Checker sections include raw parent traversal, nested object-path variables, argument traversal and argument errors, Query-field and callback-provider variables, callback-provider conditions on both input roots, raw resolver inputs, duplicate populated named pairs, named-empty pairs, and successful or denying outcomes.

The explicit variable section creates a four-edge acyclic dependency chain between executed resolver argument values. Separate sections exercise nested and nullable input traversal, nested variable expressions in input objects and lists, runtime singleton coercion, abstract provider paths, variable use beneath passive descendants, and distinct symbolic expressions that converge to the same grounded arguments. These additions exercise each capability a few times while retaining the bulk workload's size and depth. Mutation ordering, nested execution, cancellation, cycles, and concurrency pressure require their separate contracts or benchmarks and remain outside this measurement.
