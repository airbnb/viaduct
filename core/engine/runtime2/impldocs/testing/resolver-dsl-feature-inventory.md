# Resolver DSL Feature Inventory

## Scope

This inventory compares the [current DSL](resolver-dsl.md) with the schema and registry declarations in the native Resolution feature contracts and focused tests. It identifies useful scripted declaration capabilities; universal DSL migration is not a goal. Kotlin assertions, execution harnesses, generated-world construction, and fixtures whose native boundary is the subject remain in Kotlin.

The primary entry points are [ResolverContractTest](../../src/test/kotlin/viaduct/engine/runtime2/resolution/ResolverContractTest.kt), its precomputed-construction-demand variant, and [CoroutineResolveTest](../../src/test/kotlin/viaduct/engine/runtime2/resolution/CoroutineResolveTest.kt), together with the focused suites under `src/test/kotlin/viaduct/engine/runtime2/resolution`. The audit also checks the other native contract fixtures for reusable declaration patterns. The [shared Engine API feature contracts](../../../api/src/testFixtures/kotlin/viaduct/engine/runtime/execution) provide a secondary check for capabilities hidden by the native harness.

The distinction between a declaration gap and a test-boundary requirement matters: some tests deliberately construct or corrupt a registry, supply a custom engine object, or assert the exact object passed through an adapter. Converting those fixtures through a validating script adapter can remove the behavior being tested.

## Existing Capabilities

The DSL already supports nonselective and selective field and node scripts, field and concrete-type checker scripts with explicit allow/deny outcomes, named paired checker inputs, object and Query required selections, field arguments, computed variables providers, object-rooted path variables, concrete and abstract objects, lists, nulls, ordinary scalar and enum outputs, explicit error outputs, nested queries and mutations with ordinary input values and named fragment documents, and root-field references. Ordinary GraphQL selection syntax supplies aliases, inline fragments, conditions, namespaces, and `@parent` traversal within the engine's existing restrictions. Mutation field declarations also work; [MutationResolutionTest](../../src/test/kotlin/viaduct/engine/runtime2/resolution/MutationResolutionTest.kt)'s `inactive payload dependencies do not prevent the next mutation` already uses the DSL.

RSS object views carry the read-only `"**FROM_RSS**"` metadata key recursively. Field and Node resolver outputs reject marked maps, including nested reuse and copies retaining that key, before conversion or selective projection. Scalars can be copied into fresh maps. Explicit query/mutation results and GraphQL input-object arguments are unmarked; direct subquery-object returns retain adapter-specific alias validation. Empty checker RSS objects contain only the marker, while a checker with no input pairs still receives an empty `inputs` map.

`TestWorld.fromDSL` also accepts Kotlin field- and type-checker maps for policies, applicability, exact identities, and host effects that remain outside scripts. DSL and Kotlin checker declarations may coexist at distinct coordinates; duplicate coordinates are rejected. A fixture using that entry point can therefore still contain substantial registry construction outside its schema. Other tests start with a DSL world and subsequently replace resolver definitions. Neither pattern means that all declarations are expressible in the DSL.

### Checker Details That Must Survive Compilation

The DSL compiles through the production factories [FieldCheckerResolver](../../src/main/kotlin/viaduct/engine/runtime2/model/registry/FieldCheckerResolver.kt), [TypeCheckerResolver](../../src/main/kotlin/viaduct/engine/runtime2/model/registry/TypeCheckerResolver.kt), and [CheckerResolverBase](../../src/main/kotlin/viaduct/engine/runtime2/model/registry/CheckerResolverBase.kt).

- A field checker receives the checked field's grounded arguments and a map of named `CheckerInput` pairs. A type checker receives the pairs without a field argument tuple.
- Each pair owns an object fragment, a Query fragment, and its variable declarations. A variable is shared across both fragments within its pair; equal external variable names in different pairs remain independent. Pair names also preserve independent response-key projections.
- Zero named inputs produces an empty `inputs` map. A named pair with empty fragments retains its name and exposes empty object values for both roots.
- Checker providers run per named pair and reuse the existing error-free input conversion: provider failure fails bindings; it never makes an error into a variable's data value.
- Checker-origin reads use raw values. Entering an ordinary value resolver restores checked reads at the appropriate boundary. A checker Query callable must use its own `ResolutionExecutionContext`, preserving this behavior and task ownership.
- Success, explicit denial, and a thrown callback failure need distinct tests. Policy-sensitive denial additionally uses `CheckerResult.Error.isErrorForResolver(CheckerResultContext)` and `combine`; a Boolean checker result alone cannot represent every existing case.
- Type-checker applicability is a separate metadata predicate evaluated before its provider and input demand. The native hooks depend on root/path and sometimes the request `EngineExecutionContext`; a conditional inside the checker body would execute too late.

The suites named `SelectiveFieldCheckerExactnessContract` and `SelectiveTypeCheckerExactnessContract` test checker demand propagated into selective value producers. They do not call for a new selective-checker interface.

### Variable Details

Automatic argument inference covers a whole argument under the same variable name. Explicit `variables` declarations override inference and compile to `FromArgument` or `FromField` with their original provenance; they do not simulate those sources with computed providers. Existing `pathVars` remains an object-fragment shorthand, even when the consumer is the Query fragment.

The explicit source description contains exactly one of `fromArgument`, `fromObjectField`, or `fromQueryField`, each with a nonempty path. It reuses existing path compilation for aliases, argument-bearing selections, inclusion guards, and legal traversal. Tests cover null argument traversal, variables used in both fragments, and conditional Query paths. Checker pairs reuse these declarations with their own owner targets; type checkers reject `FromArgument`.

Replacing a renamed or nested `FromArgument` declaration with `vars: {script: ...}` can give the same numeric answer while deleting the binding-source assertion that the original test was meant to establish. [ResolverBindingSourceTest](../../src/test/kotlin/viaduct/engine/runtime2/resolution/ResolverBindingSourceTest.kt), [ResolverFromFieldBindingOracleTest](../../src/test/kotlin/viaduct/engine/runtime2/resolution/ResolverFromFieldBindingOracleTest.kt), and [FromFieldExclusionTest](../../src/test/kotlin/viaduct/engine/runtime2/resolution/FromFieldExclusionTest.kt) make that distinction observable.

### Demand And Node Details

D5 composes a nonselective script result with the existing `snipToDemand` helper when `isSelective: true`, preserving its handling of canonical fields, nested selections, concrete types, and arguments. Node scripts register with the corresponding selective or nonselective mode; projection does not erase their distinct ID-only loading behavior. Scripts need not inspect demand for that projection. Existing observers retain supplied-demand assertions independently of the returned value. Fixtures that inspect or forward supplied demand retain native callbacks.

The current finite `@nodeResolver(ids: ...)` declarations are sufficient to enumerate the IDs used by the fixed native scenarios. A per-concrete-type lookup that accepts arbitrary IDs would preserve the generality of Kotlin node functions such as `dispatches argument-bearing abstract node lists`, without enumerating query-derived IDs. Treat that as a useful extension, rather than a blocker for that fixed test. Keep routing untyped `Query.node(id:)` requests distinct from dispatching a reference whose concrete Node type is already known; relaxing global ID uniqueness requires an explicit routing policy.

Ordinary object/list construction, scalar values, Node reference maps, and `ref(...)` are already available. Direct demand inspection and host metadata remain native; ordinary selectivity uses output projection.

D7 reuses error-free input conversion for String IDs, Boolean, finite Double, enum-name, list, and input-object values. Named-fragment documents use the existing document expansion path; retaining named spreads preserves fragment expansion as a test subject. D8 migrations in `FieldCheckerLifecycleTest`, `TypeCheckerLifecycleTest`, and `TaskObservationTest` preserve independent creator and lifecycle observations. Focused DSL tests cover checker raw reads and checked boundaries, native checker mutation rejection, selective and nonselective node queries, and ordered nested mutations.

## Host-Fixture Inventory

Shared bindings supply the script-level escape hatch for test-owned values and synchronous effects. The map is supplied once and its objects are shared across callbacks and executions; there is no per-invocation factory. Engine arguments and required-selection inputs remain invocation-local. Bound public helper classes are accessible without exposing arbitrary classes globally, and existing script conversion, error handling, and execution contexts still apply. Do not add production instrumentation to support these fixture declarations. Scheduling controls, assertion callbacks, and recording mechanics stay at their existing boundaries.

Deliberately invalid fixtures need particular care. `PassiveValueResolutionLogicTest` supplies unknown or argument-bearing output keys and an object whose getter fails if an undemanded field is read. Likewise, malformed provider-map cases test the engine's handling of missing/extra bindings, while the script adapter already validates provider result shape. Keep the raw callback or carrier at the boundary being tested; a validating DSL conversion can reject the fixture too early. Registry-factory validation tests and oracle mutations similarly retain their direct construction or corruption step.

## Shared Engine API Cross-Check

The shared contracts confirm D1–D8 and expose integration requirements beyond the native DSL. [FromFieldVariablesContract](../../../api/src/testFixtures/kotlin/viaduct/engine/runtime/execution/FromFieldVariablesContract.kt) exercises both variable roots and argument paths; [AccessCheckExecutionContract](../../../api/src/testFixtures/kotlin/viaduct/engine/runtime/execution/AccessCheckExecutionContract.kt) adds named checker inputs, conditional RSS callbacks, policies, and providers; selective field/node contracts exercise structured demand; [SubqueryExecutionContract](../../../api/src/testFixtures/kotlin/viaduct/engine/runtime/execution/SubqueryExecutionContract.kt) adds ordinary GraphQL variable values and nested mutations.

Their bootstrap, executor SPI, scoped-schema, and GraphQL completion coverage must survive. Replacing `EngineTestModule` setup with a native `TestWorld` would test a different entry path. `EngineTestModule.fromDSL` adapts the shared DSL into that harness, retaining the contract's `TODO`/`ALT`/`N/A` classifications and executor observations. The native fixture compiler remains independent.

The interpreter and metadata parser live in Engine API test fixtures (`viaduct.engine.api.testing`), with no Runtime2 dependencies. They own JEXL preparation, permissions, source diagnostics, coroutine bridging, bindings, read-only views, input-value validation, standard checker outcomes, and plain declaration parsing. Runtime2 retains registry compilation, schema lowering, errors/references, output alias checks, selection execution, and `snipToDemand`. `EngineTestModule.fromDSL` builds Engine API field/node/checker executors and RSS variable graphs through the existing bootstrap path. Both engine runners retain their support classifications. The access-check dependency-read throwing-checker sample uses JEXL `throw` with its original result/error assertions; a separate dependency-denial sample uses `denyWithMessage`.

Demand inspection/forwarding, provider callbacks with their own RSS inputs, and batch-wide inputs/results retain native Kotlin fixtures. Native `vars` supplies a single argument-based provider; it does not model every Engine API variables-provider plan. Keep provider input selections and execution conditions at their native boundary instead of turning them into ordinary field dependencies. These cases do not require additional script capabilities.

The Engine API migration stress pass exposed two fixture requirements. A module must combine scripted declarations with native executor registrations: `EngineTestModule.fromDSL` accepts an optional trailing `MockTenantModuleDSL` block using the same stripped schema. Field resolvers, Node resolvers, field checkers, and type checkers merge independently, with duplicate declarations rejected. A native checker can accompany a scripted resolver and conversely. The API adapter also omits the parser's minimal built-in schema and uses its existing schema factory, retaining `Query.nodes` and default scope metadata. These changes let ordinary declarations migrate without replacing batch callbacks, provider-owned RSS, custom policies, or lifecycle controls. The stress migrations remain separate from the committed DSL extension.

Shared Engine API suites often reuse a larger schema while changing executor registrations per test. The current combined schema/declaration input forces those migrations to duplicate schema text; this is a fixture integration gap, not a scripting-language limitation. Per-test scripted declarations should be attachable to a shared schema before adopting those bulk migrations. Native Runtime2 worlds can retain their self-contained schema and registry declarations.

The following are not solved by DSL syntax: physical batching/cache behavior, scoped versus full schema wiring, custom-scalar or asynchronous-EOD support, subscriptions, unsupported mutation namespace checkers, reference-target checker enforcement gaps, and intentionally invalid adapter/bootstrap fixtures. Their current support boundary is documented in [Feature Tests](../integration/feature-tests.md) and [Engine API Integration](../integration/engine-api.md). Tests whose subject is an API wrapper, data loader, registry factory, or adaptation boundary should keep exercising it directly.

## Further Migration

Field/type checker declarations, named pairs, standard checker outcomes, explicit variables and pair-local providers (D1–D4), scalar outputs (D6), selective field/Node output projection (D5), nested execution inputs/fragments/callbacks (D7–D8), and shared script bindings (H1) are available. Future migration can use bindings for provider counters, ordinary snapshots, and configurable synchronous effects where declarations become clearer. Custom policies, lifecycle mechanics, identity-sensitive contracts, and direct construction at a tested boundary retain their Kotlin fixtures; no additional DSL hooks are required for those cases.

Migrations preserve result shape, aliases, error/null positions, variable-source identity, raw/checked demand, exact applications, and lifecycle assertions. A script spelling is useful only when the existing scenario can use it without weakening those claims. Not every eligible fixture needs to migrate.
