# Normalized Document Schema-4 Benchmark

`NormalizedDocumentSelectionBenchmark` compares Runtime2's current operation conversion with a candidate based on graphql-java [PR #4562](https://github.com/graphql-java/graphql-java/pull/4562), pinned to commit `69c7bfbef920e5b95b7c295b60ef0652523eef3d`. It uses only the upstream `large-schema-4.graphqls` and `large-schema-4-query.graphql` fixtures already checked into `src/jmh/resources`. Graphql-java counts 259,832 field occurrences after fragment expansion; Runtime2's construction forest contains 187,215 selections after introspection fields are erased. This is intentionally a stress workload.

The candidate walks the validated `NormalizedDocument` graph and constructs a `SelectionForest` directly, without allocating Viaduct `SpecSelection` or a separate materialization tree. Each candidate conversion uses a new identity cache of `ObjectEngineResult.Key` values by shared normalized field, so a field reused through fragment spreads has its arguments decoded once per conversion. The cache is not retained across benchmark invocations. Trial setup recursively compares the candidate and current construction forests by key, applicability set, inclusion condition and nested members; a mismatch fails each fork before measurement. This equivalence check covers the schema-4 query, not all possible operation semantics or mutation materialization.

The six cases are `validateBaseline` (validation with normalized-document creation disabled), `validateNormalized` (enabled), `convertAst` (current validated AST to construction forest), `convertNormalized` (prebuilt normalized document to construction forest), `validateAndConvertBaseline` and `validateAndConvertNormalized` (fresh validation followed by the respective conversion). The complete paths quantify the net preparation difference. Cases are independent measurements; their scores need not add exactly because JIT, cache and allocation behavior differ. Parsing, schema creation, variable coercion and execution are outside the timed region. Validation uses `QueryComplexityLimits.NONE` because this query exceeds graphql-java's default field-count threshold.

The repository pins the PR dependency for all modules. The main source set contains the [ND-backed integration](../integration/normalized-document.md); no opt-in source sets or mixed graphql-java classpaths are used. The eager AST reference lives in unpublished test fixtures. Following API unification, that reference also uses the unified forest model, so it is not the exact pre-migration AST baseline. Historical measurements retain their own source snapshots and must be attributed to those revisions.

From the pinned graphql-java PR worktree, build the jar with `./gradlew buildFinalJar`. From the Viaduct root, run `core/engine/runtime2/scripts/with-graphql-java-pr.sh /path/to/graphql-java-0.0.0-HEAD-SNAPSHOT.jar :core:engine:runtime2:jmhJar --no-configuration-cache`. The helper supplies a temporary Maven repository to all included builds. On Hetzner, run `run-normalized-document-benchmark.sh JMH_JAR RESULT_DIRECTORY`; transfer `selection-forest-benchmark-host-settings.py` beside it. The runner locks the server, saves/restores governors and service states, records jar/host metadata, and captures JMH JSON plus allocation metrics.

There are six methods and two forks, for 12 forks. Every fork schedules two 30-second warmup iterations and three 60-second measurement iterations: `6 × 2 × (2 × 30 + 3 × 60) = 2,880 seconds`, exactly 48 minutes. JVM startup, schema construction in trial setup, forest equivalence checks and reporting add wall-clock time. The runner enforces a 70-minute JMH deadline plus up to 30 seconds for forced termination, and verifies that all six case results are present.

## Shared Forest Consumption

`NormalizedDocumentBackedForestBenchmark` adds four cases on the same schema-4 query. `startNormalized` creates only a request-local ND-backed root view. `consumeAst`, `consumeNormalizedEager`, and `consumeNormalizedShared` each create a fresh forest and recursively visit all 187,215 logical selections, returning their count. The shared case retains child references and caches request-local field decoding; its traversal still visits repeated occurrences. Setup compares all three representations by key, applicability, inclusion condition, and recursive shape, and verifies that creating the shared root decoded no fields. Parsing, validation, schema construction, variable coercion, resolver execution, and response completion are excluded from these cases. Initial-view timing must not be presented as complete execution or complete consumption cost.

Build with the same script, then run `run-normalized-document-benchmark.sh JMH_JAR RESULT_DIRECTORY backed`. Four cases and two forks schedule `4 × 2 × (2 × 30 + 3 × 60) = 1,920 seconds`, exactly 32 minutes of timed iterations. Startup, setup, and reporting add wall-clock time. This suite has a 50-minute wall-clock deadline plus 30 seconds for forced termination. Omitting `backed` retains the original six-case, 48-minute suite.

## Migration Comparison

The `baseline` suite runs only `consumeAst` from the preserved pre-migration benchmark jar; `unified` runs only `consumeNormalizedShared` from the current jar. Each suite schedules eight minutes (one case, two forks, two 30-second warmups and three 60-second measurements). Run them sequentially on the same server for sixteen scheduled minutes plus setup. Each has a fifteen-minute deadline and records its jar hash. This preserves the real old two-forest implementation as the baseline instead of silently benchmarking the new unified model through the AST reference parser.
