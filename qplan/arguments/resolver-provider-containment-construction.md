# Argument for [resolver-provider-containment-construction]

This claim concerns the pre-reasoning Kotlin fixture and registry construction boundary, not semantic variable execution or the TLA+ refinement boundary. Every canonical `FieldValueResolver` has one fixed open parent-object fragment; its optional Query-rooted fragment is outside this object-provider claim. Node-valued source fields retain their coordinates and arguments, while the built-in `Query.node` dispatcher has an empty object fragment; genuine field-relative variables on a source resolver are therefore constructed against the unchanged canonical producer coordinate.

Pre-reasoning composition resolves each provider's response-key path against its alias-preserving object-fragment source, rejects lossy type conditions and ambiguous canonical occurrences, and emits an alias-free key path. `resolverRegistryOf` requires that path to match an occurrence path in its defining resolver's fixed fragment with exact keys. Registry extension consequently traverses one defining envelope and no longer computes or roots a separate `extendedVariables` fragment. The arbitrary generator explicitly inserts every chosen aliased provider path into that envelope before emitting its variable use, then invokes the same compiler used by static fixtures.

Focused `FromObjectFieldTest`, `ResolverDemandTest`, and `BranchOrderInvariantTest` cases reject absent, wrongly rooted, lossy, canonically ambiguous, argument-distinct, overlapping, and cyclic provider paths. Generator tests exercise the same compilation and ordering boundary. Resolver26 consumes the compiled provider metadata at runtime within its documented domain.
