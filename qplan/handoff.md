## Source And Lowered Schema Boundary

Fixture composition retains two distinct schemas:

- The source `GraphQLSchema` owns external GraphQL parsing, validation, source spread rules, source output types, coercion where required, and response completion.
- The canonical lowered `ViaductSchema` owns qplan fields, types, selections, resolver registry entries, conformance checks, values, and subtype reasoning. Source-backed definitions retain exact source GraphQL-Java EOD witnesses; synthetic typename definitions remain model-internal.

`GJSchema.fromSDL` parses and validates the source schema and lowers it to the final canonical `ViaductSchema`. `SourceSchemaAdapter` is the explicit source-to-lowered boundary and requires the canonical source/lowered fixture pair. Node-valued source fields retain their schema coordinates. Source-shaped node references are normalized to root-field references targeting the built-in `Query.node`; that resolver decodes the concrete type and original ID and dispatches to the matching node resolver. Typename remains compiled into ordinary synthetic field resolvers before semantic reasoning.

## Current Semantic Capabilities

All maintained resolvers support source-sensitive ownership of argumentless registered fields: an ancestor output may supply such a field passively, while an absent field uses its standard resolver. Fields with arguments are always active. The exact contract and resolver support matrix live in [`semantics/testing-contracts.md`](./semantics/testing-contracts.md).

Resolver22/23 and Resolver26 support `@parent` fields. Schema preparation validates an argument-free singular parent field and maps it to its unique argument-free child producer; child producers may return singular objects, lists, or nested lists. Resolver input validation rejects variables on every concrete branch reachable beneath a parent selection, including parent fields retargeted from abstract coordinates, while allowing variables guarded by concrete branches disjoint from all parent retargets. It otherwise preserves selective-resolver support. Each child parent cell points to its actual containing ancestor OER, but EOD materialization creates a fresh finite parent projection rather than preserving resolver-visible object identity. One-level demand lifting composes for grandparent selections. Conservative lifting may over-resolve or over-materialize ancestor demand when an active grandchild field is dynamically passive; this is an accepted tradeoff for the uncommon overlap of those features. The focused Resolver26 parent property test classifies exact variable-bearing argument selections reached across resolver boundaries beneath parents by fragment, depth, and binding-source combination, and measures diagonal dependencies in which a resolver selected below one parent independently requires its own parent.

Resolver01–03, Resolver06–08, and Resolver21 require a schema with no `@parent` fields, including unselected fields, as an input precondition. They do not validate or define rejection behavior for out-of-domain schemas. Parent-induced dependencies can require an ancestor resolver to re-enter the same still-open descendant occurrence, which cannot be represented by their local sibling ordering without adding occurrence-aware suspension or graph re-entry machinery. The maintained depth-first versions stay small for comparison and future proof work; [`examples.md`](./examples.md#why-the-depth-first-resolvers-do-not-support-parent) contains the concrete counterexample.

Resolver26 closes each OER once. Successor demand statically transposes descendant parent demand into selective producer output, while construction-demand closure independently discovers parent-induced construction demand in requested descendants and reachable resolver inputs and transposes it across matching producer edges. Passive resolution therefore passes construction demand unchanged into each returned OER rather than mixing in successor invocation demand. This makes all ancestor work discoverable before child construction while retaining source-sensitive suppression of standard resolver demand. Every OER freezes after its one local launch cycle.

Resolver02/03, Resolver07/08, Resolver22/23, and Resolver26 support Query-rooted resolver fragments through one associated Query OER per containing orchestration. Applications share exact value production in that scope while retaining response-key-preserving occurrence-local projections; correctness validates the unioned shared result once and each owner projection separately. The general distinction between variable producers and fragment consumers is defined in [`semantics/README.md`](./semantics/README.md#variable-production-and-consumption): `FromObjectField` and `FromQueryField` choose the provider fragment, while either the object fragment or Query fragment may consume either binding. Resolver26 implements both provider kinds and all three consumption shapes.

All maintained resolvers now support symbolic root-field references whose arguments are grounded and variable-free. A reference is executed only when its source position is demanded; a reference-bearing field omitted from non-selective demand is skipped entirely, including when the reference is a list element. Source presence takes precedence over registry membership, so a reference supplied for an argumentless registered field suppresses that field's standard resolver and input demand. Every hop uses a fresh empty Query OER for identity, the descriptor's canonical path and grounded arguments, and an empty object input typed as the target's containing type. Targets must have empty object fragments. Resolver01-23 admit only `FromArgument`; Resolver02/03, Resolver07/08, and Resolver22/23 also execute target Query fragments, while Resolver03/08/23 supply full successor demand. Each target remains an independently rooted execution, and declared fragments reached inside it use singular sharing. Direct reference results are followed as tails. Dynamically returned infinite tails retain ordinary tenant-code recursion semantics, like recursive `ctx.query()`; qplan does not add a reference-specific detector, while registry validation rejects declarative RSS cycles. Resolver01-08 perform each hop inline before continuing depth-first sibling work; Resolver21-23 perform it under their existing structured coroutine scope. Referenced composite outputs retain detached descendant OERs for ordinary active resolution even though their symbolic source cannot be structurally revisited.

Unlike production's object-only `LazyEngineObjectData` representation, a qplan reference target may return a singular scalar or enum as well as a composite object because the resolved value is published directly into the consumer cell. Ordinary abstract targets are admitted conservatively before invocation only when all of their possible concrete object types belong to the consumer's possible object types; partial overlap is rejected. A canonical `Query.node` reference instead uses the validated concrete type encoded in its ID for that same conformance check, while the resolved runtime value is still checked against the consumer field type. Every resolver family retains the originating node ID as authoritative when node dispatch returns another root-field-reference tail. Resolver26 reference targets may additionally retain `FromQueryField` and provider variables, and namespace-relative requirements must be written as Query RSS with the Query-to-namespace path prefixed.

Resolver26 implements that common behavior through its conditioned passive occurrences, `FieldResolverTask`, and `FieldResolutionLogic`. After ordinary active-field demand reaches its fixed point, each object orchestration scans its directly demanded source fields once for reference carriers; closure itself can add active fields but cannot create new references. `ValueSourceOccurrence` carries the publication selection, path, expected type, and construction demand. Each OER with active work launches its own request-root orchestration task, while a passive OER with no work freezes synchronously. The orchestration root is retained as an explicit placeholder and ownership boundary for possible future asynchronous orchestration; the current implementation does not require it to suspend, and its undispatched body synchronously installs each publication through `FieldResolverTask.launchAll`, launches its request-root field tasks, freezes the OER, and completes. Each field task owns setup and launches its Query-fragment and object-provider producers as children of its field scope. `FieldResolutionLogic` holds the concrete task as a constructor property and handles ordinary object fields, object-field references, list-element references, and direct reference results using one reference-tail loop. Resolver26 does not expose the raw request scope through its operation context: `CoroutineTaskDispatcher` is the narrow request-root capability, accepts only orchestration and field-resolution contexts, and intentionally provides no generic `launch`; `RequestScopeOwnershipTest` locks the permitted source locations. Each tail hop creates another fresh identity root while retaining the original publication identity. These roots are intentionally never shared or deduplicated; production's physical deduplication and support for target object RSS are outside qplan's semantic model. Resolver observations retain the invocation/publication link so correctness replay and application accounting can follow every hop without treating a finalized OER as relaunchable.

Every maintained resolver supports canonical `FromArgument` paths through nested input objects, with null propagation through nullable intermediate objects and no list traversal. Resolver26 additionally evaluates compiled `FromObjectField` provider paths at runtime and evaluates compiled `FromQueryField` provider paths in each occurrence's containing shared Query OER. Resolver26 preserves symbolic OER keys and treats grounding as readiness and invocation data rather than a rekeying operation; distinct symbolic keys may therefore invoke the same grounded field arguments more than once.

Resolver26 supports a third `FromProvider` variable source backed by one optional suspending function on `FieldResolver`. Each active resolver occurrence invokes that function exactly once after grounding its own arguments, validates that the returned names exactly match its provider declarations, and completes the occurrence-local bindings before materializing either resolver fragment. Object- and Query-fragment work remains independently scheduled and suspends on those bindings. Ordinary provider failures, including task-local `CancellationException`s thrown while the field task remains active, complete the owning resolver field with causal error metadata and unblock dependent variable reads with error bindings. Actual request cancellation cancels outstanding field and binding promises with `CancellationException`; field-task-root completion handlers own cleanup, including cancellation before entry and bindings created by reference hops, while Kotlin propagates cancellation to helper coroutines and Query-producer `Deferred` values. `Error`s are not caught or converted by Resolver26. The durable protocol and canonical field-task boundary are recorded in [`semantics/resolver26/design.md`](./semantics/src/main/kotlin/semantics/resolver26/design.md#failure-and-cancellation-protocol).

## Execution Harness Boundary

The execution module runs validated GraphQL queries through Resolver26 and uses GraphQL Java for response completion. `EngineTestModule.runQPlanFeatureTest` adapts pre-dispatcher Engine API field and node executors into ordinary suspending qplan fixture functions and awaits the executor SPI directly; it does not construct production dispatchers or data loaders. Resolver26 passes each concrete `FieldResolverTask` explicitly to the registry function as its `ResolutionExecutionContext`; no coroutine-context lookup is involved. The adapter wraps that capability in an invocation-local `EngineExecutionContext`. Query `ctx.query()` converts its Engine selection set into canonical qplan selections and delegates back to the task, which resolves a fresh Query-rooted OER under its own field-task scope while retaining the parent operation's world, variable bindings, cycle checker, binding declarations, and observer. Nested calls, aliases, arguments, variables, and field- and node-executor callers are supported; `ctx.mutation()` remains outside the Query-only model. When a feature test supplies a scoped executable schema, the adapter still builds the reasoning world and registry from the full schema but validates and completes the operation against the scoped schema, allowing resolver RSSes to retain private full-schema fields.
