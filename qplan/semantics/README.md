# Semantics

The semantics project defines transformations, resolver algorithms, and correctness judgments over qplan's model carriers. It constructs model values but does not redefine or defensively re-check carrier invariants established by `model`.

## Principal Judgment

```kotlin
fun ObjectEngineResult.correctResolution(
    operation: SharedOperationContext<*>,
    selections: ObjectSelectionForest,
): Boolean
```

`correctResolution` judges the value slots of a completed primary Query OER extensionally. When a field resolver declares a nonempty Query-rooted fragment, the judgment also requires the independently resolved Query OER stored for that exact resolver occurrence to be correct and uses its materialized value when re-evaluating the resolver relation. Reapplication supplies the finite canonical demand reconstructed from the completed output occurrence; this is sufficient under the selective-function agreement law and is not a claim that the judgment recovered the algorithm's original supplied demand. Access-result slots are deliberately outside this judgment: access checks are future qplan work, and maintained resolver versions do not publish or agree on those slots. It also does not establish resolver application count, supplied demand, execution order, provider binding, lifecycle ownership, or concurrency. Those properties require separate witnesses and tests. [`testing-contracts.md`](./testing-contracts.md#resolver-fixture-and-oracle-boundary) explains why the judgment reapplies resolver relations and how `FieldResolver.of` and `FieldResolver.ofSelective` define different test-oracle boundaries.

Correctness predicates retain their result receivers and receive `operation` or `world` explicitly. The private `ResolverConformanceLogic`, `ResolverDemandValidationLogic`, and `ResolverReplayLogic` classes retain stable operation/cache dependencies for their recursive checks. Each result judgment has one replay cache shared between demand validation and resolver conformance. Nested Query results get separate caches while sharing the same reference witness; repeated judgments and standalone predicates create fresh state. No cache or witness is moved into long-lived operation state. Operation-bound witness/cache factories and root-reference replay are operation extensions.

## Vocabulary

Within qplan's semantic architecture, a **context** is an immutable bundle of configuration and state references organized around a defining principle. Context is a role, not a requirement to use the `Context` suffix or inherit a common type. Referenced state can evolve while the context's configuration and references remain fixed. Every context must have a clear organizing principle.

Use **Occurrence** for a context organized around a particular occurrence of an abstraction. It can include the configuration and state references needed for that occurrence; those references do not make it cease to be an occurrence context. Use **Task** and **Logic** for logic contexts organized around algorithmic needs, binding the required context to the procedures that use it. A task can operate on an occurrence while its primary role remains algorithmic. Existing logic implementations can also retain incidental lifecycle bookkeeping.

Use the generic **Context** suffix when the organizing principle is some other one, and explain that principle in the type's KDoc. `SharedOperationContext`, for example, bundles the world and shared state references for one semantic operation. `ClosedConstructionDemandContext` bundles the inputs established by demand closure for one object orchestration; `VariableProviderReadOccurrence` describes one planned provider read that produces a variable binding. Decompose a larger algorithm's context into focused contexts that can be composed as needed, rather than accumulating a monolithic bundle. Choose names by how types are used; occurrence contexts and logic contexts are specializations of the broader context role.

Name variables, parameters, and properties for their semantic role rather than repeating their type's `Context` or `State` suffix. Use `operation`, `publication`, and `variableBindings` for their respective roles. Distinguish `oerOccurrence` for a containing OER occurrence, `sourceOccurrence` for the value-source occurrence being published, and `fieldResolverOccurrence` for one specific resolver invocation; the invocation occurrence is distinct from its registered resolver. Use `variableProviderRead` in property names and `providerRead` for locals and parameters, pluralizing collections. Retain established platform terminology such as `coroutineContext`.

Do not overload semantic helper functions solely by extension-receiver type. Give each helper a distinct name that identifies its receiver level, such as `analyzeParentDemandInSelectionForest` and `analyzeParentDemandInObjectSelection`, so a reviewer can identify the selected operation directly from the call and a search leads to one declaration.

A type with the suffix **State** owns one mutable protocol. Its storage is private, and its methods expose the protocol's legal reads and transitions. `VariableBindingsState`, `CycleCheckState`, and `BindingDeclarationsState` keep mutation out of configuration and context types.

A type with the suffix **Observer** is semantically passive instrumentation. Replacing a normally returning observer that does not mutate resolver inputs or state with its NOP implementation preserves resolution's semantic input/output behavior. A synchronous observer can still affect failure or latency by throwing or blocking, so the convention is not a claim that arbitrary observer implementations are operationally invisible.

Resolver classes use `init` blocks only for constructor preconditions and object invariants. Property initializers and explicit lifecycle methods perform initialization and operational transitions; an `init` block must not enqueue work, publish state, or otherwise start the resolution lifecycle.

An **OER** is an `ObjectEngineResult`, always associated with one concrete GraphQL object type. An **LER** is a `ListEngineResult`, whose element cells preserve exact list positions. The ordinary object-field and list-element containment edges form a well-founded structural tree. A demanded `@parent` field adds the sole distinguished backedge: its `ParentKey` cell references the actual immediate ancestor OER. Structural traversals and occurrence paths exclude parent backedges; finite selection-driven materialization may follow them.

When discussing relationships among OER occurrences, a list is treated as a one-to-many path edge. The object containing a list field is therefore the parent of each object element for resolver-ancestry purposes, while each `ListEngineResult.Index` remains part of the element's exact identity.

A schema-derived map validates each argument-free, singular composite `@parent` field and associates it with its unique compatible argument-free producer field. Producer output may contain the child directly or through any finite list nesting. This relation supports demand lifting from a child occurrence to the producer's containing ancestor.

An **active field** has a standard registered field resolver. At a particular output occurrence, an argumentless active field is dynamically passive when the resolver that owns an ancestor output region supplies it; otherwise its standard resolver owns it. Fields with arguments are always active and may never be supplied passively. A resolver's **fringe** is the set of produced object occurrences whose selected fields require further active resolution.

A **resolver template** is the static registry definition for one concrete object field. A **resolver instance** is the dynamic application associated with one exact field key on one OER occurrence. Unqualified "resolver" usually means the instance when discussing execution and the template when discussing registry structure; use the full term where that distinction matters.

**Content** is the materialized object fragment, Query fragment, and arguments a resolver consumes, or the output value it produces. A resolver is a **reader** or consumer of resolver-produced fields selected by either input fragment; the inverse producer is sometimes called the **author**. At the template level this is a guarded may-read relationship, while actual execution relates exact resolver instances.

A producer is a **predecessor** of a consumer when the consumer must materialize content produced by that resolver instance. The inverse relation is **successor**. Predecessor edges arise both from object-fragment reads and from the resolver instance that creates a descendant OER; runtime variables may add value-flow dependencies. These are occurrence relationships, not merely relationships between schema coordinates.

`SharedOERContext` retains one OER occurrence together with its passive source and closed construction demand. `SharedOrchestrationTask` owns the containing context through `objectOER` and a paired Query context through `queryOER`; an undemanded context has empty closed demand. The coroutine families temporarily use an undemanded placeholder while their existing independent Query-fragment production remains in place. `SharedFieldResolverTask` describes the field-task role: orchestration dispatches active fields for its prepared OERs, while field tasks invoke resolvers, resolve passive output, and dispatch descendant orchestration. Resolver01-03 and Resolver06-08 share concrete `DepthFirstOrchestrationTask` and `DepthFirstFieldResolverTask` implementations. Depth-first ordering is their way of satisfying data dependencies; the coroutine resolvers use promises and structured ownership instead.

Maintaining Resolver01–23 helps preserve the architectural integrity of Resolver26, the intended end product, by exercising how resolver concerns are decomposed and encapsulated across execution families. Shared interfaces may deliberately enforce those architectural relationships without polymorphic consumers. `SharedFieldResolverTask<P>` is such a contract: it preserves the central field-task role and its concretely typed publication ownership, while current callers use the concrete tasks. Retain it for that architectural purpose. [`resolver-versions.md`](../resolver-versions.md#purpose) explains the broader role of the maintained resolver grid.

## Package Ownership

Reserve `semantics.shared` for code shared by all resolver families, including common materialization and correctness support. Put code shared by Resolver01–23 in `semantics.resolvers`. Put code shared by Resolver21–23 and Resolver26 in `semantics.resolver26`, the end-state resolver implementation. Private implementation details may stay in `semantics.shared` even when their use is narrower, but may also accompany a relocated API while retaining private visibility. Do not expose a new shared API merely to leave that implementation behind. Apply the package rule to public/internal declarations. When choosing a consolidation, favor aligning Resolver21–23 with Resolver26 over aligning them with Resolver01–08. `liftParentConstructionDemand` and `installParentBackedgeFields`, used by Resolver22/23 and Resolver26, now live in `semantics.resolver26`. The private parent-demand helpers and supporting classes moved with their entry point, retaining its per-call cache; the unrelated private `CycleCheckStateImpl` remains in shared. The unused `ObjectSelectionForest.fetchBindings` and `Arguments.fetchBindings` extensions were removed after confirming the selection helper had no callers and was the argument helper's only caller. Active semantics grounding helpers and the model's separate `fetchGroundWithBindings` API remain unchanged.

## Demand Vocabulary

**Construction demand** describes the selections used to construct an object result. Construction-demand closure expands those selections with the requirements of unresolved resolvers and parent-induced demand. **Resolver input demand** means one resolver's required object- or Query-fragment selections; those requirements contribute to construction demand. **Successor demand** is the demand supplied to a producer to satisfy downstream requirements, while the original construction demand continues into its returned objects.

`semantics.shared.liftParentSuccessorDemand`, in `ParentSuccessorDemand.kt`, lifts parent selections already present in a forest and is shared by successor-demand algorithms across all resolver families. `semantics.resolver26.liftParentConstructionDemand`, in `ParentConstructionDemand.kt`, also discovers parent selections in reachable resolver fragments and serves Resolver22/23 and Resolver26. Both functions return additional demand for the caller to add to its original forest; contributions may overlap existing selections. Successor lifting combines original child selections with recursive additions when lifting across another ancestor boundary, while returning only the additions and their containing paths. Grounded successor-demand calculation adds lifted demand after expansion; Resolver26 adds it before and after expansion. Parent resolution remains supported by Resolver22/23 and Resolver26; Resolver01–03, Resolver06–08, and Resolver21 require a schema with no `@parent` fields.

## Shared Semantic Boundaries

Shared argument classification, including the internal `Arguments.Ground.argumentsContainErrorValue()` helper, belongs in `semantics.shared`. Within main sources, `semantics.correctresolution` imports shared APIs; other semantics packages do not import `correctresolution`.

Open selections are specialized to a concrete object type with `merge(type)`. The resulting `ObjectKey` values may identify OER cells directly. Bindings are instantiated before operations cross through `groundKeys()`, `byGroundKey()`, or `ObjectSelection.groundKey()` when those operations require resolved argument values.

GraphQL `@skip` and `@include` are lowered into symbolic `InclusionCondition` values. Conditions inherited by one occurrence are conjunctive; equal keys merged during demand closure are activated by the disjunction of their occurrence conditions. Resolver26 launches the infrastructure task for every closed active key, awaits the condition's variable bindings inside that task, negatively activates the reserved cell when the condition is false, and invokes tenant resolver code only after positive activation. Resolver-input materialization evaluates conditions before response-key collection, while passive-field publication remains source-presence-driven and does not independently interpret conditions.

`semantics.shared.materializeResult` projects selected OER values into response-keyed `EngineObjectData`, preserving aliases, inclusion conditions, and null/error/list structure. It expects selected cells and value promises to be installed, but can await unfinished values and argument or inclusion-condition bindings. It supports ground keys and contextually grounded symbolic keys: lookup prefers the exact symbolic key and falls back to a grounded stored key. It does not rekey cells.

Runtime inputs for Resolver01–23 use `semantics.resolvers.materializeResolverInput`, a thin wrapper around `materializeResult` for both object and declared Query-fragment inputs. Resolver26 keeps its distinct `semantics.resolver26.materializeResolverInput`, which can reserve symbolic cells and value promises before their producers install them. The two existing private implementations remain `MaterializationLogic` and `ResolverInputMaterializationLogic`; each retains the explicit operation and independently selected checker for one recursive computation. Both runtime input APIs require the checker explicitly: coroutine input materialization uses its operation's checker, while DFS supplies a no-op checker. Shared `materializeResult` defaults to a no-op checker. Correctness replay and witness reconstruction use that default; nested `ctx.query` result projection explicitly supplies the child operation's checker so the caller's reads participate in runtime cycle rejection.

Correctness replay uses shared `materializeResult` to reconstruct resolver inputs from existing results and re-evaluate deterministic resolver relations. This includes replay of Resolver26 inputs: their results may retain symbolic key identities even though their bindings are resolved. Witness reconstruction uses the same shared projection.

A nested `ctx.query` call is distinct from a resolver's declared Query fragment. The former executes a selection requested by resolver code under the calling field task and returns a result through shared `materializeResult`. The latter declares a Query-rooted dependency that the engine resolves and materializes as input to the resolver using its family's `materializeResolverInput`. Both may involve a fresh Query OER, but they serve different purposes.

Model fixture preparation accepts resolver selection documents that retain named fragment definitions. The current selection carrier cannot represent named fragment spreads, so `fragmentFromDocument` owns lowering those spreads to inline fragments before semantic reasoning. Keeping that conversion beside the model carrier's other parsing helpers allows a future carrier to preserve or optimize named fragments without requiring execution adapters to pre-process them. Resolver query fragments are a different concept: they are Query-rooted resolver inputs that are resolved into an independent OER for each owning resolver occurrence.

Resolver entry points are extensions on their owning operation: `SharedOperationContext<*>.resolve(...)` and `.startResolve(...)` live in their resolver-family packages. Callers import the desired algorithm and write `operation.resolve(selections)`. The concrete `OperationContext.startResolve(...)` and `CoroutineOperationContext.startResolve(...)` helpers start another Query root within an existing execution scope. Selection, key, value, and materialization helpers retain their data receivers and take operation/world dependencies explicitly.

All maintained resolvers use `shared/SharedPassiveValueResolutionLogic` plus `SharedOrchestrationTask`, `SharedFieldPublicationOccurrence`, `SharedFieldResolverTask`, and `SharedTaskDispatcher`. An orchestration-domain factory closes demand and initializes task state; the task-independent `materializePassiveFields(SharedOERContext, ...)` operation fills one supplied OER's source-owned fields, while `resolvePassiveObjectValues` coordinates task preparation, object-side passive materialization, and paired dispatch from a source and occurrence. Resolver26 uses request-root coroutines and promises for readiness. The six depth-first resolvers use the same grounded task implementations under `resolvers/resolver01`: their orchestration factory closes grounded demand for the containing OER and its shared Query OER, orchestration dispatches both sides through the same sibling-ordering path, and each field dispatcher synchronously creates a task that claims its publication before execution or enqueue. The task completes its cell after passive resolution.

`SharedOperationContext` and Resolver26's `OperationContext` are interfaces with `create(...)` factories returning anonymous implementations. `DepthFirstOperationContext` and `CoroutineOperationContext` are concrete classes constructed directly. Specialized contexts delegate their shared operation properties, and publication occurrences retain their operation-context subtype relationship through delegation. Resolver26's `FieldPublicationOccurrence` is a class implementing `OperationContext by operation`; field tasks retain it through composition. Orchestration tasks supply their typed `operation`, and field tasks supply their typed `publication`; tasks compose these contexts without subtyping them. The shared coroutine implementation bases retain their lifecycle responsibilities. Publication delegation reuses configuration, state, dispatcher, and destination-cell identities. Resolver26 child operations replace their dispatcher while sharing the logical operation's state.

Keep a value on its owning context when that context is already reachable at every use site. Do not add a forwarding property or constructor argument merely to shorten an access path: orchestration tasks obtain configuration and state through `operation` and their occurrence-specific values through `objectOER` and `queryOER`, while field tasks obtain operation and publication data through `publication`. Retain a projection when a consumer needs a common contract and would otherwise branch on implementation-specific context types. Current deliberate projections include the orchestration task's two OER-context properties, `ValueSourceOccurrence` publication metadata across source variants, and `DepthFirstTask.path` for scheduling both depth-first task kinds.

Resolver26's blocking `resolve` requires an explicit caller-owned `CoroutineContext`; `startResolve` likewise borrows its caller's `CoroutineScope`, and nested resolution inherits execution resources from the calling field-task scope. `ResolutionDispatcherFactory.create(threadCount)` creates a fresh daemon-backed fixed dispatcher on every call and retains none. Setup boundaries read the existing external thread-count configuration once, reuse their owned dispatcher for the appropriate test-class, campaign-round, corpus-tool, benchmark-trial, fixture, or service lifetime, and close it afterward. Resolver algorithms create, retain, and close none of these execution resources.

`DepthFirstResolve.resolve(selections)` creates the primary Query OER and dispatches its prepared orchestration task directly. It creates an empty Query source internally, so orchestration always receives a non-null source. Every Query field uses a registered resolver, allowing root dispatch without passive traversal. Declared Query fragments of ordinary fields use that task's shared Query OER; independently rooted reference-target invocations continue to start their own Query OER.

Resolver01–23 share the immutable `semantics.resolvers.GroundedFieldPublicationOccurrence<O>` class: operation, containing OER occurrence, selection, publication cell, optional reference and invocation demand, exact publication path, and expected type. Both field-task implementations retain this occurrence through `publication`, preserving their concrete operation type. DFS dispatchers call `DepthFirstFieldResolverTask.create(publication)` synchronously to validate, claim, and activate the publication before executing or enqueuing its task, preserving promise installation before orchestration freezes the object. Resolver21–23 retain their existing prepare-all-before-dispatch boundary and cycle-writer registration. Context construction itself performs no promise or activation transitions.

Resolver01–23 close construction demand through `semantics.resolvers.closeConstructionDemand`, an extension on the source EOD that receives the operation, object occurrence, and initial demand. Resolver26 exposes `semantics.resolver26.closeConstructionDemand` with symbolic keys and returns `ClosedConstructionDemandContext`, which also carries occurrence and binding metadata. Both implementations use an explicit `do`/`while` fixed-point loop organized around `accumulatedDemand`, `demandNotClosed`, and concrete merged demand, and both finalize after the loop. The grounded implementation additionally grounds each pass, binds arguments for newly discovered resolver keys, and records which grounded keys have contributed their fixed inputs; Resolver26 instead tracks concrete symbolic keys and each newly discovered satisfiable key-inclusion condition. Parent lifting always participates and contributes no demand when the schema has no parent relations. Both implementations live in `ConstructionDemandClosure.kt` in their respective packages. The DFS implementations use `semantics.resolvers.resolver01.SiblingDependencyLogic(operation, oerOccurrence)` to compute `order(keys)` and sibling-demand relationships; ordering accumulators remain local to each computation.

`DepthFirstTaskDispatcher` executes fields synchronously and drains each field's accumulated orchestration fringe before the next sibling. `DepthFirstReactor` queues the same tasks: deeper paths precede shallower paths, field tasks precede orchestration at equal depth, and insertion order preserves sibling dependency order. Since shared passive traversal discovers children before parents, the reactor holds child orchestrators until their parent has run. List-element reference tasks use their publication location for queue depth so they finish before a consuming sibling. Both variants resolve independent Query fragments with a fresh recursive dispatcher, isolating them from the enclosing fringe.

The shared passive-value path also interprets `RootFieldReferenceData` only at demanded source positions. Each hop receives a fresh empty Query identity root, its canonical grounded path and arguments, and an empty object input for the target's containing type. A target must have an empty object fragment. Pre-Resolver26 targets may use only `FromArgument`; fragment-capable versions run the target's independent Query fragment, and selective versions pass complete successor demand. Direct reference results form a tail. The shared passive traversal dispatches orchestration for referenced output directly, without rediscovering it through the symbolic source. Resolver01-03 and Resolver06-08 use the same field task for reference positions, through synchronous and queued dispatch respectively; reference work precedes ordinary sibling resolver work. Resolver21-23 and Resolver26 invoke references through their field-task protocol, including references found in lists. An undemanded field containing a reference, including one inside a list, is skipped rather than materialized as non-selective over-fetch.

`resolvers/resolver06/DepthFirstReactor.kt` implements the Resolver06-08 dispatcher for the common depth-first tasks. `resolvers/resolver21/CoroutineResolve.kt` starts Resolver21-23 requests. Their `CoroutineOperationContext`, `CoroutineOrchestrationTask`, `GroundedFieldPublicationOccurrence`, `CoroutineFieldResolverTask`, `FieldResolutionLogic`, and the shared coroutine implementations correspond to the Resolver26 roles: factories prepare demand and bindings, passive traversal resolves source-owned fields, orchestration installs field tasks and freezes objects, and field tasks own Query-fragment producers while resolution logic invokes and publishes values. Orchestration and field tasks belong to the request root; helper coroutines belong to their field task. Explicit cancellation cleanup belongs to task-root completion handlers, while helpers retain local exception-to-error boundaries. Grounded demand and immediately bound `FromArgument` variables keep Resolver21-23 simpler. Resolver21-23 and Resolver26 publish ordinary field failures as error values, including exceptions from Query-fragment producers. A thrown `CancellationException` becomes a field error only while the coroutine remains active; actual cancellation and JVM `Error`s propagate. Unexpected non-cancellation exceptions escaping launched orchestration tasks fail the request; synchronous factory and dispatch checks follow the caller's error boundary. `CoroutineResolverContract` checks their common promise lifecycle and [failure protocol](./src/main/kotlin/semantics/resolver26/design.md#failure-and-cancellation-protocol). `semantics.resolver26.CoroutineTaskDispatcher<O, F>` owns request-root scheduling for both coroutine families and calls their shared `semantics.resolver26.CoroutineOrchestrationTask<O>` base directly. That base retains the typed operation/occurrence/source, owns the atomic one-shot dispatch check and installation/freezing sequence, and provides a validation hook. Concrete orchestration tasks retain their demand preparation, active-work predicate, and field installation; Resolver26 retains its passive-field validation and binding-declaration guard. Their concrete field tasks extend `semantics.resolver26.CoroutineFieldResolverTask<P>`, which retains the typed publication context and helper scope and provides the common exception-to-field-error boundary. Concrete tasks retain their own resolution logic and setup/cleanup protocols. The `shared` package contains the operation context, variable-binding and cycle-check state, observer boundaries, grounding, materialization, and other operations used across resolver and correctness boundaries. [`resolver-versions.md`](../resolver-versions.md) explains the capability grid and how to use it.

Resolver26 is the self-contained advanced resolver with runtime from-field bindings. It supports both `FromObjectField` and `FromQueryField`, extends reference targets with `FromQueryField` and `FromProvider`, and integrates references with conditioned passive activation; its current protocol is documented in [`resolver26/design.md`](./src/main/kotlin/semantics/resolver26/design.md).

Resolver22/23 and Resolver26 resolve `@parent` selections. Each installs the child's parent cell with the containing ancestor OER itself, including for list and nested-list child occurrences. Resolver input fragments may not use variables beneath a parent selection. Demand on `parent { ... }` is lifted one ancestor at a time, so repeated static closure handles grandparents. Both coroutine implementations use the shared parent-input analysis to close ancestor work before descending, so parent reads do not reopen orchestration. Their successor-demand policies also carry parent-induced demand into producer output before selective invocation.

Resolver01–03, Resolver06–08, and Resolver21 require a schema with no `@parent` fields (`world.parentFieldRelations.isEmpty()`), including fields not selected by the operation. This is an input-domain precondition, with no capability flag or runtime rejection checks. The depth-first versions order sibling resolver keys within one OER, but parent-induced work can require leaving a descendant for an ancestor and re-entering that same still-open descendant before either resolver can complete. Supporting that graph re-entry would require occurrence-aware suspension or orchestration beyond their intentionally small execution models. [`examples.md`](../examples.md#why-the-depth-first-resolvers-do-not-support-parent) demonstrates the ordering problem.

## Variable Production And Consumption

A variable recipe determines where one resolver-occurrence binding is produced. Independently, every occurrence of that variable in the resolver's object fragment or Query fragment is a consumer of the same binding. The fragment that consumes a variable does not determine or change its source, and a binding may be consumed by either fragment or by both.

| Recipe | Binding producer | Legal consumers |
| --- | --- | --- |
| `FromArgument` | A path rooted at an argument of the defining resolver occurrence | Object fragment, Query fragment, or both |
| `FromObjectField` | A provider path in the defining resolver's object fragment | Object fragment, Query fragment, or both |
| `FromQueryField` | A provider path in the defining resolver's Query fragment | Object fragment, Query fragment, or both |
| `FromProvider` | The defining resolver's one-shot tenant variables-provider function | Object fragment, Query fragment, or both |

Producer/consumer legality is distinct from current implementation support. `FromArgument` is implemented by every maintained resolver, while Resolver26 implements `FromObjectField`, `FromQueryField`, and `FromProvider`. Resolver26 invokes a provider once per active resolver occurrence after grounding that occurrence's arguments; every provider binding may be consumed by the object fragment, Query fragment, or both.

From-field reads use the defining object or Query fragment's local inclusion conditions. An excluded path step binds null before reserving or awaiting its OER value, even if another fragment or alias requests the same physical field. Selected intermediate and terminal null values also bind null; included field errors and failed condition bindings remain errors. The original conditioned fragments supply all construction demand: variable production does not add unconditional provider-path demand. Circular inclusion dependencies and statically excluded provider paths are rejected during registry assembly.

## Publication

A `FieldPublicationOccurrence` retains its destination cell and initial `ValueSourceOccurrence`. In the case of references, resolution may transitively reach additional value sources before completing that cell's value slot.

An `EngineResultCell` has an activation decision and independent value, field-checker-result, and type-checker-result slots. Field-value resolution publishes an `EngineResult` or GraphQL null into the value slot after positive activation. Negative activation excludes the cell's slots. Resolver26 does not yet resolve the checker-result slots, so completing a field value does not mean computing the cell as a whole.

OER construction is monotonic. Active cells have one writer, parent values may publish stable child OERs before those children complete, and each algorithm must install or reserve discoverable child work before a reader can depend on it.

Resolver-visible `EngineObjectData` does not retain OER identity. Materializing a parent selection follows the selected parent backedge and constructs a fresh finite EOD projection; the resulting object is not reference-equal to an EOD previously used to construct or materialize that ancestor. Parent backedges therefore do not enter the EOD carrier.

Sometimes-passive active fields make transitive parent demand conservative: a grandchild field that ultimately remains passive can still lift `parent.parent` demand and resolve or materialize unused ancestor fields. This marginal speculative work is an accepted precision tradeoff for keeping closure monotonic and independent of the later dynamic ownership decision.

## Resolution Observations

All maintained resolver families use the `ResolverObserver` carried by `SharedOperationContext`. Its implementations vary by observation use case, not by resolver family. Every callback defaults to no-op, allowing narrow consumers to implement the interface directly and record only what they need. `ResolverObserver.NOP` is the nested singleton used when no observations are needed. Observation belongs to semantics: neither `FieldResolver` nor model fixtures install an invocation callback. Resolver26 uses the same observer and execution entry points as the other families, without a separate `resolveObserved` path or observer adapter.

Resolver26's operation factory takes its observer from the base operation, and child scopes retain that same observer. Callbacks may run concurrently, so recording must be thread-safe; independent invocations have no guaranteed event order beyond each callback's documented lifecycle relationship. OER references remain live and potentially unfinished even when their observation payloads have immutable properties. Benchmark-only symbolic argument counts and variable-owner identities are derived by extension properties in the `semantics.benchmark` test fixtures, keeping shared event carriers limited to captured facts.

| Recording point | Families | Timing and evidence |
| --- | --- | --- |
| `onResolverInvocation` | 01–03, 06–08, 21–23, 26 | Immediately before each ordinary or reference-target `FieldResolver.invoke`, after its inputs are ready. Records field, input, instantiated input selections, resolved arguments, optional selective demand, exact occurrence identity, and path. A null demand denotes nonselective execution. Attempts that subsequently throw or cancel remain recorded; no output or outcome is recorded. |
| `onQueryFragmentPrepared` | All three execution implementations; declared Query fragments are supported by 02–03, 07–08, 22–23, 26 | After preparing the fresh Query-root orchestration and before dispatch. Associates the owning resolver occurrence with a live OER whose cells and values may be unfinished. Empty fragments emit nothing. |
| `onRootFieldReferenceInvocation` | 01–03, 06–08, 21–23, 26 | After the reference-target helper returns, associates the original publication root/path and reference descriptor with the independently rooted invocation path/key and supplied demand. This is an association witness, not an outcome event; Resolver26 can emit it when input preparation returns an error without entering the target resolver. |
| `onTaskStarted` | 06–08 | The work-queue driver calls its internal optional hook just before running a dequeued orchestration or field task. Used by ordering contracts. Recursive declared-Query work uses the separate DFS driver and does not pass through this hook. |

There are twelve shared-observer emission sites: two invocation sites, one Query-preparation site, and one reference-association site in each execution implementation (common DFS, grounded coroutine, and Resolver26). The work-queue hook is one additional site. Passive fields, variable-provider calls, value publication, failures, cancellation, and checker execution have no separate shared observer events. A nested `ctx.query()` is distinct from a resolver's declared Query fragment: its resolver calls use the same operation observer, but the nested-query boundary itself emits no Query-fragment event.

`semantics.correctresolution.CorrectnessResolverObserver` directly supplies correctness evidence as snapshots: a set of invocation IDs plus duplicate-preserving Query-root and reference-hop records. The observer interface, no-op singleton, and event payloads remain in `semantics.shared`; resolver algorithms depend only on that API. Correctness consumers retain the recorder base and add invocation counts, arguments, or input fingerprints when needed. Narrow consumers implement `ResolverObserver` directly, including benchmark statistics and algorithm tests that retain only the recording their assertions need. The ordinary/reference invocation test retains a `CorrectnessResolverObserver` subclass because it uses all three recording categories to check observation delivery. Invocation-ID deduplication has both local algorithm-test coverage and a dedicated recorder test. DSL argument assertions, generated resolution witnesses, and benchmark statistics consume the same recording point. Correctness replay calls `evaluateRelation` without emitting algorithm observations.
