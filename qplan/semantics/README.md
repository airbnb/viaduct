# Semantics

The semantics project defines transformations, resolver algorithms, and correctness judgments over qplan's model carriers. It constructs model values but does not redefine or defensively re-check carrier invariants established by `model`.

## Principal Judgment

```kotlin
fun ObjectEngineResult.correctResolution(
    operation: SharedOperationContext<*>,
    selections: ObjectSelectionForest,
): Boolean
```

`correctResolution` judges the value slots of a completed primary Query OER extensionally. When resolvers or checkers declare nonempty Query-rooted fragments, the judgment also requires their containing orchestration's associated Query OER to satisfy its unioned closed demand and uses each owner occurrence's materialized projection when replaying its relation. A shared result is traversed once by identity, while owner projections are validated separately. Reapplication supplies the finite canonical demand reconstructed from the completed output occurrence; this is sufficient under the selective-function agreement law and is not a claim that the judgment recovered the algorithm's original supplied demand. Checked client and resolver-input selections with registered field checkers must have claimed checker-result slots. Claimed checker object fragments must be present in their containing OERs as unchecked demand. Checker replay reconstructs every named raw object/Query input pair and requires the replayed success/error variant to match the stored slot; a checked occurrence at which no checker can run instead requires a null slot. Resolver invocation observations retain both materialized input values; correctness replay requires them to match the checked values reconstructed from the OERs, including access errors at exact response-key and list positions. Checker errors expose no tenant-independent equality, so replay does not compare error object identity. Exact checker application counts remain a separate observer-backed judgment. `correctResolution` also does not establish supplied demand, execution order, provider binding, lifecycle ownership, or concurrency. Those properties require separate witnesses and tests. [`testing-contracts.md`](./testing-contracts.md#resolver-fixture-and-oracle-boundary) explains why the judgment reapplies resolver relations and how `FieldValueResolver.of` and `FieldValueResolver.ofSelective` define different test-oracle boundaries.

Correctness predicates retain their result receivers and receive `operation` or `world` explicitly. The private `ResolverConformanceLogic`, `ResolverDemandValidationLogic`, and `ResolverReplayLogic` classes retain stable operation/cache dependencies for their recursive checks. Each result judgment has one replay cache shared between demand validation and resolver conformance. Each nested Query result gets one cache reused across all owners while sharing the same reference witness; repeated judgments and standalone predicates create fresh state. No cache or witness is moved into long-lived operation state. Operation-bound witness/cache factories and root-reference replay are operation extensions.

## Vocabulary

This section defines semantic roles; [`resolver-versions.md`](../resolver-versions.md#elements-of-alignment) explains how to align those roles across implementations and gives contextual [code naming preferences](../resolver-versions.md#code-naming-preferences). Keep definitions here and cross-family naming policy there.

Within qplan's semantic architecture, a **context** is an immutable bundle of configuration and state references organized around a defining principle. Context is a role, not a requirement to use the `Context` suffix or inherit a common type. Referenced state can evolve while the context's configuration and references remain fixed. Every context must have a clear organizing principle.

Use **Occurrence** for a context organized around a particular occurrence of an abstraction. It can include the configuration and state references needed for that occurrence; those references do not make it cease to be an occurrence context. Use **Task** and **Logic** for logic contexts organized around algorithmic needs, binding the required context to the procedures that use it. A task can operate on an occurrence while its primary role remains algorithmic. Existing logic implementations can also retain incidental lifecycle bookkeeping.

Use the generic **Context** suffix when the organizing principle is some other one, and explain that principle in the type's KDoc. `SharedOperationContext`, for example, bundles the world and shared state references for one semantic operation. `ClosedConstructionDemandContext` bundles the inputs established by demand closure for one object orchestration; `VariableProviderReadOccurrence` describes one planned provider read that produces a variable binding. Decompose a larger algorithm's context into focused contexts that can be composed as needed, rather than accumulating a monolithic bundle. Choose names by how types are used; occurrence contexts and logic contexts are specializations of the broader context role.

Name variables, parameters, and properties for their semantic role rather than repeating their type's `Context` or `State` suffix. Use `operation`, `publication`, and `variableBindings` for their respective roles. Distinguish `oerOccurrence` for a containing OER occurrence, `sourceOccurrence` for the value-source occurrence being published, and `fieldResolverOccurrence` for one specific resolver invocation; the invocation occurrence is distinct from its registered resolver. Use `variableProviderRead` in property names and `providerRead` for locals and parameters, pluralizing collections. Retain established platform terminology such as `coroutineContext`.

Do not overload semantic helper functions solely by extension-receiver type. Give each helper a distinct name that identifies its receiver level, such as `findParentDemandInSelectionForest` and `findParentDemandInObjectSelection`, so a reviewer can identify the selected operation directly from the call and a search leads to one declaration.

A type with the suffix **State** owns one mutable protocol. Its storage is private, and its methods expose the protocol's legal reads and transitions. `VariableBindingsState`, `CycleCheckState`, and `BindingDeclarationsState` keep mutation out of configuration and context types.

A type with the suffix **Observer** is semantically passive instrumentation. Replacing a normally returning observer that does not mutate resolver inputs or state with its NOP implementation preserves resolution's semantic input/output behavior. A synchronous observer can still affect failure or latency by throwing or blocking, so the convention is not a claim that arbitrary observer implementations are operationally invisible.

Resolver classes use `init` blocks only for constructor preconditions and object invariants. Property initializers and explicit lifecycle methods perform initialization and operational transitions; an `init` block must not enqueue work, publish state, or otherwise start the resolution lifecycle.

An **OER** is an `ObjectEngineResult`, always associated with one concrete GraphQL object type. An **LER** is a `ListEngineResult`, whose element cells preserve exact list positions. The ordinary object-field and list-element containment edges form a well-founded structural tree. A demanded `@parent` field adds the sole distinguished backedge: its `ParentKey` cell references the actual immediate ancestor OER. Structural traversals and occurrence paths exclude parent backedges; finite selection-driven materialization may follow them.

When discussing relationships among OER occurrences, a list is treated as a one-to-many path edge. The object containing a list field is therefore the parent of each object element for resolver-ancestry purposes, while each `ListEngineResult.Index` remains part of the element's exact identity.

A schema-derived map validates each argument-free, singular composite `@parent` field and associates it with its unique compatible argument-free producer field. Producer output may contain the child directly or through any finite list nesting. This relation supports demand lifting from a child occurrence to the producer's containing ancestor.

An **active field** has a standard registered field resolver. At a particular output occurrence, an argumentless active field is dynamically passive when the resolver that owns an ancestor output region supplies it; otherwise its standard resolver owns it. Fields with arguments are always active and may never be supplied passively. A resolver's **fringe** is the set of produced object occurrences whose selected fields require further active resolution.

A **resolver template** is the static registry definition for one concrete object field. A **resolver instance** is the dynamic application associated with one exact field key on one OER occurrence. Unqualified "resolver" usually means the instance when discussing execution and the template when discussing registry structure; use the full term where that distinction matters.

**Content** is the materialized object fragment, Query fragment, and arguments a resolver consumes, or the output value it produces. A resolver is a **reader** or consumer of resolver-produced fields selected by either input fragment; the inverse producer is sometimes called the **author**. At the template level this is a guarded may-read relationship, while actual execution relates exact resolver instances.

A producer is a **predecessor** of a consumer when the consumer must materialize content produced by that resolver instance. The inverse relation is **successor**. Predecessor edges arise both from object-fragment reads and from the resolver instance that creates a descendant OER; runtime variables may add value-flow dependencies. These are occurrence relationships, not merely relationships between schema coordinates.

`SharedOERContext` retains one OER occurrence together with its passive source and closed value-selection projection (`closedValueSelections`). Provenance-preserving construction demand remains on the orchestration task. `SharedOrchestrationTask` owns the containing context through `objectOER` and a paired Query context through `queryOER`; an undemanded context has empty closed value selections. Every maintained resolver prepares one real associated Query OER for every orchestration. `SharedFieldResolverTask` describes the field-resolver-task role: orchestration dispatches active fields for its prepared OERs, while field-resolver tasks invoke resolvers, resolve passive output, and dispatch descendant orchestration. Resolver01-03 and Resolver06-08 share concrete `DepthFirstOrchestrationTask` and `DepthFirstFieldResolverTask` implementations. Depth-first ordering is their way of satisfying data dependencies; the coroutine resolvers use promises and structured ownership instead.

Maintaining Resolver01–23 helps preserve the architectural integrity of Resolver26, the intended end product, by exercising how resolver concerns are decomposed and encapsulated across execution families. Shared interfaces may deliberately enforce those architectural relationships without polymorphic consumers. `SharedFieldResolverTask<P>` is such a contract: it preserves the central field-resolver-task role and its concretely typed publication ownership, while current callers use the concrete tasks. Retain it for that architectural purpose. [`resolver-versions.md`](../resolver-versions.md#purpose) explains the broader role of the maintained resolver grid.

### Lifecycle and task roles

Use **field-resolver task** for the role represented by `SharedFieldResolverTask`, including tasks that publish references or conditioned passive values, and **field-checker task** for the parallel checker role. **Field-value work** distinguishes value-slot production from checker work; it does not name another task kind.

| Verb | Meaning |
| --- | --- |
| Close demand | Compute complete construction demand and retain descriptions needed for preparation. |
| Prepare a publication | Reserve its cell, claim its promise, and register its writer where the family uses cycle tracking; do not start execution. DFS preparation also activates the cell and returns an executable task. |
| Materialize passive fields | Fill source-owned values and recursively prepare descendant orchestration. |
| Dispatch | Hand prepared publication or task handles to the family dispatcher. DFS dispatch prepares an executable field-resolver task before entering or queueing it. |
| Launch | Create a coroutine, enqueue a task, or enter its synchronous execution. Coroutine dispatchers construct running field-resolver tasks inside the dispatched root. |
| Execute | Await or read inputs, invoke tenant code when applicable, and resolve passive output. |
| Publish | Complete the owned value or checker slot. |
| Freeze | Seal an OER's key set after all discoverable publications have been prepared; claimed promises may still be pending. |

**Passive traversal** is the shared recursive component `SharedPassiveValueResolutionLogic`. **Passive descent** is the orchestration phase that materializes source-owned fields before dispatching that orchestration. **Passive value resolution** is the conversion of returned data into engine results; it uses passive traversal and may discover further orchestration or reference work.

An orchestration owns one **associated Query OER**. Owners share production in that associated OER while retaining separate input projections. **Independently rooted Query execution** means a reference-target Query fragment or `ctx.query()` execution; it has a distinct lifecycle and is owned by the invoking field-resolver or field-checker task.

## Package Ownership

The [production direction](../resolver-versions.md#production-direction-and-package-ownership) places Resolver26 and its production dependencies in runtime2's `main`, with maintained earlier families in unpublished development `support`. Coroutine-only shared machinery therefore belongs in today's `resolver26`, its eventual production home. `CoroutineOrchestrationTaskBase` and `CoroutineFieldResolverTaskBase` use the `Base` suffix to distinguish them from earlier concrete tasks without changing that ownership.

Reserve `semantics.shared` for code shared by all resolver families, including common materialization and correctness support. Put code shared by Resolver01–23 in `semantics.resolvers`. Put code shared by Resolver21–23 and Resolver26 in `semantics.resolver26`, the end-state resolver implementation. Private implementation details may stay in `semantics.shared` even when their use is narrower, but may also accompany a relocated API while retaining private visibility. Do not expose a new shared API merely to leave that implementation behind. Apply the package rule to public/internal declarations. When choosing a consolidation, favor aligning Resolver21–23 with Resolver26 over aligning them with Resolver01–08. `liftParentConstructionDemand` and `installParentBackedgeFields`, used by Resolver22/23 and Resolver26, now live in `semantics.resolver26`. The private parent-demand helpers and supporting classes moved with their entry point, retaining its per-call cache; the unrelated private `CycleCheckStateImpl` remains in shared. The unused `ObjectSelectionForest.fetchBindings` and `Arguments.fetchBindings` extensions were removed after confirming the selection helper had no callers and was the argument helper's only caller. Active semantics grounding helpers and the model's separate `fetchGroundWithBindings` API remain unchanged.

## Demand Vocabulary

**Construction demand** describes the selections used to construct an object result. Construction-demand closure expands those selections with the requirements of unresolved resolvers and parent-induced demand. **Resolver input demand** means one resolver's required object- or Query-fragment selections; those requirements contribute to construction demand. **Successor demand** is the demand supplied to a producer to satisfy downstream requirements, while the original construction demand continues into its returned objects.

`semantics.shared.liftParentSuccessorDemand`, in `ParentSuccessorDemand.kt`, lifts parent selections already present in a forest and is shared by successor-demand algorithms across all resolver families. `semantics.resolver26.liftParentConstructionDemand`, in `ParentConstructionDemand.kt`, also discovers parent selections in reachable resolver fragments and serves Resolver22/23 and Resolver26. Both functions return additional demand for the caller to add to its original forest; contributions may overlap existing selections. Successor lifting combines original child selections with recursive additions when lifting across another ancestor boundary, while returning only the additions and their containing paths. Grounded successor-demand calculation adds lifted demand after expansion; Resolver26 adds it before and after expansion. Parent resolution remains supported by Resolver22/23 and Resolver26; Resolver01–03, Resolver06–08, and Resolver21 require a schema with no `@parent` fields.

Use **checked demand** and **unchecked demand** for construction provenance. During closure, checked demand adds the transitive obligation to include field-checker inputs; unchecked demand does not. A value resolver reached through either provenance still contributes its own checked input demand. Use **checked materialization/read** and **raw materialization/read** for consuming results: checker inputs contribute unchecked construction demand and are materialized raw. Raw is a read policy, not another demand carrier.

**Closed construction demand** preserves provenance in `Demand<...>` and in the paired `OrchestrationConstructionDemand`. **Closed value selections** are their merged value-selection projection, exposed as `SharedOERContext.closedValueSelections` and `ClosedOERConstructionDemandContext.closedValueSelections`; that projection cannot recover checker provenance.

Grounded construction and successor analysis take `operation: SharedOperationContext` because they ground arguments and consult runtime bindings. Resolver26 takes `world: Assumptions` because symbolic analysis is independent of occurrence-time bindings. Grounded `newResolverKeys` and `SuccessorBoundary.key` retain argument-sensitive identities; Resolver26's `newResolverKeyInclusions` and `SuccessorBoundary.field` expose new inclusion alternatives and argument-independent fixed-template analysis. Both successor contexts own an explicit `SuccessorExpansionState`; the grounded state tracks only active boundaries, while Resolver26 additionally tracks memoized inputs and recursion cuts.

### Parent construction lookahead

`closeOrchestrationConstructionDemand` expands resolver inputs for top-level keys on the object whose construction it is closing. It knows that object's concrete type and source EOD, so source-present fields do not activate their standard resolvers. `liftParentConstructionDemand` additionally looks through requested descendants and reachable fixed resolver inputs to discover requirements on ancestors before passive descent and freezing.

A lift can place demand on an intermediate descendant rather than on the object whose closure is running. For example, while closing a Grand object's demand `parentNode { child { result } }`, suppose `Child.result` requires `parent { bridge }` and `Parent.bridge` requires `parent { grandValue }`. The first lift adds `bridge` at the Parent level. Grand's local closure loop does not expand `Parent.bridge`, so parent lookahead must inspect its input and lift `grandValue` again before Grand's construction closes. The helper follows the dependencies of newly lifted demand to find further parent requirements; it returns parent-induced additions and their containing paths, without adding every ordinary RSS selection it visits. The worked examples in [`ParentConstructionDemandTest`](./src/test/kotlin/semantics/resolver26/ParentConstructionDemandTest.kt) cover this intermediate-object case.

This lookahead is conservative. It considers every possible concrete key of a selection and follows registered resolver inputs without knowing whether a future source EOD will supply the field instead. Some ancestor requirements can therefore turn out to be unused. Waiting for descendant resolution to settle those choices would discover ancestor demand after its construction boundary has closed.

Inclusion conditions have two distinct roles here. Conditions on the supplied selections and their containing paths remain guards on lifted demand. When lookahead inspects a fixed resolver RSS, however, its occurrence-local bindings are not yet available: `withoutInclusionConditions` treats unresolved conditions as `Always`, while dropping selections already reduced to `Never`, such as `@skip(if: true)`. The original resolver fragment retains its conditions for occurrence-local closure and materialization. This conservative RSS analysis does not disable directives at runtime or revive statically excluded selections. [`Resolver26's construction-demand design`](./src/main/kotlin/semantics/resolver26/design.md#construction-demand-closure) describes how this lookahead participates in symbolic closure.

Grounded Resolver23 and Resolver26 expose `successorDemandFromConstructionDemand`, with corresponding `successorDemandWithChecks`, `fixedSuccessorInputDemand`, resolver/checker input helpers, and explicit `SuccessorBoundaryKind` roles. Resolver26 retains schema-field boundary identity for argument-independent fixed-template analysis, symbolic producer projection, conservative unresolved conditions, recursion-cut-aware memoization, and concrete-key compaction. Grounded analysis substitutes available argument bindings and identifies boundaries by grounded key. Resolver26 runs construction-parent lookahead before symbolic projection and successor-parent transposition afterward; the shared parent algorithms and their invocation schedule are unchanged.

## Shared Semantic Boundaries

Shared argument classification, including the internal `Arguments.Ground.argumentsContainErrorValue()` helper, belongs in `semantics.shared`. Within main sources, `semantics.correctresolution` imports shared APIs; other semantics packages do not import `correctresolution`.

Open selections are specialized to a concrete object type with `merge(type)`. The resulting `ObjectKey` values may identify OER cells directly. Bindings are instantiated before operations cross through `groundKeys()`, `byGroundKey()`, or `ObjectSelection.groundKey()` when those operations require resolved argument values.

GraphQL `@skip` and `@include` are lowered into symbolic `InclusionCondition` values. Conditions inherited by one occurrence are conjunctive; equal keys merged during demand closure are activated by the disjunction of their occurrence conditions. Resolver26 launches the infrastructure task for every closed active key, awaits the condition's variable bindings inside that task, negatively activates the reserved cell when the condition is false, and invokes tenant resolver code only after positive activation. Resolver-input materialization evaluates conditions before response-key collection, while passive-field publication remains source-presence-driven and does not independently interpret conditions.

`semantics.shared.materializeResult` projects selected OER values into response-keyed `EngineObjectData`, preserving aliases, inclusion conditions, access-check bypass metadata, and null/error/list structure. It expects selected cells and value promises to be installed, but can await unfinished values and argument or inclusion-condition bindings. It supports ground keys and contextually grounded symbolic keys: lookup prefers the exact symbolic key and falls back to a grounded stored key. It does not rekey cells. Checked materialization reads the field result from the selected cell, recursively follows value and list structure, reads the type result from each reached OER occurrence, and combines applicable results through the production `CheckerResult.combine` contract at enforcement. Raw materialization skips access-check results while retaining the same recursive projection, bindings, aliases, conditions, and value-slot cycle reads. It is reserved for checker-input edges; an active value resolver reached through such an edge still consumes its own inputs with checked semantics.

Runtime inputs for Resolver01–23 use `semantics.resolvers.materializeResolverInput`, a thin wrapper around `materializeResult` for both object and declared Query-fragment inputs. Resolver26 keeps its distinct `semantics.resolver26.materializeResolverInput`, which can reserve symbolic cells and value promises before their producers install them, preserves exact symbolic cell identity while awaiting argument bindings, and accepts the selected object's explicit result path. The implementations remain distinct because Resolver01–23 deliberately require prior cell and promise installation, while Resolver26 reservation is a readiness protocol; using reservation everywhere would turn an installation bug in an earlier family from an immediate failure into a possible indefinite wait. Both runtime input APIs require the cycle checker explicitly: coroutine input materialization uses its operation's checker, while DFS supplies a no-op checker. Shared `materializeResult` defaults to a no-op checker. Correctness replay and witness reconstruction use that default; nested `ctx.query` result projection explicitly supplies the child operation's checker so the caller's reads participate in runtime cycle rejection. Cycle edges identify the exact task by kind, Query-root identity, and path, and identify field-check slots by cell identity and type-check slots by OER identity, so equal paths in distinct Query OERs and value/checker writers do not alias.

Correctness replay uses shared `materializeResult` to reconstruct resolver inputs from existing results and re-evaluate deterministic resolver relations. This includes replay of Resolver26 inputs: their results may retain symbolic key identities even though their bindings are resolved. Witness reconstruction uses the same shared projection.

A nested `ctx.query` call is distinct from a resolver's declared Query fragment. The former executes a selection requested by resolver code under the calling field-resolver task and returns a result through shared `materializeResult`. The latter declares a Query-rooted dependency that the engine resolves and materializes as input to the resolver using its family's `materializeResolverInput`. Nested queries always start a new execution root; ordinary declared Query fragments use the containing orchestration's associated Query OER in every maintained resolver.

Model fixture preparation accepts resolver selection documents that retain named fragment definitions. The current selection carrier cannot represent named fragment spreads, so `fragmentFromDocument` owns lowering those spreads to inline fragments before semantic reasoning. Keeping that conversion beside the model carrier's other parsing helpers allows a future carrier to preserve or optimize named fragments without requiring execution adapters to pre-process them. Resolver Query fragments are a different concept: they are Query-rooted resolver inputs whose production is shared within one associated OER. Root-field-reference targets retain independently rooted Query execution.

Resolver entry points are extensions on their owning operation: `SharedOperationContext<*>.resolve(...)` and `.startResolve(...)` live in their resolver-family packages. Callers import the desired algorithm and write `operation.resolve(selections)`. The concrete `OperationContext.startResolve(...)` and `CoroutineOperationContext.startResolve(...)` helpers start another Query root within an existing execution scope. Selection, key, value, and materialization helpers retain their data receivers and take operation/world dependencies explicitly.

All maintained resolvers use `shared/SharedPassiveValueResolutionLogic` plus `SharedOrchestrationTask`, `SharedFieldPublicationOccurrence`, `SharedFieldResolverTask`, and `SharedTaskDispatcher`. An orchestration-domain factory closes demand and initializes task state; the task-independent `materializePassiveFields(SharedOERContext, ...)` operation fills one supplied OER's source-owned fields, while `resolvePassiveObjectValues` coordinates task preparation, object-side passive materialization, and paired dispatch from a source and occurrence. Resolver26 uses request-root coroutines and promises for readiness. The six depth-first resolvers use the same grounded task implementations under `resolvers/resolver01`: their orchestration factory closes grounded demand for the containing OER and its associated Query OER, orchestration dispatches both sides through the same sibling-ordering path, and each field dispatcher synchronously creates a task that claims its publication before execution or enqueue. The task completes its cell after passive resolution.

`SharedOperationContext` and Resolver26's `OperationContext` are interfaces with `create(...)` factories returning anonymous implementations. `DepthFirstOperationContext` and `CoroutineOperationContext` are concrete classes constructed directly. Specialized contexts delegate their shared operation properties, and publication occurrences retain their operation-context subtype relationship through delegation. Resolver26's `SymbolicFieldPublicationOccurrence` is a class implementing `OperationContext by operation`; field-resolver tasks retain it through composition. Orchestration tasks supply their typed `operation`, and field-resolver tasks supply their typed `publication`; tasks compose these contexts without subtyping them. The shared coroutine implementation bases retain their lifecycle responsibilities. Publication delegation reuses configuration, state, dispatcher, and destination-cell identities. Resolver26 child operations replace their dispatcher while sharing the logical operation's state.

Keep a value on its owning context when that context is already reachable at every use site. Do not add a forwarding property or constructor argument merely to shorten an access path: orchestration tasks obtain configuration and state through `operation` and their occurrence-specific values through `objectOER` and `queryOER`, while field-resolver tasks obtain operation and publication data through `publication`. Retain a projection when a consumer needs a common contract and would otherwise branch on implementation-specific context types. Current deliberate projections include the orchestration task's two OER-context properties, `ValueSourceOccurrence` publication metadata across source variants, and `DepthFirstTask.path` for scheduling both depth-first task kinds.

Resolver26's blocking `resolve` requires an explicit caller-owned `CoroutineContext`; `startResolve` likewise borrows its caller's `CoroutineScope`, and nested resolution inherits execution resources from the calling field-resolver-task scope. `ResolutionDispatcherFactory.create(threadCount)` creates a fresh daemon-backed fixed dispatcher on every call and retains none. Setup boundaries read the existing external thread-count configuration once, reuse their owned dispatcher for the appropriate test-class, campaign-round, corpus-tool, benchmark-trial, fixture, or service lifetime, and close it afterward. Resolver algorithms create, retain, and close none of these execution resources.

`DepthFirstResolve.resolve(selections)` creates the primary Query OER and dispatches its prepared orchestration task directly. It creates an empty Query source internally, so orchestration always receives a non-null source. Every Query field uses a registered resolver, allowing root dispatch without passive traversal. Declared Query fragments of ordinary fields use that task's associated Query OER; independently rooted reference-target invocations continue to start their own Query OER.

Resolver01–23 share the immutable `semantics.resolvers.GroundedFieldPublicationOccurrence<O>` class: operation, containing OER occurrence, selection, publication cell, optional reference and invocation demand, exact publication path, and expected type. Both field-resolver-task implementations retain this occurrence through `publication`, preserving their concrete operation type. DFS dispatchers call `DepthFirstFieldResolverTask.prepare(publication)` synchronously to validate, claim, and activate the publication before executing or enqueuing its task, preserving promise installation before orchestration freezes the object. Resolver21–23 retain their existing prepare-all-before-dispatch boundary and cycle-writer registration. Context construction itself performs no promise or activation transitions.

Resolver21–23 and Resolver26 keep task preparation separate from dispatch. Their value and checker task helpers expose `prepareAll`; orchestration dispatches the resulting publications after value promises have been claimed and all cycle writers have been installed. Grounded preparation derives its publication records from closed grounded selections. Resolver26 preparation consumes the occurrence and provider descriptions retained by symbolic closure, declares pending bindings, and leaves activation to execution. Resolver26 still prepares checker work during orchestration creation, before passive descent, and prepares ordinary value publications during `prepareAndDispatchFieldWork`. Its `FieldCheckerPreparation` records every demanded checker promise, executable checker publication, and delayed null result: orchestration publishes null for completed passive values, while field-resolver activation or cancellation terminates the remaining non-applicable checker promises. Grounded preparation returns all demanded publications, including null-checker entries that orchestration can complete immediately. During passive descent, Resolver26 registers prepared conditioned passive-list publications with their owning orchestration; `prepareAndDispatchFieldWork` dispatches them alongside ordinary publications. List-element reference helpers retain a combined preparation/dispatch boundary because elements may be discovered during passive value resolution after the containing object orchestration has frozen.

Both closure implementations expose `closeOrchestrationConstructionDemand` as an extension on the object source EOD and close object- and Query-rooted demand together. Object-side resolvers contribute their object fragment to the object OER and their Query fragment to the associated Query OER, while Query-side resolvers contribute both fragments back into that Query OER. Both accumulate the shared `OrchestrationConstructionDemand` pair of checked/unchecked object/Query forests; their direct fragment contributions use the shared `ResolverInputConstructionDemand` pair. Both discover new expansion events before collecting and routing their fragment contributions. The shared source-ownership predicate `requiresStandardResolution` suppresses standard resolvers for source-supplied argumentless fields, and the shared `Demand.descendants` projection preserves checked/unchecked provenance during field publication. The grounded implementation returns `OrchestrationConstructionDemand`, grounds each pass, binds arguments for newly discovered resolver keys, and records which grounded keys have contributed their fixed inputs. Resolver26 returns `ClosedConstructionDemandContext`, retaining occurrence and binding metadata while tracking symbolic keys and each newly discovered satisfiable key-inclusion condition. Parent lifting always participates and contributes no demand when the schema has no parent relations. Both implementations live in `ConstructionDemandClosure.kt` in their respective packages. Resolver26 finishes its richer closure result in `finalizeClosedOERConstructionDemand`: occurrence, variable, reference, and provider-read descriptions belong to demand construction and are retained for subsequent task preparation. This step does not install promises or dispatch tasks. The DFS implementations use `semantics.resolvers.resolver01.SiblingDependencyLogic(operation, oerOccurrence)` to compute `order(keys)` and sibling-demand relationships; ordering accumulators remain local to each computation.

`DepthFirstTaskDispatcher` executes fields synchronously and drains each field's accumulated orchestration fringe before the next sibling. `DepthFirstReactor` queues the same tasks: deeper paths precede shallower paths, field-resolver tasks precede orchestration at equal depth, and insertion order preserves sibling dependency order. Since shared passive traversal discovers children before parents, the reactor holds child orchestration tasks until their parent has run. List-element reference tasks use their publication location for queue depth so they finish before a consuming sibling. Ordinary Query-fragment work uses the same paired orchestration and ordering machinery; independently rooted reference targets use a fresh recursive dispatcher.

The shared passive-value path also interprets `RootFieldReferenceData` only at demanded source positions. Each hop receives a fresh empty Query identity root, its canonical grounded path and arguments, and an empty object input for the target's containing type. A target must have an empty object fragment. Pre-Resolver26 targets may use only `FromArgument`; fragment-capable versions run the target's independent Query execution, whose ordinary declared fragments use singular sharing internally, and selective versions pass complete successor demand. Direct reference results form a tail. Such dynamically returned recursion has the same tenant-code nontermination semantics as recursive `ctx.query()` or other resolver code; qplan does not impose a reference-tail detector, while registry validation still rejects declarative RSS dependency cycles. The shared passive traversal dispatches orchestration for referenced output directly, without rediscovering it through the symbolic source. Resolver01-03 and Resolver06-08 use the same field-resolver task for reference positions, through synchronous and queued dispatch respectively; reference work precedes ordinary sibling resolver work. Resolver21-23 and Resolver26 invoke references through their field-resolver-task protocol, including references found in lists. An undemanded field containing a reference, including one inside a list, is skipped rather than materialized as non-selective over-fetch.

`resolvers/resolver06/DepthFirstReactor.kt` implements the Resolver06-08 dispatcher for the common depth-first tasks. `resolvers/resolver21/CoroutineResolve.kt` starts Resolver21-23 requests. Their `CoroutineOperationContext`, `CoroutineOrchestrationTask`, `GroundedFieldPublicationOccurrence`, `CoroutineFieldResolverTask`, `FieldResolutionLogic`, and the shared coroutine implementations correspond to the Resolver26 roles: factories jointly close object- and Query-rooted demand, passive traversal resolves source-owned fields, orchestration prepares both OERs' ordinary value and checker publications before dispatch and freezes both OERs, and field-resolver tasks materialize owner-local Query projections before invocation and publication. Orchestration, field-resolver, and field-checker tasks belong to the request root; only independently rooted reference-target Query producers belong to their field-resolver task. Explicit cancellation cleanup belongs to task-root completion handlers, while helpers retain local exception-to-error boundaries. Grounded demand and immediately bound `FromArgument` variables keep Resolver21-23 simpler, while Resolver26 retains symbolic keys and runtime binding producers. Both coroutine families publish ordinary field failures as error values, including errors read through Query-fragment inputs. A thrown `CancellationException` becomes a field error only while the coroutine remains active; actual cancellation and JVM `Error`s propagate. Unexpected non-cancellation exceptions escaping launched orchestration tasks fail the request; synchronous factory and dispatch checks follow the caller's error boundary. `CoroutineResolverContract` checks their common promise lifecycle and [failure protocol](./src/main/kotlin/semantics/resolver26/design.md#failure-and-cancellation-protocol). `semantics.resolver26.CoroutineTaskDispatcher<O, F, C>` owns request-root scheduling for both coroutine families and calls their shared `semantics.resolver26.CoroutineOrchestrationTaskBase<O>` base directly. It implements the all-family `SharedTaskDispatcher<O, F>` value-work contract and adds the coroutine-only checker-publication type `C`; Resolver26 supplies its symbolic `SymbolicFieldCheckerPublicationOccurrence`; the grounded family supplies `GroundedFieldCheckerPublicationOccurrence`. Both retain concrete publication types and parallel checker tasks. The orchestration base retains the typed operation and paired OER contexts, owns the atomic one-shot dispatch check and preparation/dispatch/freezing sequence, and provides a validation hook. Concrete orchestration tasks retain their demand preparation, active-work predicate, and publication preparation; Resolver26 retains its passive-field validation and binding-declaration guard. Their concrete field-resolver tasks extend `semantics.resolver26.CoroutineFieldResolverTaskBase<P>`, which retains the typed publication context and helper scope and provides the common exception-to-field-error boundary. Concrete tasks retain their own resolution logic and setup/cleanup protocols. The `shared` package contains the operation context, variable-binding and cycle-check state, observer boundaries, grounding, materialization, and other operations used across resolver and correctness boundaries. [`resolver-versions.md`](../resolver-versions.md) explains the capability grid and how to use it.

Resolver21-23 create one immutable `GroundedFieldCheckerPublicationOccurrence` and dispatch one `CoroutineFieldCheckerTask` for each checked grounded field occurrence with a checker on either OER; unchecked-only checker inputs do not recursively request another check. The task retains its publication separately from its lifecycle. All ordinary field-value and checker publications across the pair are prepared before that orchestration dispatches them. List-element references discovered during passive value resolution use their own preparation/dispatch boundary. Resolver21 accepts only fragment-free checkers and passes their grounded field arguments. Resolver22 closes every checker's object and Query construction demand as unchecked demand in the containing orchestration's paired OERs. All resolver and checker owners in that containing occurrence share its associated Query OER, while every named checker member retains its owner-local raw object and Query projections for materialization. No checker-owned fresh Query root or separate Query-input producer exists. Checked and unchecked construction demand remain distinct through passive descent; active value resolvers reached through an unchecked path still add and consume their own inputs as checked demand. Each concrete OER orchestration likewise dispatches exactly one type-checker task when its concrete type has a checker and completes its OER-owned result with null otherwise. Resolver21 remains the fragment-free publication baseline; Resolver22/23 add meaningful enforcement through ordinary object- and declared Query-fragment inputs. `CheckerResult.Error.isErrorForResolver` receives the selected occurrence's generic field-directive context, and an applicable denial becomes `EngineErrorData` in the consuming input. Qplan assigns no built-in meaning to any directive name.

Resolver26 closes the same checked/unchecked object and Query demand while preserving symbolic keys. It declares checker bindings in the existing variable state, schedules `FieldCheckerTask` beside value tasks, and projects named inputs raw from the containing orchestration's paired OERs. From-field provider inclusion stays local to the defining alias, and named providers retain separate namespaces and one invocation per active checker occurrence. Checked inclusion can be false while overlapping unchecked demand activates the value; that occurrence receives an absent checker result. The [Resolver26 design](./src/main/kotlin/semantics/resolver26/design.md#field-checks) owns its preparation, activation, symbolic expansion, cancellation, and independent-scope details.

Resolver26 is the self-contained advanced resolver with runtime from-field bindings. It supports both `FromObjectField` and `FromQueryField`, extends reference targets with `FromQueryField` and `FromProvider`, and integrates references with conditioned passive activation; its current protocol is documented in [`resolver26/design.md`](./src/main/kotlin/semantics/resolver26/design.md).

Resolver22/23 and Resolver26 resolve `@parent` selections. Each installs the child's parent cell with the containing ancestor OER itself, including for list and nested-list child occurrences. Resolver input fragments may not use variables beneath a parent selection. Demand on `parent { ... }` is lifted one ancestor at a time, so repeated static closure handles grandparents. Both coroutine implementations use the shared parent-input analysis to close ancestor work before descending, so parent reads do not reopen orchestration. Their successor-demand policies also carry parent-induced demand into producer output before selective invocation.

Resolver01–03, Resolver06–08, and Resolver21 require a schema with no `@parent` fields (`world.parentFieldRelations.isEmpty()`), including fields not selected by the operation. This is an input-domain precondition, with no capability flag or runtime rejection checks. The depth-first versions order sibling resolver keys within one OER, but parent-induced work can require leaving a descendant for an ancestor and re-entering that same still-open descendant before either resolver can complete. Supporting that graph re-entry would require occurrence-aware suspension or orchestration beyond their intentionally small execution models. [`examples.md`](../examples.md#why-the-depth-first-resolvers-do-not-support-parent) demonstrates the ordering problem.

## Variable Production And Consumption

A variable recipe determines where one resolver-occurrence binding is produced. Independently, every occurrence of that variable in the resolver's object fragment or Query fragment is a consumer of the same binding. The fragment that consumes a variable does not determine or change its source, and a binding may be consumed by either fragment or by both.

| Recipe | Binding producer | Legal consumers |
| --- | --- | --- |
| `FromArgument` | A path rooted at an argument of the defining resolver occurrence | Object fragment, Query fragment, or both |
| `FromObjectField` | A provider path in the defining resolver's object fragment | Object fragment, Query fragment, or both |
| `FromQueryField` | A provider path in the defining resolver's Query fragment | Object fragment, Query fragment, or both |
| `FromProvider` | The defining resolver's one-shot tenant variables-provider function | Object fragment, Query fragment, or both |

Producer/consumer legality is distinct from current implementation support. `FromArgument` is implemented by every maintained resolver, while Resolver26 implements `FromObjectField`, `FromQueryField`, and `FromProvider`. Resolver26 invokes a provider once per active resolver occurrence after grounding that occurrence's arguments; every provider binding may be consumed by the object fragment, Query fragment, or both.

From-field reads use the defining object or Query fragment's local inclusion conditions. An excluded path step binds null before reserving or awaiting its OER value, even if another fragment or alias requests the same physical field. Selected intermediate and terminal null values also bind null; included field errors and failed condition bindings remain errors. The original conditioned fragments supply all construction demand: variable production does not add unconditional provider-path demand. Circular inclusion dependencies and statically excluded provider paths are rejected during registry assembly.

## Publication

Coroutine field-resolver tasks validate prepared publication metadata inside their field-error boundary before launching helpers or invoking resolvers. Both families check the containing type, object-field destination cell, and a reference target's registration; Resolver26 additionally checks its retained resolver and occurrence identity. Invalid metadata publishes a field error, preserving sibling progress. Resolver26 terminates the bindings of provider readers that validation prevented from starting. DFS keeps its existing synchronous preparation preconditions and fail-fast semantics; claiming a publication remains a preparation responsibility in all families.

A `SymbolicFieldPublicationOccurrence` retains its destination cell and initial `ValueSourceOccurrence`. In the case of references, resolution may transitively reach additional value sources before completing that cell's value slot.

An `EngineResultCell` has an activation decision, a reservable value promise, and a field-checker-result promise. Field-value resolution claims and publishes an `EngineResult` or GraphQL null after positive activation. Negative activation excludes the cell's promises. Resolver21–23 and Resolver26 resolve field-checker results independently of values; checker-free, unchecked-only, and otherwise non-applicable field occurrences terminate with null. Every concrete `ObjectEngineResult` owns one type-checker-result promise. An OER checked by a registered type checker receives a deferred promise completed exactly once by its orchestration so all checked consumers reaching the same occurrence reuse one result; an occurrence with no applicable type checker uses an immediate null promise.

OER construction is monotonic. Active cells have one writer, parent values may publish stable child OERs before those children complete, and each algorithm must install or reserve discoverable child work before a reader can depend on it.

Resolver-visible `EngineObjectData` does not retain OER identity. Materializing a parent selection follows the selected parent backedge and constructs a fresh finite EOD projection; the resulting object is not reference-equal to an EOD previously used to construct or materialize that ancestor. Parent backedges therefore do not enter the EOD carrier.

Sometimes-passive active fields make transitive parent demand conservative: a grandchild field that ultimately remains passive can still lift `parent.parent` demand and resolve or materialize unused ancestor fields. This marginal speculative work is an accepted precision tradeoff for keeping closure monotonic and independent of the later dynamic ownership decision.

## Resolution Observations

All maintained resolver families use the `ResolverObserver` carried by `SharedOperationContext`. Its implementations vary by observation use case, not by resolver family. Every callback defaults to no-op, allowing narrow consumers to implement the interface directly and record only what they need. `ResolverObserver.NOP` is the nested singleton used when no observations are needed. Observation belongs to semantics: neither `FieldValueResolver` nor model fixtures install an invocation callback. Resolver26 uses the same observer and execution entry points as the other families, without a separate `resolveObserved` path or observer adapter.

`SharedOperationContext.checkerObserver` is the separate access-check instrumentation boundary. Resolver21–23 and Resolver26 emit `onCheckerInvocation` after both checker inputs are ready and immediately before entering `FieldCheckerResolver.invoke`; its immutable payload records checker kind, logical Query root, exact occurrence path, grounded arguments, and checked schema coordinate. `CheckerApplicationRecorder` compares duplicate-preserving application multisets, so missing and over-executed checks fail independently of `correctResolution`. Resolver01–08 emit no checker events because they do not execute checker functions. Resolver26 preserves symbolic paths in these events and reports late-grounded arguments separately.

Resolver26's operation factory takes its observer from the base operation, and child scopes retain that same observer. Callbacks may run concurrently, so recording must be thread-safe; independent invocations have no guaranteed event order beyond each callback's documented lifecycle relationship. OER references remain live and potentially unfinished even when their observation payloads have immutable properties. Benchmark-only symbolic argument counts and variable-owner identities are derived by extension properties in the `semantics.benchmark` test fixtures, keeping shared event carriers limited to captured facts.

| Recording point | Families | Timing and evidence |
| --- | --- | --- |
| `onResolverInvocation` | 01–03, 06–08, 21–23, 26 | Immediately before each ordinary or reference-target `FieldValueResolver.invoke`, after its inputs are ready. Records field, input, instantiated input selections, resolved arguments, optional selective demand, exact occurrence identity, and path. A null demand denotes nonselective execution. Attempts that subsequently throw or cancel remain recorded; no output or outcome is recorded. |
| `onQueryFragmentPrepared` | All three execution implementations; declared Query fragments are supported by 02–03, 07–08, 22–23, 26 | After Query-rooted preparation and before dispatch. Associates each nonempty ordinary owner with its orchestration's associated Query OER and owning object occurrence; reference-target execution records its independently rooted input result without treating that result as the fresh occurrence's associated Query OER. Cells and values may still be unfinished. |
| `onRootFieldReferenceInvocation` | 01–03, 06–08, 21–23, 26 | After the reference-target helper returns, associates the original publication root/path and reference descriptor with the independently rooted invocation path/key and supplied demand. This is an association witness, not an outcome event; Resolver26 can emit it when input preparation returns an error without entering the target resolver. |
| `CheckerObserver.onCheckerInvocation` | 21–23 | Immediately before each `FieldCheckerResolver.invoke`, after its named object and Query inputs are ready. Records checker kind, logical Query root, exact occurrence path, grounded arguments, and checked coordinate. Attempts that subsequently throw or cancel remain recorded; no result is recorded. |
| `onTaskStarted` | 06–08 | The work-queue driver calls its internal optional hook just before running a dequeued orchestration or field-resolver task. Used by ordering contracts. Recursive declared-Query work uses the separate DFS driver and does not pass through this hook. |

Each execution implementation emits ordinary and reference-target invocations, associated Query-OER and owner associations, and reference-hop associations at its corresponding lifecycle boundaries. Independently rooted reference-target Query preparation remains a separate emission site. Grounded coroutine checker execution has one separate checker-observer emission site, and the work-queue hook is additional. Passive fields, variable-provider calls, value publication, failures, and cancellation have no separate shared observer events. A nested `ctx.query()` is distinct from a resolver's declared Query fragment: its resolver calls use the same operation observer, but the nested-query boundary itself emits no Query-fragment event.

`semantics.correctresolution.CorrectnessResolverObserver` directly supplies correctness evidence as snapshots: a set of invocation IDs plus duplicate-preserving Query-root and reference-hop records. The observer interface, no-op singleton, and event payloads remain in `semantics.shared`; resolver algorithms depend only on that API. Correctness consumers retain the recorder base and add invocation counts, arguments, or input fingerprints when needed. Narrow consumers implement `ResolverObserver` directly, including benchmark statistics and algorithm tests that retain only the recording their assertions need. The ordinary/reference invocation test retains a `CorrectnessResolverObserver` subclass because it uses all three recording categories to check observation delivery. Invocation-ID deduplication has both local algorithm-test coverage and a dedicated recorder test. DSL argument assertions, generated resolution witnesses, and benchmark statistics consume the same recording point. Correctness replay calls `evaluateRelation` without emitting algorithm observations. Generated selective-node fixtures additionally record the demand delivered to the raw node callback; concurrency tests count active dispatcher continuations, and benchmark/JFR wrappers measure operation and validation phases outside the algorithm observer API.
